# Lee Trader 점수 체계 정리 v1

## 0. 문서 목적

이 문서는 현재 프로젝트 소스 기준으로 다음 항목을 정리한다.

* 코드 파일별 점수 계산 위치
* 실제 컬럼명 사전
* 점수 정규화 방식
* 분위수/백분위 처리 방식
* acceptance report와 점수 체계 연결 방식
* score drift 감시 기준
* confidence calibration 방법

중요 전제:

1. 현재 프로젝트에는 **라이브 랭킹 점수 체계**와 **백테스트/히스토리 점수 체계**가 동시에 존재한다.
2. 두 체계는 일부 산식이 다르므로, 문서와 운영 시 반드시 구분해야 한다.
3. 현재 압축본 소스 기준으로는 `confidence_score` 생성 로직과 `acceptance report` 생성 코드는 확인되지 않았다.
4. 따라서 `confidence_score`, `acceptance report`, `score drift 감시`는 **현재 구현 사실**과 **운영 설계 제안**을 분리해서 다룬다.

# 1. 코드 파일별 점수 계산 위치

## 1.1 `quality_builder.py`

역할:

* `fundamentals.csv`를 읽어 재무 품질 점수 원점수인 `quality_score`를 생성한다.

핵심 함수:

* `_zscore(series)`
* `build_quality(df)`

입력 후보 컬럼:

* `roe`
* `op_margin`
* `net_margin`
* `debt_ratio`

유연 매핑 후보:

* `roe`, `ROE`, `return_on_equity`
* `op_margin`, `operating_margin`, `OPE_MARGIN`
* `debt_ratio`, `debt`, `liabilities_ratio`
* `net_margin`, `netprofit_margin`, `NPM`

산식 개요:

* `roe`, `op_margin`, `net_margin`는 높을수록 우수
* `debt_ratio`는 낮을수록 우수하므로 부호 반전
* 각 지표를 z-score로 표준화 후 가중합
* 최종 `quality_score`를 `[-3, 3]` 범위로 clip

가중치:

* `z_roe`: 0.35
* `z_op`: 0.25
* `z_net`: 0.20
* `z_debt_inv`: 0.20

보정 방식:

* 실제로 존재하는 지표만 사용
* 사용 가능한 지표만 합이 1이 되도록 가중치 재정규화

출력:

* `date`
* `code`
* `quality_score`

# 3. 점수 정규화 방식

현재 프로젝트에는 정규화 방식이 하나가 아니라 여러 개가 공존한다.

---

## 3.1 z-score 정규화

사용 위치:

* `quality_builder.py`
* `scoring.py` 일부 함수

정의:

```text
z = (x - mean) / std
```

특징:

* 단면 기준 상대적 우수도를 표준화한다.
* `quality_builder.py`에서는 각 재무 지표를 z-score로 만든 뒤 가중합한다.
* 최종 `quality_score`는 `[-3, 3]`으로 clip된다.

의미:

* 재무 품질의 원점수 성격
* 아직 0~100 점수는 아님

---

## 3.2 날짜별 percentile 정규화 (0~100)

사용 위치:

* `ranking_builder.py`
* `build_backtest_predictions.py`

구현:

```python
s.rank(pct=True, ascending=True) * 100
```

특징:

* 같은 날짜 안에서 상대순위를 0~100 점수로 변환한다.
* 절대값보다 해당 날짜 유니버스 내 위치를 반영한다.

적용 대상 예:

* `tech_score`
* `pred_score_60`
* `pred_score_90`
* `qual_score`
* `vol_20_pct`
* `vol_60_pct`
* `liquidity_score`

의미:

* 해당 날짜 내 상대적 강약을 점수화한다.

---

## 3.3 날짜별 percentile 정규화 (0~1)

사용 위치:

* `ranking_builder.py`

구현:

```python
s.rank(pct=True, ascending=True)
```

적용 대상:

* `pred_return_60d_pct01`
* `pred_return_90d_pct01`

용도:

* `ret_score_v11` 계산용 중간 스케일

산식:

```text
ret_score_v11 = 100 * (0.7 * pred_return_60d_pct01 + 0.3 * pred_return_90d_pct01)
```

중요:

* `ret_score_v11`은 존재하지만,
* 현재 라이브 최종 점수에서는 `ret_score = pred_score`가 사용된다.
* 즉 `ret_score_v11`은 현재 운영 핵심 점수라기보다 실험/후보 산식 흔적에 가깝다.

---

## 3.4 직접 스케일링

### `prob_score`

`ranking_builder.py`:

```text
prob_score = prob_top20_60d * 100
```

범위:

* `0 ~ 100`

### `risk_penalty`

`ranking_builder.py`:

```text
penalty_raw = max(0, -pred_mdd_60d - 0.15)
risk_penalty = penalty_raw * 100
final_score = final_score - risk_penalty
```

의미:

* 예측 최대낙폭이 -15%보다 깊으면 그 초과분만큼 감점한다.

예시:

* `pred_mdd_60d = -0.12` → 감점 0
* `pred_mdd_60d = -0.20` → 감점 5점
* `pred_mdd_60d = -0.30` → 감점 15점

# 4. 분위수 / 백분위 처리 방식

## 4.1 라벨 생성 시 분위수 처리

`label_builder.py` 기준:

```text
target_{h}d_top20 = 1 if target_{h}d >= date별 80% 분위수 else 0
```

해석:

* 해당 날짜 단면에서 수익률 상위 20% 종목을 positive label로 둔다.
* 즉 분류모델 확률 `prob_top20_*`는
  **“상위 20% 진입 확률”**이다.

---

## 4.2 점수 산정 시 백분위 처리

`ranking_builder.py` 기준:

```text
percentile = rank(pct=True) * 100
```

해석 예:

* 95점: 해당 날짜 유니버스 상위권
* 50점: 중간 수준
* 10점: 하위권

중요한 점:

* 이 점수는 절대 수익률/절대 품질을 뜻하지 않는다.
* 같은 날짜 안에서의 상대적 위치다.
* 따라서 날짜가 다르면 동일 점수라도 절대 의미는 달라질 수 있다.

---

## 4.3 tie 처리

`rank(pct=True)` 기본 동작을 사용하므로 동일값 tie는 pandas 기본 rank 규칙을 따른다.

운영상 의미:

* 동일값이 많으면 백분위가 계단형으로 뭉칠 수 있다.
* 특히 분산이 작은 품질 지표나 변동성 지표는 tie 영향 점검이 필요하다.

# 5. 라이브 점수 체계 상세

## 5.1 `tech_score`

우선순위:

1. `composite`가 있으면 날짜별 percentile
2. 없으면 `score_score` 날짜별 percentile
3. 둘 다 없으면 NaN 후 최종 계산 시 0 처리

정의:

```text
tech_score = percentile_by_date(composite or score_score)
```

---

## 5.2 `pred_score`

정의:

* `pred_return_60d`, `pred_return_90d`를 각각 날짜별 percentile로 변환 후 혼합

산식:

```text
pred_score_60 = percentile_by_date(pred_return_60d)
pred_score_90 = percentile_by_date(pred_return_90d)

pred_score = 0.6 * pred_score_60 + 0.4 * pred_score_90
```

예외:

* 60d만 있으면 그것만 사용
* 90d만 있으면 그것만 사용

---

## 5.3 `ret_score`

현재 라이브 정의:

```text
ret_score = pred_score
```

즉 현재 운영상 `ret_score`는 별도 독립 산식이 아니라
**`pred_score`의 alias**다.

이 점은 문서에서 반드시 명확히 적어야 한다.

---

## 5.4 `prob_score`

정의:

```text
prob_score = clip(prob_top20_60d * 100, 0, 100)
```

특징:

* 현재 라이브 랭킹에서는 60일 분류 확률만 직접 반영한다.
* 90일 분류 확률은 메인 `prob_score`에 직접 반영되지 않는다.

---

## 5.5 `qual_score`

정의:

```text
qual_score = percentile_by_date(quality_score)
```

특징:

* `quality_builder.py`의 원점수 `quality_score`를 다시 날짜별 상대순위 점수로 변환한다.

---

## 5.6 `safety_score`

정의:

* 변동성이 낮을수록 높은 점수

산식:

```text
vol_20_pct = percentile_by_date(vol_20)
vol_60_pct = percentile_by_date(vol_60)

safety_score = 평균(100 - vol_20_pct, 100 - vol_60_pct)
```

예외:

* 둘 중 하나만 있으면 그 값만 사용
* 둘 다 없으면 NaN 후 최종 계산 시 0 처리

---

## 5.7 `liquidity_score`

우선순위:

1. `vol_ma_20`
2. `volume`

정의:

```text
liquidity_score = percentile_by_date(vol_ma_20 or volume)
```

---

## 5.8 `final_score`

라이브 기본 산식:

```text
final_score =
    0.15 * tech_score
  + 0.30 * pred_score
  + 0.25 * prob_score
  + 0.10 * qual_score
  + 0.15 * safety_score
  + 0.05 * liquidity_score
```

그 후 리스크 감점:

```text
risk_penalty = max(0, -pred_mdd_60d - 0.15) * 100
final_score = final_score - risk_penalty
```

결측치 처리:

* `tech_score`
* `pred_score`
* `prob_score`
* `qual_score`
* `safety_score`
* `liquidity_score`

위 구성요소 NaN은 모두 0으로 대체 후 계산한다.

운영상 주의:

* 결측이 많으면 점수 0 처리로 인해 특정 종목이 구조적으로 불리해질 수 있다.
* 문서상 “결측은 중립이 아니라 사실상 불이익”이라고 보는 것이 더 정확하다.

---

# 6. 백테스트 점수 체계 상세

`build_backtest_predictions.py`는 라이브와 다른 별도 점수 체계를 가진다.

## 6.1 `ret_score`

산식:

```text
r_comb = 평균(pred_return_30d, pred_return_60d, pred_return_90d)
pred_mdd_comb = 평균(pred_mdd_30d, pred_mdd_60d, pred_mdd_90d)
r_adj = r_comb / (1 + 3.0 * abs(pred_mdd_comb))
ret_score = clip(50 + 10 * zscore(r_adj), 0, 100)
```

특징:

* 라이브 percentile 기반 점수와 다르게
* 백테스트에서는 risk-adjusted return을 z-score 방식으로 0~100에 사상한다.

---

## 6.2 `prob_score`

산식:

```text
prob = prob_top20_30d 우선, 없으면 prob_top20_60d, 없으면 prob_top20_90d
prob_score = clip(prob * 100, 0, 100)
```

---

## 6.3 `qual_score`

산식:

```text
qual_score = percentile_by_date(quality_score)
```

---

## 6.4 `tech_score`

우선순위:

1. `vol_ma_20`
2. `vol_ratio_20`
3. `vol_20`

산식:

```text
tech_score = percentile_by_date(selected_col)
```

주의:

* 라이브의 `tech_score`는 `composite / score_score`
* 백테스트의 `tech_score`는 `vol_ma_20 / vol_ratio_20 / vol_20`
* 즉 정의가 완전히 다르다.

이건 문서에서 반드시 크게 표시해야 한다.

---

## 6.5 `risk_penalty`

산식:

```text
dd = mean(abs(pred_mdd_30d), abs(pred_mdd_60d), abs(pred_mdd_90d))
risk_level = clip(dd / 0.4, 0, 1)
risk_penalty = clip(1 - 0.5 * risk_level, 0.5, 1.0)
```

특징:

* 라이브는 “감점 점수”
* 백테스트는 “곱셈형 penalty multiplier”
* 정의가 다르다.

---

## 6.6 `final_score`

산식:

```text
base =
    0.4 * ret_score
  + 0.25 * prob_score
  + 0.15 * qual_score
  + 0.10 * tech_score
  + 0.10 * 60

final_score = clip(base * risk_penalty, 0, 100)
```

여기서 `60`은 bias score 역할이다.

# 7. acceptance report 와 점수 체계 연결

## 7.1 현재 구현 사실

현재 압축본 소스 기준으로:

* `acceptance report` 생성 코드
* `acceptance score`
* `acceptance gate`

는 확인되지 않았다.

즉 현재 단계에서는 acceptance report가
**별도 스크립트/외부 문서/수동 검증 체계**에 있을 가능성이 높다.

---

## 7.2 운영 문서상 정의해야 할 연결 방식

acceptance report는 점수 체계 변경의 품질 보증 문서로 정의하는 것이 적절하다.

핵심 목적:

* 점수 산식 수정 후
* 추천 결과가 얼마나 변했는지
* 그 변화가 허용 가능한지
* 성능이 개선되었는지
  를 확인하는 것

---

## 7.3 acceptance report에서 반드시 연결해야 할 점수 항목

### A. `ret_score`

의미:

* 수익 기대 축 변화 감시

권장 체크:

* Top20 평균 `ret_score`
* 전체 평균 `ret_score`
* 기준 버전 대비 증감

### B. `prob_score`

의미:

* 상위권 진입 확률 축 변화 감시

권장 체크:

* Top20 평균 `prob_score`
* 전체 평균 `prob_score`
* calibration 전후 분포 변화

### C. `final_score`

의미:

* 최종 순위 시스템의 직접 결과

권장 체크:

* Top20 churn
* 상위 5/10/20 종목 교체율
* rank 이동 폭

### D. `qual_score`

의미:

* 품질 편향 여부 점검

권장 체크:

* 상위권 종목의 평균 `qual_score`
* 산식 수정 후 quality 축이 과도하게 무시되거나 과도하게 강화되지 않았는지

### E. `risk_penalty`

의미:

* 점수 체계 변경이 리스크 높은 종목을 과도하게 끌어올리지 않는지 확인

권장 체크:

* Top20 평균 predicted MDD
* penalty 적용 전/후 점수 순위 차이

---

## 7.4 acceptance report 권장 지표

문서상 아래 항목을 표준으로 권장한다.

* Top20 churn
* Top10 churn
* 평균 `final_score` 변화
* 평균 `ret_score` 변화
* 평균 `prob_score` 변화
* 평균 `qual_score` 변화
* 평균 `pred_mdd_60d` 변화
* 상위권 업종 쏠림 변화
* 과거 성과 지표 변화

  * hit rate
  * 평균 realized return
  * max drawdown
  * turnover

---

## 7.5 acceptance 판단 예시 기준

예시:

* `Top20 churn <= 30%`: 안정적
* `Top20 churn 30~50%`: 주의
* `Top20 churn > 50%`: 산식 급변 가능성 점검 필요

추가 예시:

* Top20 평균 `ret_score` 하락 + Top20 평균 `prob_score` 하락이면 보수적으로 reject 검토
* churn이 높더라도 백테스트 성과가 유의미하게 개선되면 conditional accept 가능

# 8. score drift 감시 기준

## 8.1 현재 구현 사실

현재 압축본 소스 안에 명시적인 drift monitoring 로직은 확인되지 않았다.

즉 score drift 감시는 현재 구현이 아니라
**운영상 반드시 추가해야 하는 감시 체계**다.

---

## 8.2 왜 drift 감시가 필요한가

이 프로젝트 점수는 상당 부분 날짜별 percentile 기반이다.

따라서 아래 문제가 생길 수 있다.

* 입력 피처 분포 변화
* 예측값 분포 붕괴
* 특정 날짜 유니버스 구성이 달라져 점수 해석이 흔들림
* 모델 리트레이닝 후 확률 calibration 붕괴
* 점수 평균은 비슷하지만 상위 종목이 크게 바뀌는 현상

---

## 8.3 권장 drift 감시 항목

### A. 분포 drift

매일 또는 리밸런싱 시점마다 아래를 기록:

* 전체 평균 `ret_score`
* 전체 표준편차 `ret_score`
* 전체 평균 `prob_score`
* 전체 표준편차 `prob_score`
* 전체 평균 `qual_score`
* 전체 평균 `final_score`
* 전체 평균 `pred_mdd_60d`

경보 예시:

* 최근 20영업일 평균 대비 `±2σ` 이탈 시 경고
* `±3σ` 이탈 시 강경고

---

### B. 랭킹 drift

상위권 변동성 감시:

* Top20 churn
* Top10 churn
* Top20 평균 `final_score`
* Top20 평균 `ret_score`
* Top20 평균 `prob_score`
* Top20 평균 `pred_mdd_60d`

경보 예시:

* Top20 churn > 0.30 → 주의
* Top20 churn > 0.50 → 강경고

---

### C. 피처 결측 drift

결측 0처리 구조 때문에 반드시 감시 필요:

* `quality_score` 결측 비율
* `prob_top20_60d` 결측 비율
* `pred_return_60d`, `pred_return_90d` 결측 비율
* `vol_20`, `vol_60`, `vol_ma_20` 결측 비율

경보 예시:

* 핵심 컬럼 결측률이 직전 평균 대비 2배 이상 상승 시 경고

---

### D. sector / market composition drift

상위권이 특정 테마나 업종에 몰리는지 확인:

* Top20 sector concentration
* 시총 분포
* KOSPI/KOSDAQ 비중
* 거래대금 상위 편중 여부

---

# 9. confidence calibration 방법

## 9.1 현재 구현 사실

현재 압축본 소스 기준으로는:

* `prob_score`는 존재
* `confidence_score` 생성 로직은 확인되지 않음

즉 현재 코드 기준 문서에는 다음처럼 적는 것이 정확하다.

> 현재 구현에는 `prob_score`는 존재하지만, 별도의 `confidence_score` 계산 및 calibration 파이프라인은 확인되지 않았다.

---

## 9.2 confidence와 prob의 차이

* `prob_score`: 모델이 예측한 상위 20% 진입 확률을 점수화한 값
* `confidence_score`: 그 확률 예측을 얼마나 신뢰할 수 있는지까지 반영한 운영용 신뢰도 점수

즉 둘은 같지 않다.

예:

* `prob_top20_60d = 0.75`라도
* 최근 calibration이 깨졌거나
* horizon 간 방향 불일치가 크거나
* 리스크가 과도하면
* confidence는 더 낮아야 한다.

---

## 9.3 권장 calibration 1단계: 확률 보정

분류모델 출력 확률 `prob_top20_60d`, `prob_top20_90d`에 대해 calibration을 적용한다.

추천 방법:

* 데이터가 충분하면 `Isotonic Regression`
* 표본이 적거나 안정성이 중요하면 `Platt Scaling`

권장 절차:

1. out-of-fold 예측 확률 수집
2. 실제 `target_60d_top20`, `target_90d_top20`와 비교
3. calibration model 적합
4. 추론 시 raw probability 대신 calibrated probability 사용

---

## 9.4 권장 calibration 2단계: confidence_score 별도 정의

예시 정의:

```text
confidence_raw =
    0.50 * calibrated_prob_60d
  + 0.20 * calibrated_prob_90d
  + 0.15 * return_agreement
  + 0.15 * risk_stability
```

최종 변환:

```text
confidence_score = clip(100 * confidence_raw, 0, 100)
```

---

## 9.5 보조 구성요소 예시

### `return_agreement`

의미:

* 60d와 90d 예측 수익 방향 및 강도가 일관적인지

예시:

* 둘 다 양수이고 percentile 상위 → 높게
* 한쪽만 강하고 다른 쪽이 약함 → 중간
* 방향이 반대 → 낮게

### `risk_stability`

의미:

* 예측 MDD가 과도하지 않고 안정적인지

예시:

* `pred_mdd_60d`와 `pred_mdd_90d`가 모두 허용 범위 안 → 높게
* 둘 중 하나라도 과도한 낙폭 → 낮게

---

## 9.6 confidence calibration 검증 지표

추가로 아래를 모니터링해야 한다.

* Brier score
* Log loss
* Reliability curve
* Decile hit rate
* Probability bin별 실제 hit rate

권장 해석:

* `0.8` 확률 구간 종목들이 실제로도 대체로 높은 hit rate를 보여야 한다.
* 그렇지 않으면 확률은 높아도 confidence는 낮게 부여해야 한다.

# 10. 현재 문서화 시 반드시 적어야 할 주의사항

## 10.1 라이브 점수와 백테스트 점수는 다르다

가장 중요하다.

특히 다음 항목은 서로 다르다.

* `ret_score`
* `tech_score`
* `risk_penalty`
* `final_score`

따라서 문서에 “점수 체계”를 한 벌로만 적으면 안 되고,
반드시 아래처럼 구분해야 한다.

* 라이브 운영 점수 체계
* 백테스트/히스토리 점수 체계

---

## 10.2 현재 라이브 `ret_score`는 독립 점수가 아니다

현재 구현:

```text
ret_score = pred_score
```

즉 운영상 `ret_score`는 사실상
`pred_return_60d`, `pred_return_90d` percentile 혼합 점수다.

---

## 10.3 `ret_score_v11`은 존재하지만 메인 운영 점수는 아니다

`ranking_builder.py` 안에 `ret_score_v11`이 존재하지만,
실제 최종 점수 결합에는 `pred_score`가 사용된다.

따라서 문서에서는 `ret_score_v11`을

* 실험용
* 후보 산식
* 참고용 중간 컬럼

중 하나로 분리 기재해야 한다.

---

## 10.4 `confidence_score`는 아직 설계/구현 과제다

현재 압축본 기준으로는 confidence 점수는 미구현으로 보는 편이 정확하다.

---

## 10.5 결측치 처리 방식은 점수 왜곡 가능성이 있다

라이브 랭킹에서 주요 구성 점수 결측치는 모두 `0`으로 채운다.

이 방식은 단순하지만,

* 데이터 누락
* 피처 생성 실패
* 특정 종목만 재무 데이터 부재

같은 상황에서 점수 체계를 구조적으로 왜곡할 수 있다.

따라서 향후에는

* 결측 이유 플래그
* 중립 대체값
* hard gate
  중 하나를 검토하는 것이 좋다.
