# 20260421 모의투자-실자동매매 통합 전략 설계안

## 1. 문서 목적

이 문서는 현재 분리되어 있는

- `모의투자(paper trading)`
- `실자동매매(live auto trading)`

를 장기적으로 같은 전략 엔진 위에 올리기 위한 설계안입니다.

핵심 목표는 다음과 같습니다.

- 모의투자와 실자동매매가 같은 전략 규칙을 사용하도록 정렬
- 실자동매매에는 실계좌/실주문 제약만 추가
- 두 결과를 매일 비교 가능하게 만들어 원인 분석을 쉽게 함

한 줄로 요약하면:

`전략은 하나로, 실행 레이어는 둘로 분리한다`

- 모의투자에서 좋은 성과가 나온 전략이 왜 실자동매매에서는 다르게 보이는가
- 차이가 전략 때문인가, 실행 제약 때문인가
- 실전 성과 저하가 종목선정 문제인가, 체결/현금/수량 문제인가

## 3. 목표 상태

목표 상태는 아래 구조입니다.

### 3.1 공통 전략 엔진

공통 전략 엔진은 아래만 책임집니다.

- 입력 후보 집합에서 전략상 어떤 종목을 선택할지
- 현재 보유를 어떻게 유지/축소/청산할지
- 신규 진입과 교체를 어떤 조건에서 허용할지
- 목표 비중을 어떻게 계산할지

즉 전략 엔진의 출력은 브로커 주문이 아니라 `전략 액션`입니다.

예:

- `ENTER`
- `ADD`
- `HOLD`
- `TRIM`
- `EXIT`
- `REPLACE`
- `NO_ACTION`

### 3.2 모의투자 레이어

공통 전략 엔진이 만든 액션을

- 가상 가격
- 가상 수수료
- 가상 슬리피지
- 가상 NAV

로 변환합니다.

### 3.3 실자동매매 레이어

공통 전략 엔진이 만든 액션을

- 계좌 현금
- 보유 수량
- 주문 가능 수량
- 실계좌 시장 상태
- 주문 승인/안전 제약

으로 필터링한 뒤 실주문으로 제출합니다.

즉 차이는 아래뿐입니다.

- 전략 결정: 공통
- 실행 제약: 환경별 차이

## 4. 권장 아키텍처

권장 구조는 아래 3계층입니다.

### 4.1 Layer A: Strategy Core

새 공통 전략 엔진

예상 책임:

- candidate universe 정리
- 진입 적격성 판단
- 보유 종목 평가
- 교체 판단
- 목표 비중 계산
- 전략 액션 생성

입력 예시:

- 추천 후보 DataFrame
- 현재 보유 포지션
- 전략 설정
- gate 상태
- 모드 정보(`paper`, `live`)

출력 예시:

- `strategy_actions.json`
- row 단위 액션 목록

예상 컬럼:

- `code`
- `name`
- `strategy_action`
- `action_reason`
- `target_weight`
- `priority`
- `entry_eligible`
- `replacement_candidate`
- `exit_candidate`

### 4.2 Layer B: Simulation Adapter

모의투자 전용 변환 레이어

책임:

- 전략 액션을 종가 기반 가상 체결로 변환
- 포지션 레저 갱신
- NAV 산출
- 승률/드로다운 산출

기존 [python/run_paper_trading_ledger.py](/d:/ai/lee_trader/python/run_paper_trading_ledger.py)가 이 역할을 맡되,
후보 선택 부분은 공통 엔진 호출로 교체합니다.

### 4.3 Layer C: Live Execution Adapter

실자동매매 전용 변환 레이어

책임:

- 전략 액션을 실계좌 주문 의도로 변환
- 실계좌 보유/현금/가능수량 반영
- 주문 제한 적용
- preview / execute / execution result 생성

기존

- [python/build_trade_intents.py](/d:/ai/lee_trader/python/build_trade_intents.py)
- [python/submit_live_orders.py](/d:/ai/lee_trader/python/submit_live_orders.py)

가 이 역할을 맡되, 전략 판단은 공통 엔진 결과를 사용하도록 변경합니다.

## 5. 무엇을 공통화할 것인가

공통 전략 엔진으로 올려야 하는 항목은 아래입니다.

### 5.1 후보 선택 규칙

현재 모의투자는 `top5/top8/top10` 스냅샷 중심이고,
실자동매매는 `top20 -> review top8/top10 -> gate 제한` 구조입니다.

공통화 원칙:

- 하나의 기본 candidate pool 사용
- 전략 모드에 따라 target size만 다르게 설정
- rank/confidence/liquidity/trading value 조건을 같은 함수에서 평가

### 5.2 보유 평가 규칙

공통화 대상:

- 계속 보유 조건
- 추가 매수 허용 조건
- 축소 필요 조건
- 청산 후보 조건

### 5.3 청산 규칙

모의투자의

- 보유 20거래일 종료
- 손절
- confidence 붕괴
- 점수 약화
- rank fade

를 실자동매매에서도 같은 전략 판단 코드로 해석 가능하게 해야 합니다.

### 5.4 교체 규칙

현재 실자동매매에는 `REPLACE_CANDIDATE` 개념이 있고,
모의투자에는 replacement mode가 별도 옵션입니다.

이 둘을 공통화해서

- 어떤 보유 종목을 비우고
- 어떤 새 종목을 대체 진입시키는지

하나의 전략 규칙으로 설명 가능해야 합니다.

### 5.5 목표 비중 규칙

공통화 대상:

- target weight 계산
- confidence band 반영
- per-position cap
- sector/theme cap

단, live에서는 여기에

- 현금 부족
- 주문 가능 수량

이 추가됩니다.

## 6. 무엇을 분리할 것인가

아래 항목은 실자동매매 전용 제약으로 남겨야 합니다.

### 6.1 계좌 제약

- 가용 현금
- 주문 가능 수량
- 최소 주문 수량
- 이미 보유 중인 종목 수량

### 6.2 브로커 제약

- API 실패
- 장 상태
- 시장가/지정가
- 주문 재시도
- 체결 미완료

### 6.3 운영 제약

- `WATCH / PILOT / BUY_ALLOWED`
- 실전 신규 진입 종목 수 제한
- 총 실전 노출 비중 제한
- 종목당 최대 실전 비중 제한

즉 아래 관계가 됩니다.

- 전략 엔진: “사는 게 맞는가?”
- 실행 레이어: “지금 실제로 살 수 있는가?”

## 9. 단계별 전환 계획

한 번에 갈아엎지 말고 아래 순서가 적절합니다.

목표:

- `outputs/live_vs_paper_action_diff.json`

목표:

- hold-days

목표:

- “전략은 맞았는데 실행이 막힌 것인지”

## 12. 운영상 기대 효과

통합 설계가 완료되면 아래 이점이 있습니다.

### 12.1 설명 가능성 증가

“왜 이 종목을 샀는가 / 왜 안 샀는가”를 전략과 실행으로 분리해 설명 가능

### 12.2 검증 신뢰도 증가

모의투자 성과와 실거래 결과의 차이를 직접 비교 가능

### 12.3 디버깅 속도 증가

문제 원인을 아래처럼 빨리 분리 가능

- 전략 문제
- 계좌 문제
- 브로커 문제
- 운영 제한 문제

### 12.4 BUY_ALLOWED 승격 판단 개선

실전 승격 판단이 더 정교해집니다.

## 13. 권장 원칙

설계 원칙은 아래 4개를 유지하는 것이 좋습니다.

1. 전략 결정과 주문 실행을 분리한다.
2. 모의투자와 실자동매매는 같은 전략 액션을 공유한다.
3. 실거래 차이는 항상 명시적 blocker로 남긴다.
4. 운영자가 결과 차이를 파일/웹에서 바로 볼 수 있게 만든다.

## 14. 최종 결론

현재 프로젝트는 장기적으로 아래 구조로 가는 것이 맞습니다.

- 모의투자: 전략 엔진의 기준선
- 실자동매매: 같은 전략 엔진의 실주문 실행판
- 차이: 실계좌 제약과 운영 안전장치만 추가

즉 최종 목표는

`모의투자와 실자동매매가 서로 다른 시스템이 아니라, 같은 전략을 서로 다른 실행 환경에서 돌리는 두 개의 어댑터`

가 되는 것입니다.

이 방향이 되면

- 전략 검증
- 실주문 검증
- 승격 판단
- 장애 분석

이 모두 훨씬 쉬워집니다.
