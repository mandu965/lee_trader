# 2026-04-28 분석 인프라 준비

## 1. 배경

현재 자동매매 시스템은 단순 추천/주문 생성 단계를 넘어, 실운영 데이터가 쌓이는 구조로 이동하고 있다.

이미 운영 서버 기준으로는 다음 흐름이 형성되어 있다.

- `research.live_trade_decision`: 매매 판단
- `research.live_order_request`: 주문 요청 초안
- `research.live_order_execution`: 브로커 제출 결과
- `research.live_order_fill`: 실제 체결
- `research.live_position_snapshot`: 실계좌 보유/자산 스냅샷
- `research.live_trade_review`: 체결 후 D0/D+1/D+3/D+5 사후 리뷰

따라서 다음 개발의 핵심은 "데이터를 쌓을 수 있나"가 아니라, 쌓인 데이터를 어떻게 신뢰 가능한 운영 판단으로 바꿀 것인가이다.

## 2. 기본 방향

분석 인프라는 주문 시스템과 느슨하게 분리한다.

원칙:

- 운영 원천 테이블은 그대로 둔다.
- 분석은 별도 `analytics` schema 또는 view 계층에서 수행한다.
- 운영 화면은 분석 결과를 읽기만 한다.
- 표본이 부족한 지표는 매매 파라미터 변경 근거로 사용하지 않는다.
- D0/D+1/D+3/D+5 사후성과와 실제 실현손익은 분리해서 본다.

권장 구조:

```text
research.live_order_fill          원천 체결
research.live_order_request       주문 의도/점수
research.live_order_execution     제출 결과
research.live_position_snapshot   계좌 스냅샷
research.live_trade_review        사후성과

analytics.live_trade_fact         체결+점수+의도 결합
analytics.live_daily_account_nav  일별 계좌 NAV
analytics.live_closed_trade       매수-매도 매칭 실현손익
analytics.live_review_kpi         D0/D1/D3/D5 사후성과 KPI
analytics.live_score_bucket_kpi   점수구간별 성과
```

## 3. KPI 정의 기준

### 3.1 판단 품질 KPI

판단 품질은 체결 후 특정 시점의 가격 변화를 본다.

기본 관찰 구간:

- D0: 당일 체결 후 같은 날 기준 성과
- D+1: 익영업일 성과
- D+3: 3영업일 후 성과
- D+5: 5영업일 후 성과
- D+20: 중기 확인용, 표본이 쌓인 뒤 사용

기본 운영 판단 기준은 D+5를 우선한다. D0는 체결 품질과 당일 노이즈가 섞이므로 보조 지표로만 본다.

필수 KPI:

| KPI | 정의 |
| --- | --- |
| count | 전체 리뷰 대상 수 |
| observed_count | 해당 horizon 가격 데이터가 확보된 수 |
| win_rate | 관찰 수 중 수익률이 양수인 비율 |
| avg_return | 단순 평균 수익률 |
| weighted_avg_return | 체결 금액 가중 평균 수익률 |
| avg_win | 수익 거래의 평균 수익률 |
| avg_loss | 손실 거래의 평균 손실률 절댓값 |
| payoff_ratio | `avg_win / avg_loss` |
| expectancy | `win_rate * avg_win - (1 - win_rate) * avg_loss` |

### 3.2 실제 운용 KPI

실제 운용 KPI는 사후 가격 변화가 아니라 계좌와 체결 기준으로 계산한다.

필수 KPI:

| KPI | 정의 |
| --- | --- |
| total_assets | 실계좌 총자산 |
| cash_amount | 예수금/현금 |
| cash_ratio | `cash_amount / total_assets` |
| daily_pnl | 전일 대표 NAV 대비 증감 |
| monthly_return | 월초 대표 NAV 대비 수익률 |
| realized_pnl | 매도 체결 기준 실현손익 |
| unrealized_pnl | 보유 종목 평가손익 |
| mdd | 일별 대표 NAV 기준 최대낙폭 |
| turnover | 일별 체결금액 / 총자산 |

### 3.3 실현손익 KPI

실현손익은 `live_order_fill`만으로 단순 계산하지 않는다. 매수/매도 체결을 종목별로 매칭해야 한다.

1차 구현은 평균단가 방식으로 충분하다.

필수 필드:

```text
trade_group_id
code
name
entry_request_id
exit_request_id
entry_at
exit_at
entry_qty
exit_qty
entry_price
exit_price
gross_pnl
fee
tax
net_pnl
net_return
holding_days
entry_final_score
entry_confidence_score
entry_rank
entry_intent_type
exit_intent_type
```

주의:

- 부분매도는 `remaining_qty`를 추적한다.
- TRIM은 완전 청산이 아니므로 closed trade와 partial realized pnl을 분리해서 볼 수 있어야 한다.
- 세금/수수료가 누락되면 gross/net을 명확히 구분한다.

## 4. 분석 축

데이터가 쌓인 뒤 최소한 아래 축으로 나눠 볼 수 있어야 한다.

| 분석 축 | 목적 |
| --- | --- |
| `intent_type` | BUY/TRIM/EXIT 판단 품질 확인 |
| `rank_bucket` | top rank가 실제로 더 좋은지 확인 |
| `final_score_bucket` | 점수 cutoff 검증 |
| `confidence_bucket` | confidence가 의미 있는지 확인 |
| `risk_penalty_bucket` | 위험 감점이 손실 회피에 기여하는지 확인 |
| `dominant_theme` | 특정 테마 반복 손실/수익 확인 |
| `market_gate` | BLOCK/WATCH/PILOT/BUY_ALLOWED 상태별 성과 |
| `weekday` | 요일별 체결 성과 확인 |
| `entry_time_bucket` | 09:30, 10:00, 오후 등 시간대 성과 확인 |
| `holding_days` | 보유기간별 수익 구조 확인 |

추천 bucket:

```text
rank_bucket:
  rank_1_3
  rank_4_8
  rank_9_20
  rank_21_plus

final_score_bucket:
  score_90_plus
  score_80_89
  score_75_79
  score_70_74
  score_under_70

confidence_bucket:
  conf_90_plus
  conf_80_89
  conf_70_79
  conf_under_70

risk_penalty_bucket:
  risk_0
  risk_low
  risk_mid
  risk_high
```

## 5. 표본 신뢰도 기준

표본 부족 상태에서 매매 룰을 바꾸면 과최적화 위험이 크다.

기본 상태값:

| 상태 | 기준 | 의미 |
| --- | --- | --- |
| `INSUFFICIENT_SAMPLE` | `observed_count < 30` | 참고만 가능 |
| `MONITOR_ONLY` | `30 <= observed_count < 100` | 감시 가능, 파라미터 변경 금지 |
| `ACTIONABLE` | `observed_count >= 100` | 운영 판단 후보 |
| `DEGRADE_CONFIRMED` | 충분한 표본에서 기대값 악화 반복 | 룰 변경 검토 가능 |

그룹별 최소 기준:

- intent별 비교: 관찰 30건 이상
- rank bucket별 비교: 관찰 30건 이상
- score bucket별 cutoff 검토: 관찰 50건 이상
- theme별 평가: 관찰 50건 이상
- D+5 기준 분석: D+5 관찰 30건 이상

화면과 리포트에는 항상 `sample_status`를 표시한다.

## 7. 개발 순서

### 1단계: KPI 정의서 확정

- 이 문서를 기준으로 계산 기준을 고정한다.
- D0 사후성과와 실현손익을 분리한다.
- 표본 부족 시 매매 룰 변경 금지 원칙을 명시한다.

### 2단계: analytics schema/view 추가

우선순위:

```text
analytics.live_trade_fact
analytics.live_daily_account_nav
analytics.live_review_kpi
analytics.live_score_bucket_kpi
```

`live_trade_fact`에는 최소한 아래 정보가 있어야 한다.

- request_id
- intent_id
- code, name
- side
- intent_type
- filled_at
- filled_qty
- filled_price
- filled_amount
- ranking_rank
- final_score
- confidence_score
- risk_penalty
- dominant_theme
- score_driver_1~3
- risk_factor_1~2

### 3단계: Closed Trade 계산

- 1차는 평균단가 방식으로 구현한다.
- 부분청산과 TRIM을 처리한다.
- 산출 결과는 view보다 테이블/스냅샷 방식이 적합할 수 있다.
- 매일 장 종료 후 재계산 또는 증분 계산한다.

권장 산출물:

```text
analytics.live_closed_trade
outputs/live_closed_trade_report.md
outputs/live_closed_trade_report.json
```

### 4단계: Daily KPI 리포트 생성

`python/build_live_kpi_daily_report.py` 형태의 스크립트로 시작한다.

리포트는 운영 화면과 별도 KPI 시스템이 함께 읽을 수 있도록 JSON을 먼저 안정화한다.

### 5단계: 자동매매 화면 확장

이미 `live-auto-trading.html`에 Live Trade Review가 있으므로 새 화면부터 만들 필요는 없다.

추가할 섹션:

- 운영 KPI 요약
- 실현손익 요약
- 점수구간별 성과
- confidence 구간별 성과
- 표본 신뢰도 상태

### 6단계: 별도 KPI 앱 분리

데이터와 KPI 정의가 안정되면 별도 시스템으로 분리한다.

권장 구조:

```text
운영 DB
  ↓ read-only
lee_trader_kpi
  - analytics view 조회
  - Streamlit 또는 경량 Node 대시보드
  - Telegram/Slack 알림
```

처음부터 별도 DB를 만들지 않는다. 1차는 운영 DB read-only 조회가 맞다.

## 8. 운영 룰 후보

아래 룰은 데이터가 충분히 쌓인 뒤 검토한다. 지금 즉시 적용하지 않는다.

| 후보 룰 | 적용 조건 |
| --- | --- |
| final_score 80 미만 신규매수 제한 | score bucket별 D+5 기대값이 충분한 표본에서 음수 |
| rank_9_20 신규매수 제외 | rank_9_20 D+5 기대값이 50건 이상에서 음수 |
| TRIM 룰 완화 | TRIM 후 D+3/D+5가 반복적으로 양수 |
| PILOT 진입비중 축소 | PILOT BUY의 D+5 기대값이 충분한 표본에서 음수 |
| 특정 theme 제외 | theme별 손실률이 충분한 표본에서 반복적으로 높음 |
| risk_penalty high 차단 강화 | high bucket에서 손실률/MDD가 명확히 높음 |

## 10. 결론

현재는 매매 로직을 추가하기보다 분석 인프라를 준비할 단계다.

핵심은 다음 순서다.

```text
판단 → 주문 → 제출 → 체결 → 계좌 → 사후성과 → 실현손익 → KPI → 운영 룰
```

이미 앞쪽 체인은 상당 부분 구현되어 있으므로, 다음 개발의 중심은 `체결 데이터를 신뢰 가능한 성과 데이터로 변환하는 분석 계층`이다.
