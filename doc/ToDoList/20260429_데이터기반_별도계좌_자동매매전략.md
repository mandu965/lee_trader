# 2026-04-29 데이터 기반 별도계좌 자동매매 전략 초안

## 0. v1.1 실전 안전성 보완 기준

이 섹션은 `RULE_TREND_LIQUIDITY_V1`의 구현 전 추가 안전 기준이다. 기존 기준보다 우선 적용한다.

### 0.1 갭 리스크 조건

`expected_gap`은 신호일 D 이전 20영업일 데이터만 사용한다.

```text
expected_gap = rolling_20d_median(open / previous_close - 1)
expected_entry_price = close * (1 + expected_gap)
```

신규 진입 제외:

```text
abs(expected_gap) > 0.03
```

실제 주문 직전 보류:

```text
D+1 actual_open_gap > 0.05  -> 주문 보류
D+1 actual_open_gap < -0.04 -> 주문 보류
```

주의:

- `expected_gap`은 신호 생성과 후보 필터에 사용할 수 있다.
- `D+1 actual_open_gap`은 신호 생성에 사용하지 않는다.
- `D+1 actual_open_gap`은 백테스트 체결 검증 또는 실주문 전 최종 검증에만 사용한다.
- 백테스트에서는 D 시점 신호 확정 후 D+1 open 기준으로 체결 가능 여부와 성과를 계산한다.

저장 컬럼:

```text
expected_gap
expected_entry_price
actual_open_gap
gap_risk_blocked
gap_risk_reason
```

`gap_risk_reason` 예시:

```text
expected_gap_abs_gt_3pct
actual_open_gap_gt_5pct
actual_open_gap_lt_minus_4pct
none
```

### 0.2 run_mode별 거래대금 기준

최소 거래대금 기준은 `run_mode`에 따라 다르게 적용한다.

```text
paper: trading_value_ma_20 >= 500,000,000
pilot: trading_value_ma_20 >= 1,000,000,000
live:  trading_value_ma_20 >= 2,000,000,000
```

환경변수 또는 config:

```text
RULE_MIN_TRADING_VALUE_MA20_PAPER=500000000
RULE_MIN_TRADING_VALUE_MA20_PILOT=1000000000
RULE_MIN_TRADING_VALUE_MA20_LIVE=2000000000
RULE_ENTRY_RULE_SCORE_MIN=70
RULE_ENTRY_RULE_SCORE_V2_MIN=65
RULE_STRONG_RULE_SCORE_MIN=70
RULE_STRONG_RULE_SCORE_V2_MIN=50
```

저장 컬럼:

```text
min_trading_value_required
trading_value_pass
trading_value_block_reason
```

`trading_value_block_reason` 예시:

```text
trading_value_ma20_below_paper_threshold
trading_value_ma20_below_pilot_threshold
trading_value_ma20_below_live_threshold
none
```

운영 원칙:

- paper는 후보 탐색 폭을 넓히기 위해 5억 기준을 사용한다.
- pilot은 체결 현실성을 우선해 10억 기준을 사용한다.
- live는 슬리피지와 주문 실패 가능성을 낮추기 위해 20억 기준을 사용한다.

### 0.3 진입 신호 이원화

후보 신호:

```text
entry_signal = rule_score >= 70 OR rule_score_v2 >= 65
```

강한 진입 신호:

```text
strong_entry_signal = rule_score >= 70 AND rule_score_v2 >= 50
```

저장 컬럼:

```text
entry_signal
strong_entry_signal
signal_strength
```

`signal_strength` 값:

```text
none
entry
strong_entry
```

운영 원칙:

- paper 백테스트는 `entry_signal`, `strong_entry_signal` 기준 성과를 모두 리포트한다.
- pilot/live 주문 생성은 `strong_entry_signal`만 사용한다.
- order preview에는 `signal_strength`를 반드시 남긴다.

### 0.4 방어 모드 처리 우선순위

`market_defensive_mode = true`이면 신규 BUY는 생성하지 않는다.

기존 보유 종목은 아래 순서로 판단한다.

```text
1. stop_loss
2. ma60_break
3. rule_score_v2_drop
4. trailing_stop
5. time_stop
```

저장 컬럼:

```text
defensive_action_priority
defensive_action_reason
defensive_action_type
```

`defensive_action_type` 값:

```text
hold
reduce
exit
```

규칙:

- `stop_loss`, `ma60_break`는 `exit` 후보로 기록한다.
- `rule_score_v2_drop`, `trailing_stop`은 `reduce` 또는 `exit` 후보로 기록한다.
- `time_stop`은 우선 `reduce` 후보로 기록한다.
- pilot/live에서는 order limit과 kill switch 검증 후에만 주문 생성한다.

### 0.5 계좌 resolver와 주문 허용 검증

RULE 계좌 실주문 전 계좌 혼선을 막기 위해 별도 resolver와 검증 함수를 둔다.

필요 함수:

```text
resolve_trading_account(engine_type, run_mode)
validate_account_profile(account_profile)
assert_order_allowed(order_context)
```

`resolve_trading_account(engine_type, run_mode)` 역할:

- `engine_type=rule_based`이면 RULE 계좌 프로필을 읽는다.
- `run_mode=paper`이면 KIS 계좌 환경변수가 없어도 paper 프로필을 반환한다.
- `run_mode=pilot/live`이면 `KIS_RULE_CANO`, `KIS_RULE_ACNT_PRDT_CD` 누락 시 즉시 중단한다.

`validate_account_profile(account_profile)` 검증:

```text
account_id == RULE_ACCOUNT_01
engine_type == rule_based
run_mode in paper/pilot/live
paper 모드는 주문 API 호출 불가
pilot/live 모드는 KIS_RULE_CANO 존재
pilot/live 모드는 KIS_RULE_ACNT_PRDT_CD 존재
```

`assert_order_allowed(order_context)` 검증:

```text
account_id == RULE_ACCOUNT_01
strategy_id == RULE_TREND_LIQUIDITY_V1
engine_type == rule_based
run_mode in ["pilot", "live"]
RULE_LIVE_ENABLED == 1
RULE_ORDER_SUBMIT_ENABLED == 1
kill_switch == off
order_amount <= configured limit
signal_strength == strong_entry for BUY
market_defensive_mode == false for BUY
gap_risk_blocked == false
trading_value_pass == true
```

paper 모드:

- KIS 주문 API를 호출하지 않는다.
- 주문 파일과 preview만 생성한다.
- 계좌 환경변수가 누락되어도 paper 산출물 생성은 가능하다.

pilot/live 모드:

- 계좌 환경변수 누락 시 즉시 중단한다.
- 주문 제출 전 `account_id`, `strategy_id`, `engine_type`, `run_mode`를 로그와 산출물에 남긴다.
- `order_allowed=false`인 경우 반드시 `order_block_reason`을 남긴다.

### 0.7 회귀 테스트와 안전 점검

구현 후 반드시 확인할 항목:

```text
기존 AI 자동매매 산출물 파일을 덮어쓰지 않는가
paper 모드에서 KIS 주문 API가 호출되지 않는가
pilot/live 모드에서 계좌 환경변수 누락 시 중단되는가
expected_gap 계산에 D+1 데이터가 섞이지 않는가
D+1 open_gap은 신호 생성에 사용되지 않는가
strong_entry_signal만 pilot/live 주문 대상이 되는가
market_defensive_mode에서 신규 BUY가 생성되지 않는가
order_allowed=false 사유가 산출물에 명확히 남는가
```

초기 구현 완료 기준:

- RULE 산출물은 모두 `rule_` prefix 또는 별도 파일명을 가진다.
- 기존 AI 산출물과 DB 테이블의 의미를 변경하지 않는다.
- RULE 실주문은 별도 명시 설정 전까지 불가능해야 한다.

## 1. 목적

기존 AI 모델 기반 자동매매와 별도 계좌에서 병행 운영할 데이터 기반 자동매매 프로그램을 설계한다.

핵심 목표는 AI 모델의 예측 확률에 의존하지 않고, 가격/거래량/수급/시장상태 같은 관측 가능한 데이터만으로 매수, 보유, 축소, 청산 판단을 수행하는 것이다.

운영 형태:

```text
계좌 A: 기존 AI 모델 기반 자동매매
계좌 B: 신규 데이터 기반 룰 자동매매
```

두 계좌는 주문, 보유, 손익, 리스크 한도를 분리한다. 단, 시장 데이터와 종목 데이터 파이프라인은 가능한 한 공유한다.

## 4. 1차 전략: 유동성 필터형 추세 추종

가장 먼저 구현할 전략은 복잡한 예측 모델이 아니라, 데이터 품질이 높은 종목만 대상으로 하는 보수적 추세 추종 전략이다.

전략 ID:

```text
RULE_TREND_LIQUIDITY_V1
```

### 4.1 후보군

기본 후보군:

```text
data/features.csv 최신일 기준 전체 universe
```

초기 제외 조건:

```text
close is null
ma_20 is null
ma_60 is null
vol_ma_20 is null
volume <= 0
상장/상폐 메타데이터 이상
```

유동성 필터:

```text
liquidity_score >= 50
vol_ma_20 percentile 상위 60% 이내
value_ratio_20d >= 0.8
```

품질 필터:

```text
quality_missing_ratio <= 0.5
quality_score_confidence >= 50
```

시장 필터:

```text
regime != defensive 또는 시장 리스크 축소 모드에서 신규진입 수 제한
kospi_close >= kospi_ma20 이면 정상 진입
kospi_close < kospi_ma20 이면 신규진입 절반 이하
```

### 4.2 매수 신호

기본 매수 조건:

```text
close > ma_20
ma_20 >= ma_60
ret_5d > 0
mom_20 > 0
volume_ratio_20d >= 1.2
value_ratio_20d >= 1.1
rsi_14 between 45 and 75
vol_20 <= 같은 날짜 universe 상위 80 percentile
```

강한 매수 가산 조건:

```text
close > ma_5 > ma_20 > ma_60
volume_ratio_5d >= 1.5
ret_10d > 0
close_over_ma20 between 0.02 and 0.15
```

과열 제외 조건:

```text
rsi_14 > 80
close_over_ma20 > 0.20
ret_5d > 0.25
vol_20 상위 90 percentile 초과
```

### 4.3 점수화

룰 전략은 AI 확률 대신 `rule_score`를 만든다.

초기 공식:

```text
trend_score =
  30 * I(close > ma_20)
  + 20 * I(ma_20 >= ma_60)
  + 15 * percentile(mom_20)
  + 10 * percentile(ret_5d)
  + 10 * percentile(volume_ratio_20d)
  + 10 * percentile(value_ratio_20d)
  + 5  * rsi_band_score

risk_deduction =
  10 * I(rsi_14 > 75)
  + 10 * I(close_over_ma20 > 0.15)
  + 10 * I(vol_20 상위 80 percentile 초과)

rule_score = clip(trend_score - risk_deduction, 0, 100)
```

진입 기준:

```text
entry_signal = rule_score >= 70 OR rule_score_v2 >= 65
strong_entry_signal = rule_score >= 70 AND rule_score_v2 >= 50
```

우선순위:

```text
rule_score_v2 desc
rule_score desc
liquidity_score desc
vol_20 asc
```

### 4.4 매도/축소/보유 조건

보유 유지:

```text
close >= ma_20
rule_score >= 55
손절/익절 조건 미충족
```

비중 축소:

```text
close < ma_20
또는 rule_score < 55
또는 rsi_14 > 82
또는 close_over_ma20 > 0.25
```

전량 청산:

```text
close < ma_60
또는 매수가 대비 -7% 손실
또는 최근 고점 대비 -10% 하락
또는 시장 gate BLOCK
```

익절:

```text
매수가 대비 +12% 도달 시 50% 축소
이후 trailing stop 8% 적용
```

초기에는 청산 조건을 단순하게 유지하고, 실거래 데이터가 쌓인 뒤 보정한다.

## 9. 1차 결론

현재 탑재 데이터만으로도 1차 룰 기반 자동매매는 시작할 수 있다.

바로 가능한 전략은 `가격 추세 + 거래량/거래대금 확장 + 유동성 필터 + 시장 레짐 필터` 조합이다. 수급 데이터는 이미 수집기와 테이블 기반이 있으나 운영 기본 경로에서 비활성화되어 있으므로, 초기 실거래 판단에 바로 넣기보다는 안정화 후 2차 필터로 붙이는 것이 맞다.

가장 중요한 선행 작업은 전략 자체보다 계좌 분리다. 신규 기능의 실제 개발 단위는 아래처럼 보는 것이 적절하다.

```text
Rule Signal Engine
-> Rule Portfolio/Risk Manager
-> Rule Account Router
-> Rule Order Preview
-> Pilot Live Submit
```

기존 AI 자동매매와 같은 주문 제출기를 재사용하더라도 `account_id`, `strategy_id`, `engine_type`을 끝까지 잃지 않는 구조가 필요하다.

## 10. 확정 전략 기준 v1

이 섹션은 실제 구현 전 기준선이다. 구현 중 수익률 최적화보다 아래 항목을 우선한다.

우선순위:

```text
1. 체결 현실성
2. 계좌 분리
3. 리스크 제어
4. 백테스트 신뢰도
5. 수익률 개선
```

### 10.1 전략 이름

```text
strategy_id: RULE_TREND_LIQUIDITY_V1
engine_type: rule_based
default_run_mode: paper
```

전략 목적:

- AI 예측 확률을 사용하지 않는다.
- 가격 추세, 거래대금, 변동성, 시장 레짐만으로 판단한다.
- 실주문 전 paper 산출물과 백테스트를 먼저 쌓는다.
- 기존 AI 자동매매 산출물과 파일명을 분리한다.

### 10.2 데이터 기준

신호 생성일은 `D`로 정의한다.

```text
D close: 신호 생성 기준 가격
D+1 open: 백테스트 진입 기준 가격
```

look-ahead 방지 원칙:

- D 시점의 신호에는 D+1 open을 사용하지 않는다.
- D+1 open은 성과 계산에만 사용한다.
- expected gap은 D 이전 20영업일 데이터로만 계산한다.

추가 feature:

```text
open_gap = open / previous_close - 1
expected_gap = rolling_20d_median(open_gap)
expected_entry_price = close * (1 + expected_gap)
trading_value = close * volume
trading_value_ma_5
trading_value_ma_20
trading_value_ratio_5d
trading_value_ratio_20d
```

신규 진입 제외:

```text
abs(expected_gap) > 0.03
trading_value_ma_20 < run_mode threshold
```

운영 옵션:

```text
RULE_MIN_TRADING_VALUE_MA20_PAPER=500000000
RULE_MIN_TRADING_VALUE_MA20_PILOT=1000000000
RULE_MIN_TRADING_VALUE_MA20_LIVE=2000000000
```

### 10.3 진입 조건

```text
close > ma_20

mom_20 > 0
rsi_14 >= 45
rsi_14 <= 75
volume_ratio_20d >= 1.2
trading_value_ratio_20d >= 1.1
```

과열 제외:

```text

```

### 10.4 점수 체계

기존 additive 점수와 신규 multiplicative 점수를 둘 다 저장한다.

```text
rule_score
rule_score_v2
trend_component
liquidity_component
stability_component
regime_component
```

`rule_score`는 기존 단순 합산형이다.

`rule_score_v2`는 아래 가중합 구조를 사용한다.

```text
rule_score_v2 =
  (0.35 * trend_component)
  + (0.30 * liquidity_component)
  + (0.20 * stability_component)
  + (0.15 * regime_component)
```

정규화:

```text
각 component: 0.0 ~ 1.0
rule_score_v2: 0 ~ 100
```

초기 진입 기준:

```text
entry_signal = rule_score >= 70 OR rule_score_v2 >= 65
strong_entry_signal = rule_score >= 70 AND rule_score_v2 >= 60
```

백테스트 민감도:

```text
rule_score 기준: 65, 70, 75
trading_value_ma_20 기준: 500,000,000 / 1,000,000,000
stop_loss 기준: -5% / -7%
```

## 14. Order Generation Logic

### 14.1 주문 금액 계산

```text
target_amount = total_equity * new_entry_weight
position_remaining_limit = total_equity * max_position_weight - current_position_amount
available_buying_power = max(0, cash - total_equity * min_cash_weight)
final_order_amount = min(target_amount, available_buying_power, position_remaining_limit)
```

최소 주문 기준:

```text
min_order_amount = 100,000 또는 config 값
final_order_amount < min_order_amount 이면 주문 생성하지 않음
```

환경변수 또는 config:

```text
RULE_MIN_ORDER_AMOUNT=100000
```

### 14.2 주문 수량과 예상 체결가

```text
order_qty = floor(final_order_amount / expected_execution_price)
order_qty <= 0 이면 주문 생성하지 않음
```

예상 체결가:

```text
paper/backtest: expected_entry_price 또는 D+1 open
pilot/live 주문 직전: current_price 또는 actual_open_price
```

### 14.3 주문 타입

기본 주문 타입은 지정가다.

```text
buy_limit_price = actual_open_price * 1.01
sell_limit_price = actual_open_price * 0.99
```

시장가 주문 기본값:

```text
MARKET_ORDER_ENABLED=0
```

운영 원칙:

- 기본값은 시장가 금지다.
- pilot/live에서도 `MARKET_ORDER_ENABLED=0`이면 시장가 주문을 생성하지 않는다.
- 시장가 허용은 별도 명시 설정과 운영자 검토 후에만 가능하다.

## 16. Order Safety Rules

BUY 주문 금지 조건:

```text
run_mode == paper
order_allowed == false
signal_strength != strong_entry
market_defensive_mode == true
gap_risk_blocked == true
trading_value_pass == false
sector_limit_pass == false
cooldown_pass == false
cash_limit_pass == false
order_qty <= 0
final_order_amount < min_order_amount
```

추가 안전장치:

- paper 모드는 절대 KIS 주문 API를 호출하지 않는다.
- pilot/live에서도 `MARKET_ORDER_ENABLED=0`이면 시장가 주문 금지다.
- `order_allowed=false` 사유를 반드시 남긴다.
- BUY는 `strong_entry_signal`만 가능하다.
- defensive mode에서는 BUY 금지다.
- gap risk, 거래대금, sector, cooldown, cash 제한 중 하나라도 실패하면 BUY 금지다.

## 17. RULE 계좌 환경변수 설계

현재 코드의 KIS 계좌 조회/주문 경로는 기본적으로 아래 변수를 사용한다.

```text
KIS_CANO
KIS_ACNT_PRDT_CD
KIS_ACCOUNT_NO
```

따라서 RULE 계좌는 기존 값을 덮어쓰지 않고 별도 변수로 추가한다.

제안 변수:

```text
KIS_APP_RULE_ID=
KIS_APP_RULE_PASSWORD=
KIS_RULE_CANO=
KIS_RULE_ACNT_PRDT_CD=
```

주의:

- 현재 코드 기준 `KIS_APP_ID`, `KIS_APP_PASSWORD`는 브로커 계좌 해석/주문에 직접 사용되지 않는다.
- 실제 주문 계좌 식별에는 `CANO`, `ACNT_PRDT_CD`가 핵심이다.
- `KIS_APP_RULE_ID`, `KIS_APP_RULE_PASSWORD`는 운영자 식별 또는 향후 별도 인증 프로필용으로 둘 수 있다.
- RULE 실주문을 붙이기 전에는 `KIS_RULE_CANO`, `KIS_RULE_ACNT_PRDT_CD`를 명시적으로 읽는 계좌 resolver가 필요하다.

RULE 안전 기본값:

```text
RULE_TRADING_RUN_MODE=paper
RULE_LIVE_ENABLED=0
RULE_ORDER_SUBMIT_ENABLED=0
ACTIVE_TRADING_ENGINE=ai
```

실주문 제출 전 필수 확인:

```text
account_id == RULE_ACCOUNT_01
strategy_id == RULE_TREND_LIQUIDITY_V1
engine_type == rule_based
run_mode in pilot/live
RULE_LIVE_ENABLED == 1
RULE_ORDER_SUBMIT_ENABLED == 1
kill_switch == off
order_amount <= configured limit
```

초기 구현 원칙:

- paper 모드에서는 KIS 주문 API를 호출하지 않는다.
- pilot/live 모드는 명시적으로 설정하지 않으면 동작하지 않는다.
- 계좌 환경변수가 누락되면 실주문 단계는 실패로 중단한다.
- RULE 주문 제출기는 기존 AI 주문 제출기와 분리하거나, 최소한 별도 입력 파일만 받도록 제한한다.

## 18. Order Retry / Fallback Policy

이 섹션은 실제 주문 과정의 미체결, API 지연, 재주문 위험을 제어하기 위한 기준이다. 기본 원칙은 주문 체결률을 높이기보다 과도한 추격 매수를 막는 것이다.

### 18.1 기본 주문 흐름

```text
09:01  1차 시가/현재가 확인
09:03  order_allowed 재검증
09:05  1차 주문 제출
09:08  체결 여부 확인
09:10  미체결 주문 취소 또는 재주문 판단
09:12  fallback 주문 제출 여부 결정
09:15  최종 체결 상태 저장
```

필요 함수:

```text
check_order_fill_status(order_id, account_profile)
cancel_unfilled_order(order_id, account_profile)
build_fallback_order(original_order, market_snapshot, config)
retry_rule_order(order, account_profile, config)
```

운영 원칙:

- retry는 최대 1회만 허용한다.
- `retry_count`를 저장한다.
- retry 발생 사유를 저장한다.
- paper 모드에서는 실제 주문/취소/체결조회 API를 호출하지 않고 simulated status만 기록한다.
- pilot/live 모드에서도 `order_allowed=true`인 주문만 retry 가능하다.
- fallback 주문도 `assert_order_allowed`를 다시 통과해야 한다.

설정 기본값:

```text
RULE_RETRY_ENABLED=1
RULE_MAX_RETRY_COUNT=1
MARKET_ORDER_ENABLED=0
RULE_BUY_FALLBACK_LIMIT_BUFFER=0.015
RULE_SELL_FALLBACK_LIMIT_BUFFER=0.015
RULE_MAX_FALLBACK_PRICE_DRIFT=0.02
```

### 18.2 Fallback 주문 전략

기본 주문 타입은 지정가다.

```text
buy_limit_price = actual_open_price * 1.01
sell_limit_price = actual_open_price * 0.99
MARKET_ORDER_ENABLED=0
```

BUY fallback 기준:

```text
1차 주문 미체결
RULE_RETRY_ENABLED=1
retry_count < RULE_MAX_RETRY_COUNT
order_allowed=true
```

fallback 방식:

```text
MARKET_ORDER_ENABLED=1 -> market fallback 허용
MARKET_ORDER_ENABLED=0 -> wider limit fallback 사용
```

wider limit 예:

```text
buy_fallback_limit_price = current_price * (1 + RULE_BUY_FALLBACK_LIMIT_BUFFER)
sell_fallback_limit_price = current_price * (1 - RULE_SELL_FALLBACK_LIMIT_BUFFER)
```

추가 안전 조건:

- fallback 시에도 `gap_risk_blocked=false`여야 한다.
- BUY fallback은 `market_defensive_mode=false`여야 한다.
- BUY fallback은 현재가가 최초 `expected_execution_price` 대비 2% 이상 상승했으면 금지한다.
- `fallback_order_amount`는 원 주문 금액을 초과할 수 없다.
- `fallback_order_qty`는 원 주문 수량을 초과할 수 없다.
- fallback 주문도 `assert_order_allowed`를 다시 통과해야 한다.

필수 필드:

```text

fallback_type
fallback_reason
retry_count
original_limit_price
fallback_limit_price
fallback_order_allowed
fallback_block_reason
```

`fallback_type` 값:

```text

wider_limit
market
```

fallback 차단 사유 예:

```text

max_retry_count_reached
order_not_allowed
market_order_disabled
buy_price_drift_gt_2pct
gap_risk_blocked
market_defensive_mode

fallback_qty_exceeds_original
```

- fallback 주문도 `order_allowed=true` 조건을 다시 만족해야 한다.
- paper 모드는 주문/취소/체결조회 API를 호출하지 않는다.
- pilot/live 모드는 계좌 resolver 실패 시 즉시 중단한다.
- fallback 결과도 `order_block_reason` 또는 `fallback_block_reason`에 남긴다.
- reconciliation report가 생성되지 않으면 해당 run은 실패로 처리한다.
- 체결 결과 저장 전 다음 주문 단계로 넘어가지 않는다.

## 22. API Failure and Order Run Abort Policy

장 시작 주문 구간에서 KIS API 또는 현재가 조회가 실패하면 무리하게 주문하지 않는다.

### 22.1 API/시세 검증 함수

필요 함수:

```text
check_market_data_available(symbols, account_profile, config)
fetch_open_snapshot_with_retry(symbols, max_retry, retry_interval)
abort_order_run(reason)
```

설정:

```text
RULE_OPEN_SNAPSHOT_MAX_RETRY=3
RULE_OPEN_SNAPSHOT_RETRY_INTERVAL_SEC=10
```

### 22.2 실패 처리 기준

```text
현재가/시가 조회 실패 시 주문 생성 금지
actual_open_gap 계산 실패 시 BUY 금지
KIS API 인증 실패 시 즉시 중단
계좌 조회 실패 시 즉시 중단
주문 제출 API 실패 시 fallback 주문으로 넘어가지 않고 실패 기록
API 실패는 retry 주문과 구분해서 기록
```

필수 필드:

```text
market_data_available
api_health_status
api_failure_reason
order_run_aborted
order_run_abort_reason
```

`api_health_status` 값:

```text
ok
market_data_unavailable
auth_failed
account_query_failed
order_submit_failed
unknown_failed
```

중단 원칙:

- API 인증 실패와 계좌 조회 실패는 즉시 hard abort다.
- 현재가/시가 조회 실패는 BUY 금지로 처리한다.
- `actual_open_gap`을 계산할 수 없으면 BUY 금지다.
- 주문 제출 API 실패는 retry/fallback 미체결 흐름이 아니라 API failure로 기록한다.
- aborted run도 `outputs/rule_execution_results.json`에 남긴다.

## 23. Reconciliation Dependency Guard


```text
RULE_BLOCK_ON_MISSING_RECONCILIATION=1
RULE_PAPER_ALLOW_MISSING_RECONCILIATION=0
```

### 23.2 차단 기준

```text
전일 주문 실행 대상이 있었는데 reconciliation report가 없으면 신규 주문 금지
execution_results.json은 있는데 reconciliation_report.md가 없으면 신규 주문 금지
reconciliation_status != success이면 신규 주문 금지
```

paper 모드:

- 기본값은 missing reconciliation을 허용하지 않는다.
- `RULE_PAPER_ALLOW_MISSING_RECONCILIATION=1`일 때만 warning으로 기록하고 다음 paper run을 허용할 수 있다.
