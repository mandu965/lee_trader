# 자동매매시스템이란

## 0. 이 문서의 목적

이 문서는 "일반적인 프로그램 매매"와 "완전 자동화 매매 시스템"이 실제로 어떤 구조로 만들어지고 운영되는지 큰 그림을 설명하기 위한 문서입니다.

목적은 두 가지입니다.

1. 일반적인 자동매매 시스템이 무엇으로 구성되는지 이해하기
2. 현재 우리 시스템이 그 구조에서 어디쯤 와 있는지 비교할 기준 만들기

이 문서는 특정 증권사 API나 특정 전략 구현법보다, 자동매매 시스템의 전형적인 구조와 운영 흐름을 이해하는 데 초점을 둡니다.

---

## 1. 자동매매를 한 문장으로 정의하면

자동매매 시스템은 보통 아래 한 문장으로 정의할 수 있습니다.

> 시장 데이터를 받아서, 정해진 규칙이나 모델로 판단하고, 주문을 생성하고, 체결과 계좌 상태를 다시 반영하는 시스템

이 문장에서 핵심 단계는 4개입니다.

1. 입력
   - 시장 데이터 수집
2. 판단
   - 신호 생성, 전략 판단
3. 실행
   - 주문 생성, 제출, 체결 확인
4. 반영
   - 계좌 상태 업데이트, 리스크/포지션 재계산

이 4단계가 닫힌 루프를 이루면 자동매매 시스템이라고 부를 수 있습니다.

---

## 2. 사람들이 흔히 말하는 "프로그램 매매"는 무엇인가

일반적으로 프로그램 매매라고 할 때는 매우 넓은 의미를 가집니다.

- 사람이 정한 규칙을 프로그램으로 실행하는 것
- 정량 모델이 정한 진입/청산 신호를 기계적으로 처리하는 것
- 반복적인 매매판단을 사람이 아니라 코드가 대신하는 것

즉, 프로그램 매매는 꼭 고빈도 매매일 필요도 없고, AI 기반일 필요도 없습니다.

예를 들면 아래도 모두 프로그램 매매입니다.

- 오전 9시 5분에 조건식을 만족한 종목 상위 3개를 매수
- 이동평균 돌파 시 진입, 이탈 시 청산
- 포트폴리오 비중이 기준에서 벗어나면 자동 리밸런싱
- 신호 점수 상위 N개만 매수 후보로 선정

즉 프로그램 매매는 "판단과 실행의 일부 또는 전부를 코드가 담당하는 매매"라고 이해하면 됩니다.

---

## 3. 자동매매 시스템의 일반적인 단계

## 3-1. 데이터 수집 단계

자동매매의 출발점은 데이터입니다.

보통 다음이 필요합니다.

- 가격 데이터
  - 시가, 고가, 저가, 종가, 거래량
- 호가/체결 데이터
  - 실시간 매매용이면 중요
- 계좌 데이터
  - 보유 수량, 평균 단가, 현금, 주문 가능 금액
- 주문/체결 데이터
  - 기존 주문 상태, 미체결 여부
- 보조 데이터
  - 뉴스, 재무, 수급, 지표, 파생 변수

이 단계의 핵심은 "판단에 쓰는 데이터와 실행에 쓰는 데이터가 일관돼야 한다"는 점입니다.

예를 들어:

- 판단은 어제 종가 기준인데
- 주문은 오늘 장중 가격으로 넣고
- 계좌는 10분 전 상태를 보고 있다면

시스템은 자동화되어 있어도 매우 불안정해집니다.

그래서 좋은 자동매매 시스템은 데이터 소스보다 "기준 시점 정합성"을 더 중요하게 다룹니다.

---

## 3-2. 신호 생성 단계

데이터가 준비되면, 시스템은 이제 "무엇을 할지"를 판단합니다.

여기에는 여러 방식이 있습니다.

### 규칙 기반

- RSI 30 이하이면 매수
- 20일 신고가 돌파 시 진입
- 5일 평균 거래대금 미만이면 제외

장점:

- 설명이 쉽다
- 디버깅이 쉽다
- 예외 상황을 다루기 쉽다

단점:

- 시장 변화에 단순할 수 있다
- 조합이 많아질수록 복잡해진다

### 점수 기반

- 기술점수
- 확률점수
- 품질점수
- 리스크 페널티

를 합쳐 최종 점수를 만들고 상위 종목을 고르는 방식입니다.

장점:

- 다수 요소를 통합하기 좋다
- 후보군 비교가 쉽다

단점:

- 어떤 점수가 본선인지 흐려지기 쉽다
- 설명 체계를 따로 설계해야 한다

### 모델 기반

- 머신러닝 예측값
- 확률 모델
- 분류/회귀 모델

장점:

- 복잡한 패턴을 반영할 수 있다

단점:

- calibration, drift, leakage 문제를 항상 경계해야 한다
- 사람이 납득하기 어려운 시스템이 되기 쉽다

실제 시스템에서는 이 셋이 혼합되는 경우가 많습니다.

---

## 3-3. 포트폴리오/리스크 판단 단계

좋은 자동매매 시스템은 "무엇을 살까"만 판단하지 않습니다.

그보다 중요한 질문은 보통 아래입니다.

- 지금 사도 되는가
- 얼마나 사야 하는가
- 기존 보유와 충돌하는가
- 현금이 충분한가
- 위험이 과도하지 않은가

이 단계에서 보통 들어가는 것들은 다음과 같습니다.

- max position size
- 종목 수 제한
- 섹터 쏠림 제한
- 하루 신규 진입 건수 제한
- 손실 구간 진입 차단
- 시장 레짐 기반 gate
- 실거래/모의투자 모드 분기

이 부분이 약하면, 신호는 좋아도 실제 운영은 망가집니다.

그래서 실전에서는 "신호 엔진"보다 "리스크/집행 정책 엔진"이 더 중요해지는 경우가 많습니다.

---

## 3-4. 주문 생성 단계

자동매매 시스템은 판단이 끝나면 곧바로 주문하지 않습니다.

보통은 다음 중간 단계를 거칩니다.

1. intent 생성
   - 사고 싶다 / 팔고 싶다 / 비중을 줄이고 싶다
2. request preview 생성
   - 실제 주문 가능 수량 계산
   - 차단 사유 계산
3. execution request 생성
   - 최종 주문 파라미터 확정

이 단계가 중요한 이유는, "판단"과 "증권사 주문 제출" 사이에는 늘 현실 제약이 있기 때문입니다.

예를 들면:

- 주문 가능 금액 부족
- 최소 수량 미달
- 장 마감
- 미체결 주문 존재
- 계좌 정보 stale
- 승인 미완료

그래서 많은 시스템은 아래처럼 2단계로 나눕니다.

- 신호 단계: 무엇을 하고 싶은가
- 주문 단계: 실제로 무엇을 할 수 있는가

이 분리는 매우 중요합니다.

---

## 3-5. 주문 실행 단계

이제 시스템은 실제 브로커 API로 주문을 보냅니다.

이 단계에서 필요한 것은 다음과 같습니다.

- 주문 타입
  - 시장가 / 지정가 / 조건부
- 주문 수량
- 계좌 번호
- 종목 코드
- 매수/매도 구분
- 주문 가능 시간 확인
- 재시도 정책

보통 실전 시스템에서는 이 단계가 가장 민감합니다.

왜냐하면 여기서부터는 "결정"이 아니라 "돈"이 움직이기 때문입니다.

그래서 완전 자동화 시스템일수록 오히려 이 단계에 방어 장치가 많습니다.

예를 들면:

- 실거래 스위치
- BUY 허용 스위치
- 주문 승인 파일
- confirm text
- 특정 시간대 차단
- 특정 상황에서 강제 preview only

즉 완전 자동화는 "아무 제약 없이 다 자동"이 아니라, "제약을 코드로 강하게 건 자동"에 가깝습니다.

---

## 3-6. 체결/계좌 반영 단계

자동매매는 주문을 보냈다고 끝나지 않습니다.

그 다음이 더 중요합니다.

- 주문이 정상 제출됐는가
- 미체결인가, 부분 체결인가, 완전 체결인가
- 계좌 잔고가 실제로 바뀌었는가
- 평균 단가가 어떻게 바뀌었는가
- 현금/주문가능금액이 반영됐는가

이 반영 단계가 약하면 시스템은 자기 상태를 틀리게 이해하게 됩니다.

예를 들어:

- 시스템은 이미 매수했다고 생각하는데
- 실제로는 주문 실패였거나
- 부분 체결만 됐거나
- 미체결이었을 수 있습니다.

그래서 실전 시스템은 보통 아래를 반복합니다.

- 주문 제출
- 체결 확인
- 계좌 동기화
- 내부 상태 갱신

이 루프가 닫혀야 자동매매 시스템이 안정됩니다.

---

## 4. 완전 자동화 매매 시스템은 보통 어떻게 다른가

많은 사람이 "완전 자동화"를 아래처럼 상상합니다.

- 사람이 전혀 안 본다
- 시스템이 알아서 사고 판다
- 결과만 보면 된다

하지만 실제 완전 자동화 시스템은 오히려 반대입니다.

사람이 덜 개입하는 대신, 아래가 훨씬 더 강하게 설계됩니다.

- 데이터 정합성 검증
- 시간대 제어
- 주문 방어 규칙
- 포지션 한도
- 장애 시 fallback
- 로그와 알림
- kill switch

즉 완전 자동화의 본질은 "사람이 없어도 된다"가 아니라,

> 사람이 없어도 망가지지 않게 만드는 구조

입니다.

---

## 5. 일반적인 완전 자동화 시스템의 구조

보통은 아래와 같은 레이어로 나뉩니다.

### 1. Market Data Layer

- 시세 수집
- 데이터 정리
- 기준 시점 통일

### 2. Signal Layer

- 전략 신호 생성
- 종목/포지션 후보 선정

### 3. Risk Layer

- 종목당 한도
- 전체 익스포저 한도
- 시장 상태 기반 진입 차단

### 4. Execution Layer

- 주문 파라미터 계산
- 브로커 API 주문
- 재시도/실패 처리

### 5. State Sync Layer

- 체결/잔고 반영
- 주문 상태 갱신
- 내부 포지션 정합성 유지

### 6. Monitoring Layer

- 로그
- 경고
- 운영 대시보드
- 알림

좋은 시스템일수록 이 레이어들이 섞이지 않고 역할이 분리되어 있습니다.

---

## 6. 실제 운영은 어떻게 진행되나

완전 자동화 시스템이라고 해도, 운영 흐름은 의외로 반복적입니다.

보통 하루는 이렇게 흘러갑니다.

### 장 시작 전

- 데이터 최신성 확인
- 계좌 동기화
- 전략 기준일 확인
- 오늘 실행 가능 여부 판단

### 장중

- 실시간 또는 정시 데이터 수집
- 조건 충족 여부 확인
- 주문 가능 여부 재평가
- 주문 제출
- 체결 확인

### 장 마감 후

- 최종 상태 정리
- 로그/리포트 생성
- 다음 거래일 기준 산출물 생성
- 예외/실패 검토

즉 완전 자동화도 실제로는 "운영 없는 시스템"이 아니라, "운영 부담이 다른 형태로 옮겨간 시스템"입니다.

사람은 클릭을 덜 하지만, 설계와 감시는 더 중요해집니다.

---

## 7. 왜 많은 시스템이 "완전 자동화"까지 잘 못 가는가

이유는 크게 5가지입니다.

### 1. 데이터 기준이 자주 흔들린다

- 기준일 불일치
- stale 데이터
- 실시간/배치 데이터 혼용

### 2. 신호와 집행 사이에 현실 차이가 크다

- 사고 싶다고 실제로 다 살 수는 없다
- 유동성, 수량, 호가, 시간 제약이 있다

### 3. 계좌 상태 동기화가 생각보다 어렵다

- 주문 실패
- 부분 체결
- 브로커 응답 지연
- 내부 상태와 실제 계좌 상태 불일치

### 4. 전략보다 예외 처리가 더 어렵다

- API 오류
- 장 휴장
- 인증 만료
- 네트워크 오류
- 비정상 시세

### 5. 사람의 해석이 아직 필요한 구간이 남아 있다

- 장중 기준은 참고용인가 본선인가
- 예외 상황에서 계속 집행할 것인가
- 특정 이벤트성 장세를 어떻게 볼 것인가

결국 완전 자동화는 전략이 좋아서 되는 것이 아니라, 예외와 운영을 잘 설계해서 되는 경우가 많습니다.

---

## 8. 좋은 자동매매 시스템의 특징

제가 보기엔 좋은 자동매매 시스템은 아래 특징을 가집니다.

### 1. 기준일이 명확하다

- 어떤 데이터 기준으로 판단했는지 항상 알 수 있다

### 2. 신호와 실행이 분리되어 있다

- 사고 싶은 것과 실제로 사는 것을 혼동하지 않는다

### 3. 실패를 숨기지 않는다

- 마지막 실패, 최근 회복, 현재 정상 여부가 구분된다

### 4. 로그가 남는다

- 왜 이런 주문이 나갔는지 나중에 설명 가능하다

### 5. 사람 개입 지점이 설계돼 있다

- 정말 완전 자동화가 아니라도, 어디서 사람이 볼지 명확하다

### 6. 실험과 본선이 분리된다

- shadow, 연구 로직, 실험 점수는 본선과 구분된다

---

## 9. 그럼 현재 우리 시스템은 어디쯤인가

현재 우리 시스템은 대략 아래 중간 지점으로 보는 게 맞습니다.

- 단순 추천 시스템은 이미 넘어섰다
- 주문 preview/execution 경로도 갖고 있다
- 스케줄러와 계좌 동기화도 붙어 있다
- 운영자 화면도 있다

하지만 동시에 아래 특성도 남아 있습니다.

- 운영자 판단이 여전히 중요하다
- 장중 기준과 마감 기준의 역할 분리가 중요하다
- 승인/차단/허용 스위치가 본질적이다
- 운영 메모와 확인 단계가 실제 의미를 가진다

그래서 현재 상태를 가장 정확히 표현하면:

> 완전 무인 시스템이라기보다, 통제 가능한 자동집행 시스템

이라고 보는 게 맞습니다.

즉:

- 자동화는 이미 상당히 들어와 있지만
- 운영 판단과 통제 계층도 아직 본질적이다

이게 현재 위치에 가깝습니다.

---

## 10. 앞으로 완전 자동화 쪽으로 가려면 무엇이 더 필요할까

완전 자동화에 가까워지려면, 단순히 "주문 버튼을 자동화"하는 것보다 아래가 먼저 강해져야 합니다.

### 1. 기준 데이터 신뢰성

- 기준일 강제
- stale 차단
- 장중/마감 기준 구분

### 2. 정책 엔진 고도화

- gate
- 리스크 한도
- 포지션 제한
- 승인 조건

### 3. 상태 동기화 안정화

- 계좌/주문/체결 상태 자동 반영
- 내부 상태와 실제 상태 차이 탐지

### 4. 장애 대응 자동화

- API 실패
- 시세 결손
- 인증 문제
- 브로커 오류

### 5. 운영 결론의 구조화

- 오늘 결론
- 걸리는 사유
- 실행 가능 여부
- 보류 사유

이것이 사람이 보지 않아도 해석 가능한 형태로 나와야 합니다.

---

## 11. 자동매매 시스템을 볼 때 중요한 오해 하나

많은 경우 사람들은 자동매매를 아래처럼 생각합니다.

- 사람이 안 보면 더 발전된 시스템

하지만 실제로는 꼭 그렇지 않습니다.

더 성숙한 시스템은 아래에 가깝습니다.

- 사람이 안 봐도 되게 만들기 위해, 사람이 봐야 할 지점을 더 명확히 설계한 시스템

즉 사람 개입이 있다는 이유만으로 덜 발전된 시스템은 아닙니다.

오히려 위험한 것은:

- 사람도 잘 안 보고
- 시스템도 예외를 잘 못 다루고
- 실패 로그도 모호한 상태

입니다.

그래서 "완전 자동화"를 목표로 하더라도, 그 전 단계에서 "설명 가능하고 통제 가능한 자동화"를 확실히 거쳐야 합니다.

---

## 12. 이 문서를 읽고 같이 이야기해볼 질문

1. 우리는 궁극적으로 완전 자동화를 목표로 하는가
2. 그렇다면 사람 승인 단계는 어디까지 남길 것인가
3. 장중 기준은 앞으로도 운영 보조판단으로 둘 것인가
4. 운영자 페이지는 최종적으로 어떤 의사결정 콘솔이 되어야 하는가
5. 현재 시스템의 가장 큰 리스크는 전략인가, 데이터인가, 집행인가

---

## 13. 제 개인적 정리

제 생각에는 자동매매 시스템의 발전은 보통 아래 순서가 맞습니다.

1. 신호를 만든다
2. 신호를 운영 결론으로 정리한다
3. 운영 결론을 preview로 연결한다
4. preview를 제한적으로 execution으로 연결한다
5. 상태 동기화와 장애 대응을 안정화한다
6. 그 뒤에야 완전 자동화에 가까워진다

즉 완전 자동화는 출발점이 아니라, 마지막 단계입니다.

우리 시스템도 지금은 그 중간 어딘가에 있고, 이미 꽤 많이 와 있지만, 아직 "무인 완전 자동화"라고 부르기보다 "운영 통제를 가진 자동집행 시스템"이라고 보는 게 더 정확하다고 생각합니다.
