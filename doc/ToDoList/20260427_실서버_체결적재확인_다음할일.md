  - KIS `inquire-daily-ccld`를 주문번호별로 조회하면 `KIER2570 조회일자를 확인하십시오`가 발생했다.
  - KIS 만료 토큰이 HTTP 500 + `EGW00123`으로 내려와 기존 401/403 갱신 로직이 처리하지 못했다.
  - `--query-all` 검증 실행이 기존 fill row의 `request_id`를 NULL로 덮어쓸 수 있었다.
  - 정합성 리포트가 fill의 실제 체결일만 기준으로 세어, 요청 기준일 2026-04-24와 체결일 2026-04-27이 다른 정상 케이스를 `filled_count=0`으로 표시했다.
- 바로 수정한 항목:
  - 체결 동기화 기본 경로를 기간 전체 1회 조회 후 로컬 주문번호 필터링 방식으로 변경.
  - `ON CONFLICT` 업데이트 시 기존 `request_id`, `broker_org_order_id`를 NULL로 덮지 않도록 보호.
  - KIS `EGW00123` 만료 토큰 응답을 감지해 토큰 재발급 후 재시도하도록 보강.
  - 정합성 리포트의 `filled_count`를 기준일 execution과 broker order 매칭된 fill row 수로 계산하도록 수정.
- 다음 작업:
  - auto-buy 스케줄러 상태 파일에는 09:31 실패 이력이 남아 있으나, 동일 체결 적재 명령은 새 이미지에서 정상 통과했다. 다음 장중 자동 실행 후 상태가 정상 갱신되는지 확인한다.

핵심 변경:

- 체결 조회 시 `broker_org_order_id`를 `ORD_GNO_BRNO`로 전달
- 주문번호별 체결 조회가 비어 있으면 날짜 범위 전체 조회로 fallback
- `outputs/live_trade_consistency_report.json/md` 생성
- `GET /api/live-trade-consistency` 추가
- `live-auto-trading.html`에 `자동매매 정합성` 영역 추가

## 2. 체결 적재 복구 실행

실제 서버에서 아래 명령을 실행한다.

```powershell
python python/sync_live_order_fills.py --query-all --start-date 20260427 --end-date 20260428
```

실행 후 확인 SQL:

```sql
SELECT COUNT(*) AS fill_count
FROM research.live_order_fill;

SELECT request_id, broker_order_id, code, side, filled_qty, filled_price, filled_at, fill_status
FROM research.live_order_fill
ORDER BY filled_at DESC, fill_id DESC;
```

기대:

```text
fill_count >= 8
```

문제 지속:

```text
fill_count = 0
```

## 3. 정합성 리포트 생성

체결 적재 복구 후 아래 명령을 실행한다.

```powershell

```


확인 기준:

```text

filled_count >= 8
submitted_without_fill 비어 있음
```

```text

filled_count = 0
submitted_without_fill 8건 유지
```
