좋습니다.
아래는 **코덱스에게 그대로 붙여 넣어서 확인시키는 점검 프롬프트**입니다.

핵심 목표는:

* auto-buy 스케줄러가 실제 돌았는지
* preview까지만 갔는지
* execution까지 갔는지
* 환경변수 때문에 막혔는지
* BUY 승인/실계좌 동기화/KIS 응답 중 어디서 막혔는지

를 **증거 기반으로 판정**하게 하는 것입니다.

---

## 코덱스 점검 프롬프트

```text
현재 프로젝트는 자동매매 시스템입니다.
문제는 "Trade Intents / Order Requests Preview 화면에서는 제출 가능 상태였는데 실제 주문은 체결되지 않았다"는 점입니다.

당신의 역할은 이 프로젝트와 현재 서버 상태를 점검해서,
자동매매가 어디까지 수행되었고 어디서 멈췄는지 증거 기반으로 판정하는 것입니다.

중요:
- 절대 임의로 주문 실행하지 마세요.
- 절대 실거래 주문 명령(--execute, --allow-buy)으로 실행하지 마세요.
- 읽기/점검 위주로만 진행하세요.
- 파일 수정은 하지 말고, 필요한 경우 수정 제안만 하세요.
- 결과는 반드시 "무엇이 확인되었는지 / 무엇이 확인되지 않았는지 / 가장 유력한 원인 / 다음 조치" 형식으로 정리하세요.

아래 순서대로 점검하세요.

[1] docker compose 서비스 상태 점검
- docker compose ps 실행
- scheduler-auto-buy 서비스 존재 여부 확인
- Up / Restarting / Exited 상태 판정
- 일반 scheduler와 auto-buy scheduler가 어떻게 다른지 같이 설명

[2] auto-buy 관련 로그 점검
- docker compose logs scheduler-auto-buy --tail=300 실행
- logs/auto_ops_auto_buy_scheduler.log 파일 존재 여부 확인
- 다음 문자열이 있는지 찾기:
  - run_live_auto_trade_cycle.py
  - submit_live_orders.py
  - --execute
  - LIVE_ORDER
  - allow-buy
  - error
  - traceback
  - exception
- 실제 주문 제출 직전까지 갔는지 로그 기반으로 해석

[3] 주문 산출물 파일 점검
다음 파일 존재 여부와 최근 수정 시각을 확인:
- outputs/order_requests_preview.json
- outputs/order_requests_preview.md
- outputs/order_requests_execution.json
- outputs/order_requests_execution.md
- outputs/trade_intents.json
- outputs/order_buy_approvals.json

그리고 아래를 판정:
- preview만 있고 execution이 없으면 "실주문 제출 전 단계에서 멈춤"으로 분류
- execution 파일이 있으면 실제 제출 시도 여부를 안의 내용까지 읽어서 판정

[4] 실계좌 동기화 산출물 점검
다음 파일 존재 여부와 최신성을 확인:
- data/live_account_holdings.csv
- outputs/live_account_balance_summary.json

그리고 아래를 확인:
- holdings 파일에 종목코드, 수량, 평가금액 등이 실제 들어있는지
- balance summary에 최신 조회 흔적이 있는지
- SELL/TRIM이 가능한 환경이었는지 판정

[5] auto trade 환경변수 점검
컨테이너 내부 또는 실제 적용 환경 기준으로 아래 값을 확인:
- AUTO_TRADE_EXECUTE
- AUTO_TRADE_ALLOW_BUY
- AUTO_TRADE_CONFIRM_TEXT
- AUTO_TRADE_BUY_APPROVAL_REQUIRED
- KIS_BASE_URL
- KIS_CANO
- KIS_ACNT_PRDT_CD

반드시 아래 관점으로 해석:
- AUTO_TRADE_EXECUTE=0 이면 preview-only 가능성 큼
- AUTO_TRADE_ALLOW_BUY=0 이면 BUY 차단
- AUTO_TRADE_CONFIRM_TEXT 미설정이면 실주문 실행 불가 가능성
- AUTO_TRADE_BUY_APPROVAL_REQUIRED=1 이면 approval 파일 필요
- KIS_BASE_URL이 모의투자 URL인지 실거래 URL인지 판정

[6] trade_intents / preview 내부 내용 점검
다음 파일을 읽어서 핵심 항목을 표처럼 요약:
- outputs/trade_intents.json
- outputs/order_requests_preview.json

확인 항목:
- BUY / EXIT / TRIM / HOLD 건수
- executable 여부
- gate_status
- blocked_reason
- request_qty
- allowed_qty
- final_request_qty
- 차단 없이 제출 가능 상태인지

중요:
이전에 사용자 화면에서는 BUY 3건, EXIT 3건, 제출 가능 상태가 보였다고 합니다.
따라서 현재 파일 상태가 그 화면과 같은 시점인지, 다른 시점인지도 추론하세요.

[7] execution 파일이 있으면 실제 제출 결과 판독
outputs/order_requests_execution.json 이 있으면 내부 내용을 읽고 아래를 판정:
- submitted true/false
- skipped 여부
- broker_response 존재 여부
- success / failure 메시지
- buy_approval_required
- execute_disabled
- buy_not_allowed
- confirm_text_mismatch
- market_closed
- broker_error

즉, "실행 시도는 했으나 실패"인지
"실행 시도 자체를 안 함"인지 구분하세요.

[8] 코드 연결 구조 확인
아래 파일을 열어서 실제 흐름을 짧게 확인:
- python/run_live_auto_trade_cycle.py
- python/submit_live_orders.py
- python/build_trade_intents.py
- docker-compose.yml

반드시 확인할 것:
- auto-buy 스케줄러가 어떤 명령으로 submit_live_orders.py를 호출하는지
- execute / allow-buy / confirm-text가 어떤 조건에서 붙는지
- BUY approval이 어떻게 적용되는지
- 종가 배치 산출물과 auto-buy 실행이 어떻게 연결되는지

[9] 최종 결론 작성 형식
결과는 반드시 아래 형식으로 작성:

1. 확인된 사실
- 증거와 함께 bullet 정리

2. 확인되지 않은 사실
- 로그/파일 부재로 판단 불가한 항목 정리

3. 가장 유력한 원인 Top 3
- 1순위:
- 2순위:
- 3순위:

4. 현재 시스템 상태 판정
아래 중 하나로 분류:
- A. 자동매매 미구동
- B. preview까지만 생성
- C. execution까지 시도했으나 실패
- D. 일부 주문만 성공
- E. 실거래가 아니라 모의/테스트 환경

5. 바로 해야 할 다음 조치
- 위험도 낮은 점검부터 순서대로 제시

[10] 출력 원칙
- 추측과 사실을 구분하세요.
- "파일이 없으므로 확인 불가", "로그상 확인됨" 같은 표현으로 근거를 명확히 적으세요.
- 불필요한 일반론 말고, 현재 프로젝트 기준으로만 분석하세요.
- 명령어 실행 결과와 해석을 같이 적으세요.
```

## 더 강하게 쓰는 버전

코덱스가 너무 두루뭉술하게 답하면 아래 강화 문구를 맨 아래 추가하세요.

```text
추상적으로 설명하지 말고, 실제 실행한 명령어 / 확인한 파일 경로 / 확인된 값 / 누락된 값 / 그 의미를 바로 연결해서 작성하세요.
"아마", "가능성", "추정"이라고 쓸 때는 반드시 근거 파일 또는 로그를 같이 적으세요.
최종적으로는 "실주문이 안 된 직접 원인"을 한 문장으로 요약하세요.
```

## 제가 추천하는 사용 방식

코덱스에게 한 번에 다 시키는 것도 되지만, 더 정확하게 하려면 2단계로 나누는 게 좋습니다.

### 1차

위 프롬프트로 전체 진단

### 2차

코덱스 결과를 가져와서 다시 이렇게 요청

```text
좋습니다.
이제 방금 확인한 결과를 기준으로,
"실제 주문이 안 된 직접 원인"과
"안전하게 재현/검증하는 절차"를
운영자 체크리스트 형태로 다시 정리하세요.

조건:
- 실주문은 절대 실행하지 말 것
- preview와 execution의 차이를 명확히 설명할 것
- 환경변수 수정이 필요한 경우 어떤 값이 왜 필요한지 적을 것
- 마지막에는 '실거래 전 최종 점검 5항목'을 별도로 정리할 것
```
