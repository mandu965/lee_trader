# 실매매데이터 활용 방안

- 작성일: 2026-04-24
- 목적: 실매매 관련 데이터를 앞으로 어떤 관점으로 저장하고, 그 데이터가 시스템을 어떤 방향으로 발전시키는지 정리한다.

## 1. 현재 인식

현재 시스템은 아래 영역을 각각 어느 정도 갖추고 있다.

- 리서치 랭킹
- 모의투자 추적
- 실계좌 조회
- 실주문 실행
- 리뷰 메모

다만 이 영역들이 하나의 원장 구조로 완전히 연결되어 있지는 않다.

예를 들어 아래 질문에 대해 한 번에 답하기는 아직 어렵다.

- 어떤 종목을 왜 선택했는가
- 그 선택이 실제 주문으로 이어졌는가
- 실제로 어떤 가격과 수량으로 체결되었는가
- 체결 이후 보유/청산 과정은 어땠는가
- 결과적으로 그 판단이 맞았는가

즉, 현재는 `실행 전 판단`과 `실행 직후 확인`은 가능하지만, `실행 이후 사후관리`는 부분적으로만 가능한 상태로 본다.

## 2. 왜 데이터 축적이 중요한가

실매매 데이터를 쌓기 시작하면 시스템의 역할이 바뀐다.

초기에는 단순히 추천 화면과 점검 화면을 보는 수준이지만, 데이터가 연결되면 아래 단계로 발전할 수 있다.

1. 추천 시스템
2. 판단 추적 시스템
3. 실행 품질 관리 시스템
4. 운영 최적화 시스템

핵심은 단순히 데이터를 많이 저장하는 것이 아니라, `판단 -> 실행 -> 결과 -> 리뷰`를 연결해서 나중에 수정 가능한 구조를 만드는 것이다.

## 3. 기대 발전 방향

### 3.1 추천 시스템 -> 판단 추적 시스템

데이터가 쌓이면 다음을 볼 수 있다.

- 어떤 종목을 반복적으로 강행하는가
- 어떤 종목을 반복적으로 놓치는가
- 수동 판단이 개입되는 패턴은 무엇인가
- 랭킹 상위인데 실제로는 잘 안 되는 유형은 무엇인가

이 단계에서는 시스템이 단순한 추천기보다 `의사결정 기록 장치` 역할을 하게 된다.

### 3.2 판단 추적 시스템 -> 실행 품질 관리 시스템

그 다음에는 종목 선정이 아니라 실행 자체를 평가할 수 있다.

- 추천은 맞았는데 진입이 늦었는가
- 수량 배분이 적절했는가
- 슬리피지가 과도했는가
- 손절과 익절이 일관되게 적용되었는가
- 보유 기간이 전략 의도와 맞았는가

이 단계에서는 전략 문제와 실행 문제를 분리해서 볼 수 있다.

### 3.3 실행 품질 관리 시스템 -> 운영 최적화 시스템

데이터가 충분히 누적되면 운영 규칙을 조정할 수 있다.

- `confidence` 하한을 어디에 둘 것인가
- `risk_penalty`가 높은 종목을 어느 수준까지 허용할 것인가
- `강행`, `보류`, `누락 인정` 같은 수동 판단이 실제로 유효했는가
- 특정 섹터/시장 상황에서만 수동 판단이 더 나은가
- 오전/오후 진입 시 성과 차이가 있는가

이 단계에서는 화면 확인이 아니라 `운영 규칙의 통계적 개선`이 가능해진다.

## 4. 앞으로 답하고 싶은 핵심 질문

실매매 데이터를 저장하는 목적은 아래 질문들에 답하기 위함이다.

### 4.1 종목 선정 관련

- 좋은 종목을 실제로 잘 고르고 있는가
- 랭킹 상위 종목을 왜 놓치는가
- 수동 개입이 오히려 성과를 악화시키는 경우는 없는가
- 특정 조건의 종목을 반복적으로 과신하거나 과소평가하는가

### 4.2 실행 관련

- 추천은 맞았는데 주문 실행이 나빴던 적이 많은가
- 예상 가격과 실제 체결 가격 차이는 어느 정도인가
- 시장가/지정가/진입 시각 차이가 성과에 영향을 주는가
- 부분 체결, 미체결, 정정, 취소가 어떤 문제를 만들었는가

### 4.3 보유/청산 관련

- 너무 빨리 파는가, 너무 오래 들고 가는가
- 손절이 늦는가
- 익절 기준이 일관적인가
- 청산 사유별 성과 차이가 존재하는가

### 4.4 리뷰 및 학습 관련

- `강행` 판단은 실제로 유효했는가
- `누락 인정`한 종목은 실제로 더 좋았는가
- `보류`가 필요했던 종목을 너무 쉽게 진입하지는 않았는가
- 반복되는 실수 패턴은 무엇인가

## 5. 앞으로 저장해야 할 데이터 범주

세부 테이블 설계는 추후 진행하되, 큰 범주는 아래 5가지로 본다.

### 5.1 리서치 데이터

- 기준일 랭킹
- 점수와 세부 점수
- confidence
- risk_penalty
- driver
- 추천 사유와 리스크 요약

### 5.2 의사결정 데이터

- 선택 여부
- 선택 사유
- 제외 사유
- 수동 override 여부
- 운영자 판단 태그
- 리뷰 메모

### 5.3 실행 데이터

- 주문 요청 시각
- 주문 방향
- 주문 수량
- 주문 가격
- 실행 가능 여부
- gate 상태
- 차단 사유
- 주문 요청 id
- 실제 주문 제출 결과

### 5.4 결과 데이터

- 실제 체결가
- 실제 체결수량
- 수수료/세금
- 포지션 변동
- 평가손익
- 실현손익
- 보유 기간
- 기준일 이후 최고/최저 성과

### 5.5 리뷰 데이터

- 사전 판단 태그
- 사후 판단 태그
- 결과 해석 메모
- 다음 운영 수정 포인트

## 6. 중요 원칙

### 6.1 추천보다 원장이 중요하다

추천은 틀릴 수 있다.  
하지만 원장이 정확하면 나중에 개선할 수 있다.

즉, 앞으로는 `추천 화면 고도화`보다 `판단과 실행의 기록 구조`를 더 중요하게 본다.

### 6.2 데이터는 연결되어야 의미가 있다

리서치, 판단, 주문, 체결, 보유, 청산, 리뷰가 각각 따로 존재하면 해석이 어렵다.

앞으로는 가능한 한 아래 흐름으로 연결해야 한다.

- 리서치 후보
- 의사결정
- 주문 요청
- 실제 체결
- 보유/청산
- 사후 리뷰

### 6.3 나중에 답할 질문을 먼저 정하고 저장한다

무조건 저장 항목을 늘리는 방식은 지양한다.

먼저 아래를 정해야 한다.

- 우리는 나중에 무엇을 알고 싶은가
- 어떤 실수를 줄이고 싶은가
- 어떤 판단을 자동화하고 싶은가

그 질문에 답하는 데 필요한 데이터부터 저장하는 방향이 적절하다.

## 7. 현재 단계의 정리

현재 시스템은 아래 용도에는 충분히 강하다.

- 후보 탐색
- 운영 전 점검
- 주문 전 프리뷰
- 실계좌 현황 확인
- 모의투자 추적

하지만 아래 용도는 아직 부족하다.

- 실매매 사후관리의 일원화
- 판단과 주문/체결의 직접 연결
- 실행 품질의 정량 평가
- 반복 실수 패턴의 자동 분석

## 8. 다음 논의 주제

다음 회의에서는 아래 순서로 정리하는 것이 적절하다.

1. 우리가 반드시 답하고 싶은 운영 질문을 확정
2. 그 질문에 필요한 최소 데이터 정의
3. 리서치/판단/주문/체결/보유/청산/리뷰 연결 구조 정의
4. 실매매 사후관리용 DB 설계 초안 작성

## 9. 한 줄 결론

실매매 데이터를 쌓기 시작하면 시스템은 `추천 도구`에서 끝나지 않고,  
`판단을 복기하고 운영 규칙을 개선하는 학습형 운영 시스템`으로 발전할 수 있다.
