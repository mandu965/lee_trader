# 20260422 실자동매매 운영 적용 포인트 정리

## 0. 문서 목적

이 문서는 `실자동매매 진입장벽 완화안 v1`을 실제 운영에 적용할 때,
어디를 확인하고 어디를 수정해야 하는지 코드 기준으로 정리한 문서입니다.

핵심은 아래 4가지입니다.

- 실행 스위치는 어디서 결정되는가
- pilot / watch / confidence / cap 값은 어디서 읽는가
- 자동매매는 어떤 흐름으로 실행되는가
- 운영 화면에서는 무엇으로 확인하는가

---

## 1. 전체 구조 요약

현재 구조는 아래 흐름으로 보는 것이 가장 정확합니다.

1. `docker-compose.yml` 에서 자동매매 스케줄러 환경변수를 주입
2. `python/run_daily_scheduler.py` 가 스케줄에 맞춰 `submit_live_orders.py` 호출
3. `config/production_v1.yaml` 의 `execution_policy` 값을 Python이 읽어서 intent/policy 생성
4. 결과가 `outputs/*` 로 저장됨
5. Node 서버와 운영 화면이 이 결과와 환경 상태를 읽어서 표시

즉, 운영에서 실제로 건드릴 포인트는 크게 아래 두 군데입니다.

- 실행 스위치: `docker-compose.yml` 및 실제 서버 환경변수
- 정책 파라미터: `config/production_v1.yaml`

## 2. 실행 스위치 적용 포인트

### 2-1. 실제 스케줄러 서비스

자동매매 스케줄러 서비스는 아래 정의를 사용합니다.

- [docker-compose.yml](D:\ai\Lee_trader\docker-compose.yml)

핵심 서비스:

- `scheduler-auto-buy`

이 서비스에서 아래 환경변수가 들어갑니다.

- `AUTO_TRADE_EXECUTE`
- `AUTO_TRADE_ALLOW_BUY`
- `AUTO_TRADE_BUY_APPROVAL_REQUIRED`
- `AUTO_TRADE_CONFIRM_TEXT`

운영 의미:

- `AUTO_TRADE_EXECUTE=0`
  실행 파일은 만들어도 실제 주문 제출은 하지 않는 preview 중심 상태
- `AUTO_TRADE_ALLOW_BUY=0`
  BUY 제출 자체를 막는 상태
- `AUTO_TRADE_BUY_APPROVAL_REQUIRED=1`
  추가 승인 절차가 필요한 상태
- `AUTO_TRADE_CONFIRM_TEXT=LIVE_ORDER`
  실주문 실행 허용에 필요한 확인값

### 2-2. 실제 실행 명령 조립 위치

실제 submit 명령은 아래 파일에서 조립됩니다.

- [python/run_daily_scheduler.py](D:\ai\Lee_trader\python\run_daily_scheduler.py)

핵심 내용:

- `AUTO_TRADE_EXECUTE=1` 이어야 `--execute` 가 붙음
- 이때 `AUTO_TRADE_CONFIRM_TEXT=LIVE_ORDER` 가 아니면 예외 발생
- `AUTO_TRADE_ALLOW_BUY=1` 이어야 `--allow-buy` 가 붙음

즉, 이 영역이 먼저 정상이어야 `preview만 있고 execution이 거의 없는 상태`를 해소할 수 있습니다.

## 5. 운영 화면 확인 포인트

### 5-1. 런타임 상태 확인

Node 서버는 아래 코드에서 현재 환경변수 기준 런타임 상태를 읽습니다.

- [node/index.js](D:\ai\Lee_trader\node\index.js)

확인되는 주요 항목:

- `auto_trade_execute`
- `auto_trade_allow_buy`
- `buy_approval_required`
- `confirm_configured`

즉, 운영 화면에서 보이는 실행 가능 여부는 단순 문구가 아니라 실제 process env 기준 상태입니다.

### 5-2. 자동매매 화면

운영 화면 스크립트는 아래 파일입니다.

- [node/public/live-auto-trading.js](D:\ai\Lee_trader\node\public\live-auto-trading.js)

현재 이 화면에서는 아래 흐름을 확인할 수 있어야 합니다.

- trade intents
- order requests preview
- order execution
- skipped / hold reason
- runtime status

운영 해석 기준:

- intent는 있는데 execution이 적으면 실행 병목 가능성 큼
- preview는 있는데 execution이 적으면 execute/allow-buy/approval 확인 필요
- execution은 있는데 submitted가 적거나 skip reason이 많으면 제출 단계 사유 확인 필요

## 6. 실제 운영 적용 순서

### 단계 1. 서버 환경값 확인

먼저 실제 서버에서 아래 값을 확인합니다.

- `AUTO_TRADE_EXECUTE`
- `AUTO_TRADE_ALLOW_BUY`
- `AUTO_TRADE_BUY_APPROVAL_REQUIRED`
- `AUTO_TRADE_CONFIRM_TEXT`

확인 이유:

- 여기서 막히면 `production_v1.yaml` 을 조정해도 체감 변화가 거의 없습니다

### 단계 2. 정책값 확인

그 다음 아래 파일 값을 확인합니다.

- [config/production_v1.yaml](D:\ai\Lee_trader\config\production_v1.yaml)

우선 체크 항목:

- `pilot_limited_max_entries`
- `pilot_limited_total_exposure`
- `pilot_limited_position_cap`
- `standard_entry_confidence`
- `extended_entry_confidence`
- `min_entry_confidence`

### 단계 3. 화면에서 흐름 확인

운영 화면에서 아래 수치를 같이 봅니다.

- BUY intent 건수
- preview 건수
- execution 건수
- submitted 건수
- skipped 건수
- 상위 skip reason

### 단계 4. v1 적용

v1 기준으로 아래 순서로 적용합니다.

1. execute / allow-buy / approval 병목 점검
2. `pilot_limited_max_entries: 4 -> 5`
3. `pilot_limited_total_exposure: 0.36 -> 0.45`
4. 최소 1주일 관찰
5. 그래도 부족하면 confidence 소폭 조정 검토

## 7. 운영자가 기억해야 할 핵심

현재 실자동매매 진입장벽 완화에서 가장 중요한 포인트는 아래 두 줄입니다.

- 실행이 안 되는 원인이 `서버 환경값`인지 `정책값`인지 먼저 분리해야 합니다
- 지금은 추천모델보다 `execute / allow-buy / approval / pilot 한도`가 더 직접적인 병목일 가능성이 큽니다

한 문장 요약:

`운영 적용의 1차 포인트는 docker-compose 기반 실행 스위치와 production_v1.yaml 기반 execution_policy이며, 먼저 실행 병목을 해소한 뒤 pilot 한도를 완화하는 순서로 진행하는 것이 맞다.`
