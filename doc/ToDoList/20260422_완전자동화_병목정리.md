# 20260422 완전자동화 병목 정리

## 0. 이 문서를 쓰는 이유

`자동매매시스템이란.md`에서 일반적인 자동매매 시스템의 구조를 정리했다면,
이 문서는 한 단계 더 들어가서 아래 질문에 답하기 위한 문서입니다.

1. 지금 우리 시스템은 어디까지 자동화된 상태인가
2. 왜 아직 "완전 자동화"라고 단정하기는 어려운가
3. 앞으로 완전자동화에 가까워지려면 무엇이 병목인가

핵심은 "기능이 있느냐"보다 "운영 개입 없이도 안정적으로 굴러가느냐"입니다.

---

## 1. 먼저 결론부터

제 판단으로 현재 시스템은 아래 표현이 가장 정확합니다.

> 완전 무인 자동매매 시스템이라기보다, 운영 통제를 가진 자동집행 시스템

이 표현이 중요한 이유는 단순합니다.

- 추천이 자동으로 나오고
- gate 판단이 있고
- preview / execution 경로가 있고
- 스케줄러도 돌고
- 계좌 연동도 붙어 있지만

그렇다고 해서 곧바로 "운영자 없이 계속 돌아가는 시스템"이 되지는 않기 때문입니다.

완전자동화는 단순히 주문 버튼을 자동으로 누르는 것이 아니라,
예외 상황까지 포함해서 시스템이 스스로 상태를 해석하고 보수적으로 행동할 수 있어야 합니다.

---

## 2. 자동화 수준을 나눠서 보면

보통 자동화 수준은 아래처럼 구분해서 보는 편이 이해가 쉽습니다.

### 1단계. 분석 자동화

- 데이터 수집 자동화
- 점수 계산 자동화
- 후보 추출 자동화

이 단계에서는 "무엇을 볼지"는 자동으로 나오지만,
실제 행동은 여전히 사람이 결정합니다.

### 2단계. 집행 보조 자동화

- preview 자동 생성
- buy gate, 정책 검증
- 주문 가능 여부 점검

이 단계에서는 사람이 최종 승인만 하는 구조가 많습니다.

### 3단계. 조건부 집행 자동화

- 특정 조건에서만 자동 실행
- 시간대별 / 상태별 gate 적용
- 운영자가 미리 허용한 범위 안에서 자동 주문

지금 시스템은 대체로 이 구간에 가까워 보입니다.

### 4단계. 완전 자동화

- 데이터 이상 여부 자체를 감시
- 예외 상황에서 자동 보수모드 전환
- 계좌 / 주문 / 체결 / 스케줄 이상을 스스로 판단
- 운영자 부재 상황에서도 안전하게 지속 운영

이 단계는 구현보다 운영 신뢰성이 더 어렵습니다.

---

## 3. 왜 "거의 자동"과 "완전 자동"은 다르게 봐야 하나

겉보기에는 이미 자동화가 많이 진행된 것처럼 보일 수 있습니다.

- 스케줄러가 돈다
- 후보가 자동으로 나온다
- 주문 경로도 있다
- 실자동매매 화면도 있다

하지만 이 정도만으로는 완전자동화라고 보기 어렵습니다.

왜냐하면 완전자동화의 본질은 "정상 상황 처리"가 아니라
"비정상 상황에서도 시스템이 사고를 내지 않는 구조"이기 때문입니다.

예를 들어 아래 질문들에 시스템이 스스로 답할 수 있어야 합니다.

- 오늘 데이터 기준일이 정말 맞는가
- 아직 장중인데 종가 기준 판단을 해버린 것은 아닌가
- 계좌 상태가 최신이 아닌데 주문을 시도하는 것은 아닌가
- 과거 실패 이력이 있지만 현재는 복구된 상태인가
- 추천은 나왔지만 오늘은 집행하면 안 되는 날인가
- 일부 체결 / 미체결 / API 지연이 발생했을 때 어떻게 상태를 보수적으로 해석할 것인가

이 질문들에 대한 체계가 약하면, 기능은 자동이어도 운영은 자동이 아닙니다.

---

## 4. 현재 시스템의 가장 큰 병목

제가 보기에는 현재 병목은 "주문 API가 있느냐 없느냐"가 아닙니다.
오히려 아래 항목들이 더 본질적입니다.

## 4-1. 기준일과 데이터 정합성

자동매매에서 가장 위험한 문제 중 하나는
"서로 다른 기준의 데이터를 같은 화면에서 같이 믿는 것"입니다.

예를 들면:

- 추천은 전일 종가 기준인데
- gate는 오늘 장중 데이터 기준이고
- 계좌는 몇 분 전 snapshot이고
- 스케줄러는 방금 실패 후 복구 상태인 경우

이런 상태에서 시스템이 하나의 결론을 내리면,
겉보기에는 그럴듯해도 실제로는 논리 충돌이 생깁니다.

따라서 완전자동화의 첫 번째 병목은
"모든 판단이 같은 기준시점 위에 서 있는가"입니다.

이게 해결되지 않으면 자동 실행 비율을 올릴수록 오히려 위험해집니다.

## 4-2. 운영 결론의 구조화 부족

지금 시스템은 점수, 사유, 후보, 정책, gate, 메모가 여러 조각으로 나뉘어 있습니다.
이 자체는 나쁘지 않지만, 완전자동화로 가려면 최종적으로 시스템이 아래 형태의
"운영 결론 객체"를 안정적으로 만들어야 합니다.

- 오늘 매수 가능 / 불가
- 가능하다면 어떤 후보를 우선 볼지
- 불가하다면 정확히 어떤 이유 때문인지
- 수동 확인이 필요한 항목은 무엇인지
- 자동 실행 허용 범위는 어디까지인지

즉, 점수보다 더 중요한 것은 "오늘의 운영 결론"입니다.

점수는 판단의 재료일 뿐이고,
자동화는 결국 결론을 안정적으로 만드는 쪽으로 발전해야 합니다.

## 4-3. preview 와 execution 사이의 설명 가능성

좋은 자동매매 시스템은 주문을 보내기 전에
"왜 이 주문이 가능하다고 판단했는지"를 설명할 수 있어야 합니다.

지금도 preview / execution 구분은 매우 좋은 방향입니다.
하지만 완전자동화로 가려면 그 사이에 아래 정보가 더 명확해야 합니다.

- 어떤 정책이 통과되었는가
- 어떤 정책이 차단 사유가 될 수 있었는가
- 수량 계산 근거는 무엇인가
- 계좌 / 주문 가능 금액 / 보유 상태는 최신인가
- 이 주문은 운영자가 예상한 결론과 일치하는가

이 부분이 약하면, 자동 실행은 가능해도 사후 설명이 어려워집니다.

완전자동화는 "자동 주문"보다 "주문 결정의 추적 가능성"이 더 중요합니다.

## 4-4. 예외 상황의 정책화 부족

완전자동화에 가까운 시스템은 정상 로직보다 예외 로직이 더 중요합니다.

대표적인 예외는 아래와 같습니다.

- API 응답 지연
- 주문 실패
- 일부 체결
- 계좌 조회 실패
- 장중 / 마감 기준 혼선
- 데이터 갱신 지연
- 스케줄러 실패 후 복구

문제는 많은 시스템이 이런 상황을 "에러 메시지"로만 남기고 끝낸다는 점입니다.
하지만 완전자동화에서는 이런 것들이 모두 정책이 되어야 합니다.

예:

- 계좌 동기화 실패 시 자동 주문 금지
- 기준일 불일치 시 preview 만 허용
- 최근 실패 후 미복구 상태면 buy 차단
- 일부 체결 상태가 남아 있으면 신규 진입 제한

즉, 예외를 로그로 남기는 수준에서 끝나면 운영 보조 시스템이고,
예외를 정책으로 승격시켜야 완전자동화로 갑니다.

## 4-5. 운영 로그의 구조화 부족

완전자동화로 갈수록 자유 텍스트 메모보다 구조화된 사건 기록이 중요해집니다.

운영자가 나중에 봤을 때 아래 질문에 바로 답할 수 있어야 합니다.

- 왜 오늘은 실행되지 않았는가
- 왜 이 후보는 제외되었는가
- 왜 이 시점에 gate 가 닫혔는가
- 왜 스케줄러는 실패했지만 현재 상태는 정상인가
- 왜 자동 집행 대신 수동 검토로 남겨졌는가

이게 남지 않으면 시스템은 계속 돌더라도,
개선과 회고가 불가능해집니다.

---

## 5. 그러면 실자동매매는 자동이 아닌가

자동입니다. 다만 자동의 종류를 정확히 불러야 합니다.

현재 표현으로는 아래가 더 적절합니다.

- "자동 주문 실행 기능이 있는 시스템"
- "운영자가 통제 가능한 자동집행 시스템"
- "완전자동화로 가는 중간 단계 시스템"

반대로 아래 표현은 아직은 조심해야 합니다.

- "운영자 없이 완전히 방치 가능한 시스템"
- "예외 상황까지 모두 자율 처리하는 시스템"
- "무인 완전자동매매 시스템"

즉, 지금 시스템을 낮게 보는 것이 아니라
현재 위치를 정확히 보는 것이 중요합니다.

이걸 정확히 봐야 다음 투자 우선순위도 맞아집니다.

---

## 6. 앞으로 어디를 먼저 강화해야 하나

제 의견으로는 아래 순서가 맞습니다.

### 1순위. 기준일 / 데이터 기준 일치

- 모든 판단에 as-of-date 명시
- 장중 판단과 마감 판단 분리
- stale 데이터 차단
- 계좌 / 추천 / gate 기준시점 정렬

이건 완전자동화 이전에 기본 안전장치입니다.

### 2순위. 운영 결론 객체 만들기

운영 페이지의 핵심 출력은 점수 나열보다 아래여야 합니다.

- 오늘 판단
- 허용 / 차단 사유
- 꼭 확인할 항목
- 후보 우선순위
- 자동 집행 허용 범위

시스템이 이걸 안정적으로 만들 수 있어야
나중에 그 결론을 자동 집행으로 연결할 수 있습니다.

### 3순위. preview 기반 집행 설명 강화

- 어떤 조건으로 주문 가능 판정이 났는지
- 어떤 사유가 있으면 차단되는지
- 주문 수량 / 가격 / 정책 근거가 무엇인지

이 정보가 정리되어야 자동 실행이 늘어나도 불안해지지 않습니다.

### 4순위. 예외를 정책으로 승격

- 실패 후 복구 전까지 차단
- 계좌 동기화 실패 시 실행 금지
- 장 상태 불명확 시 preview-only
- 최근 오류가 있으면 보수 모드 전환

이 단계부터 비로소 "운영자 부재 대응력"이 생깁니다.

### 5순위. 운영 사건 로그 정리

- 오늘 결론이 왜 이렇게 났는지
- 어떤 이벤트가 상태를 바꿨는지
- 어떤 수동 개입이 있었는지

이게 있어야 시스템이 커져도 관리가 됩니다.

## 7. 운영자 페이지는 어떤 방향이 맞나

운영자 페이지는 단순 대시보드보다 "운영 콘솔"에 가까워지는 것이 맞습니다.

즉, 많이 보여주는 것이 아니라 빨리 판단하게 해주는 구조가 좋습니다.

운영자 화면에서 가장 중요한 것은 보통 아래 5가지입니다.

1. 오늘 결론
2. 지금 막히는 이유
3. 수동 확인이 필요한 항목
4. 자동 실행 가능 여부
5. 스케줄 / 계좌 / 정책 상태

반대로 아래 정보는 하단 참고영역이나 별도 페이지로 빠져도 됩니다.

- 상세 비교용 점수
- 실험용 shadow 결과
- 방문자 통계
- 메모 원문 전체

즉, 운영 페이지는 "결정 중심", 연구 페이지는 "분석 중심"으로 나눠지는 편이 맞습니다.

---

## 8. 지금 시점에서 가장 중요한 질문

앞으로 진지하게 이야기해보면 좋은 질문은 결국 아래로 모입니다.

1. 우리는 최종적으로 완전자동화를 목표로 하는가
2. 그렇다면 어디까지는 자동으로 두고, 어디부터는 의도적으로 운영자 확인을 남길 것인가
3. 운영자 페이지의 1차 출력물을 점수가 아니라 "오늘의 운영 결론"으로 바꿀 것인가
4. 예외 상황을 단순 로그가 아니라 정책으로 승격시킬 것인가
5. 메모를 자유 텍스트가 아니라 구조화된 운영 기록으로 바꿀 것인가

이 다섯 가지가 정리되면,
그 다음부터는 기능 추가보다 구조 정리가 훨씬 쉬워집니다.

---

## 9. 제 개인적인 판단

지금 단계에서 가장 현명한 방향은
"무조건 완전자동화"를 서두르는 것보다,
"운영 통제가 가능한 자동집행 시스템"을 매우 단단하게 만드는 것입니다.

그 이유는 단순합니다.

- 이미 자동화 기반은 꽤 올라와 있고
- 지금 부족한 것은 기능 수보다 운영 신뢰성이고
- 완전자동화의 본질은 실행 기능이 아니라 예외 대응 구조이기 때문입니다

즉, 지금은 자동화를 더 세게 미는 단계라기보다
자동화가 사고 나지 않게 구조를 고도화하는 단계에 가깝습니다.

이 단계를 잘 넘기면 그다음 완전자동화는 훨씬 현실적인 목표가 됩니다.
