# 20260422 시스템 개선방향

## 0. 왜 지금 이 문서를 쓰는가

지금 시스템은 이미 많은 기능을 가지고 있습니다.

- 랭킹 산출
- 점수 해석
- 장중/마감 기준 운영
- 수동매매/실자동매매 화면
- 운영자 대시보드
- 스케줄러와 산출물 관리

문제는 "기능이 없는 것"보다 "기능이 많아지면서 시스템의 중심이 무엇인지 흐려질 수 있다"는 점입니다.

한 번쯤은 다음 질문을 분명히 해야 합니다.

1. 이 시스템의 핵심 목적은 무엇인가
2. 지금 구조가 그 목적에 맞게 진화하고 있는가
3. 앞으로 무엇을 더할지보다, 무엇을 분리하고 무엇을 고정해야 하는가

이 문서는 코드 수정 지시서라기보다, 앞으로 시스템을 어떤 방향으로 키워야 하는지에 대한 운영/제품/기술 관점의 논의 초안입니다.

---

## 1. 현재 시스템을 어떻게 보고 있는가

현재 이 시스템은 단순한 "종목 추천기"도 아니고, 완성된 "자동매매 엔진"도 아닙니다.

더 정확히 말하면 아래 세 층이 섞여 있는 상태입니다.

1. 연구 시스템
   - 점수 체계 실험
   - 피처 검증
   - 확률/품질/기술/리스크 점수 비교
   - shadow 비교

2. 운영 시스템
   - 오늘 무엇을 볼지
   - 지금 gate가 어떤 상태인지
   - 어떤 산출물이 최신인지
   - 어떤 스케줄러가 정상인지

3. 집행 시스템
   - trade intents 생성
   - preview 생성
   - execution 시도
   - 계좌 동기화

이 세 층은 모두 필요합니다. 다만 앞으로는 "한 화면/한 코드 경로에 다 몰아넣는 방식"보다 "층을 분리하고 연결하는 방식"으로 가는 게 맞습니다.

지금까지는 기능을 빠르게 쌓아온 시기였다면, 앞으로는 시스템의 역할을 분리해서 오래 운영 가능한 구조로 옮겨야 하는 시기라고 봅니다.

---

## 2. 가장 중요한 방향: 시스템의 중심을 다시 정의해야 한다

제가 보기에는 이 시스템의 중심은 아래 한 문장으로 정리하는 게 가장 좋습니다.

> "신뢰 가능한 기준일 데이터로, 오늘 운영 판단을 만들고, 필요한 경우 집행까지 연결하는 시스템"

이 정의에서 핵심 단어는 세 가지입니다.

- 신뢰 가능한
- 오늘 운영 판단
- 집행까지 연결

여기서 우선순위는 분명해야 합니다.

1. 먼저 데이터와 기준일이 신뢰 가능해야 한다
2. 그 다음 오늘 운영 판단이 일관돼야 한다
3. 마지막으로 집행은 그 판단 위에서 제한적으로 연결돼야 한다

즉 앞으로의 개선 방향은 "자동매매를 더 많이 한다"가 아니라, 아래 순서가 맞습니다.

1. 기준 데이터 신뢰성 강화
2. 운영 판단 체계 명확화
3. 집행 레이어 안정화
4. 연구/실험은 본선과 분리

---

## 3. 앞으로 더 중요해질 질문들

### 3-1. 우리는 점수를 만드는 시스템인가, 운영 결론을 만드는 시스템인가

지금은 점수 체계가 매우 중요합니다. 하지만 실제 운영에서는 숫자 그 자체보다 아래가 더 중요합니다.

- 오늘 매수 가능한가
- 어떤 후보를 우선 볼 것인가
- 어떤 리스크 때문에 보류하는가
- 지금은 장중 보조판단인가, 마감 기준본인가

그래서 앞으로는 "점수"보다 "운영 결론"이 시스템의 1차 산출물이 되어야 합니다.

예를 들면:

- `final_score` 자체는 내부 계산값
- 운영 화면의 핵심은 `오늘 결론`, `걸리는 사유`, `후보`, `실행 가능 여부`

즉 사용자에게 보이는 중심 객체를

- 종목 점수
에서
- 운영 판단 패킷

으로 바꾸는 방향이 필요합니다.

### 3-2. 우리는 자동화를 키우는가, 운영 통제를 강화하는가

자동화는 매력적이지만, 이 시스템에서는 "자동 실행"보다 "통제 가능한 자동화"가 더 중요합니다.

특히 아래는 계속 강하게 유지해야 합니다.

- execute와 allow-buy 분리
- approval 단계 유지
- 장중 기준과 마감 기준의 역할 분리
- 계좌 상태 동기화 확인
- 실패 이력과 현재 정상 상태의 분리 표시

즉 발전 방향은 "사람을 빼는 자동화"보다 "사람이 개입할 지점을 분명히 가진 자동화"가 더 적합합니다.

### 3-3. 우리는 기능을 계속 얹을 것인가, 구조를 정리할 것인가

현재는 기능 추가 속도보다 구조 정리의 가치가 커지고 있습니다.

특히 다음 징후가 보입니다.

- 운영 화면과 참고 화면의 경계가 흐려짐
- 연구용 정보와 실운영 정보가 같은 층에 섞임
- 같은 정보가 여러 파일/여러 화면에서 다르게 보일 위험
- 스케줄러, 산출물, 운영 메모, 후보 화면이 각각 독립적으로 커짐

이 상태에서 기능을 더 얹기만 하면, 사용자는 기능이 많아졌다고 느끼는 대신 "어디를 먼저 봐야 하는지 모르겠다"고 느끼게 됩니다.

그래서 지금은 기능 확장보다 정보 구조 재설계가 더 중요합니다.

## 4. 권장하는 큰 방향

## 4-1. 시스템을 4개 층으로 재정리

앞으로는 시스템을 아래 4개 층으로 명확히 나누는 것이 좋습니다.

### A. 데이터 기준층

역할:

- 기준일 결정
- 산출물 최신성 보장
- stale 데이터 감지
- 스케줄러/산출물 상태 기록

핵심 원칙:

- 모든 추천/판단/집행은 같은 기준일 위에서만 이루어진다
- 기준일이 다른 데이터는 비교하지 않는다
- 데이터 최신성은 숨기지 않고 명시한다

### B. 판단층

역할:

- 점수 계산
- gate 계산
- 운영 결론 생성
- 후보군 생성

핵심 원칙:

- 숫자보다 결론이 1차 산출물
- "왜 이런 결론이 나왔는가"가 같이 출력되어야 함
- 장중 판단과 마감 판단은 역할이 다름

### C. 집행층

역할:

- intents
- preview
- execution
- approval
- 계좌 동기화

핵심 원칙:

- 판단층과 분리
- 실행은 반드시 명시적 조건에서만
- 실패는 상세하게 기록하고, 현재 상태와 구분해서 보여줌

### D. 관찰층

역할:

- 운영자 페이지
- 점수 검증
- 방문 집계
- 메모
- shadow 반복성

핵심 원칙:

- 운영 핵심 정보와 참고 정보를 분리
- 지금 바로 볼 것과 나중에 참고할 것을 나눔

---

## 4-2. 운영자 페이지는 "대시보드"가 아니라 "운영 콘솔"이 되어야 한다

운영자 페이지는 예쁜 정보 나열 화면보다 아래 성격에 더 가까워야 합니다.

- 오늘 판단 콘솔
- 문제 탐지 콘솔
- 실행 전 점검 콘솔

즉 이 페이지에서 가장 먼저 보여야 할 것은 아래입니다.

1. 오늘 결론
2. 꼭 확인할 사유
3. 지금 걸리는 항목
4. 오늘 확인 사항
5. 후보
6. 스케줄러/산출물 정상 여부

그리고 아래는 하단 참고영역으로 내려가는 것이 맞습니다.

- 방문 집계
- 방문 추이
- shadow 반복성
- 운영 메모

운영자 페이지는 "많이 보여주는 페이지"가 아니라 "결정을 빠르게 만드는 페이지"가 되어야 합니다.

---

## 4-3. 점수 검증 페이지는 운영 화면과 완전히 역할을 분리해야 한다

점수 검증은 필요합니다. 다만 이것은 운영자의 "오늘 행동"을 위한 페이지가 아니라, 모델/점수 체계의 내부 검증 페이지에 가깝습니다.

따라서 아래처럼 분리하는 것이 좋습니다.

- 운영자 페이지
  - 오늘 무엇을 할지
  - 무엇이 걸리는지
  - 어떤 후보를 볼지

- 점수 검증 페이지
  - 점수 공식이 맞는지
  - 어떤 요인이 순위를 바꿨는지
  - 모델 구조가 납득 가능한지

즉 점수 검증은 운영자 페이지의 일부가 아니라, 운영자가 필요할 때 들어가는 별도 분석실처럼 다루는 것이 맞습니다.

---

## 5. 앞으로 반드시 줄여야 할 복잡성

## 5-1. 같은 뜻의 값이 여러 이름으로 존재하는 문제

이미 시스템에는 아래처럼 비슷한 의미의 값이 섞일 여지가 있습니다.

- final_score
- live_score
- recommendation_score
- confidence score
- gate 판단
- 후보 승격/보류/제외

이 중 무엇이 운영 본선 값인지가 흐려지면, 화면과 코드와 해석이 다 달라집니다.

앞으로는 아래를 고정해야 합니다.

- 운영 본선 점수는 무엇인가
- 운영 본선 순위는 무엇인가
- 운영 결론은 무엇으로부터 나오나
- 사용자에게 설명할 기준 필드는 무엇인가

## 5-2. 화면이 많아질수록 같은 정보를 여러 번 설명하는 문제

현재는 설명 문구, 상태 문구, 안내 문구가 화면마다 조금씩 달라질 가능성이 큽니다.

이건 시간이 갈수록 운영 혼선을 만듭니다.

예를 들어 아래는 한 곳에서 정의해서 재사용하는 쪽이 낫습니다.

- gate 상태 설명
- 장중 기준 vs 마감 기준 설명
- 과거 실패 이력 vs 현재 상태 설명
- BUY 승인 필요 여부 설명

## 5-3. 연구 기능이 본선에 너무 쉽게 올라오는 문제

shadow, 새로운 점수 체계, 후보 비교, 실험적 보정 로직 등은 계속 필요합니다.

다만 이들은 본선에 바로 섞이기보다 아래 단계로 올라와야 합니다.

1. 연구
2. shadow
3. 운영자 참고
4. 제한적 반영
5. 본선 편입

이 단계가 명확해야 운영 안정성이 유지됩니다.

## 6. 앞으로 더 중요해질 기술 과제

## 6-1. 기준일 일관성

가장 중요한 기술 과제는 여전히 이것입니다.

- 모든 판단이 같은 as-of-date 위에서 이루어지는가
- 장중 기준과 마감 기준이 섞이지 않는가
- stale 데이터가 조용히 들어오지 않는가

이 부분은 화면 개선보다 우선순위가 높습니다.

## 6-2. 스케줄러와 산출물의 관측 가능성

운영자는 실패를 피할 수는 없어도, 실패를 빨리 이해할 수는 있어야 합니다.

따라서 앞으로는 아래가 더 잘 보여야 합니다.

- 마지막 성공
- 마지막 실패
- 현재 정상 여부
- 실패 이후 회복 여부
- 어떤 단계에서 멈췄는지

즉 "실패를 숨기지 말고, 해석 가능하게 만들기"가 핵심입니다.

## 6-3. 집행 단계의 방어적 설계

실자동매매로 갈수록 아래 질문이 중요합니다.

- preview와 execution 사이에 무엇이 달라질 수 있는가
- 계좌 동기화가 실패하면 무엇을 차단할 것인가
- 승인 누락이면 어디서 막을 것인가
- 주문 실행이 불가한 날 시스템은 어떤 메시지를 내야 하는가

자동화보다 방어 규칙이 더 중요합니다.

## 6-4. 운영 이벤트 로그

앞으로는 "왜 오늘 이런 결론이 나왔는지"를 사후에 추적할 수 있어야 합니다.

예를 들면 아래 같은 운영 이벤트 로그가 필요합니다.

- 오늘 기준일
- gate 상태 변화
- 후보 승격/제외 이유
- 실행 차단 이유
- 운영자 메모 저장 시점
- 수동 배포 여부

이 로그가 있으면 나중에 회고가 쉬워지고, 시스템 개선도 근거 기반으로 할 수 있습니다.

## 7. 제품 관점에서의 발전 방향

## 7-1. "추천 시스템"에서 "운영 판단 시스템"으로

앞으로 외형적으로도 시스템은 아래 방향으로 가는 것이 좋습니다.

- 추천 종목을 보여주는 제품
에서
- 운영 결론을 만드는 제품

즉 사용자가 기억해야 할 것은 "점수가 몇 점인가"보다

- 오늘 가능한가
- 왜 가능한가
- 무엇이 걸리는가
- 무엇을 먼저 봐야 하는가

입니다.

## 7-2. 운영자와 일반 사용자 경험 분리

운영자 페이지는 더 실무적이어야 하고,
일반 사용자/대외용 페이지는 더 설명적이어야 합니다.

둘을 같은 미감으로 끌고 가기보다, 목적에 맞게 분리하는 쪽이 좋습니다.

- 운영자: 밀도 높고 빠른 판단
- 일반 사용자: 이해하기 쉬운 설명과 신뢰 형성

## 7-3. "메모"보다 "결정 기록"으로

운영 메모도 앞으로는 단순 자유 텍스트보다 아래 형태로 발전시키는 게 좋습니다.

- 오늘 결론
- 보류 사유
- 수동 확인 필요 종목
- 실행 여부
- 특이사항

즉 메모를 구조화된 운영 기록으로 진화시키는 방향이 좋습니다.

## 8. 개인적으로 가장 중요하다고 보는 우선순위

제가 지금 시점에서 중요하다고 보는 순서는 아래입니다.

### 1순위. 운영 판단 체계 고정

- 오늘 판단
- 걸리는 사유
- 후보
- 실행 가능 여부

이 네 가지가 흔들리지 않는 구조를 먼저 만드는 것

### 2순위. 데이터/기준일 신뢰성 강화

- stale 차단
- 기준일 일치
- 장중/마감 역할 분리

### 3순위. 집행 단계 방어 강화

- preview/execution 차이 추적
- approval/confirm 조건 명확화
- 실패/회복 로그 명확화

### 4순위. 연구와 본선 분리

- shadow
- 실험 점수
- 반복성 검증
- 후보 비교

이들을 운영 참고층에 두고 본선과 분리

### 5순위. 화면과 문서 통일

- 같은 상태를 같은 언어로 설명
- 운영자 페이지와 점수 검증 페이지 역할 분리
- 문서와 실제 화면 해석 일치

## 9. 지금 당장 논의해볼 만한 질문

아래는 실제로 한번 진지하게 이야기 나눠볼 가치가 있는 질문들입니다.

1. 이 시스템의 1차 산출물은 점수인가, 운영 결론인가
2. 운영자 페이지에서 반드시 첫 화면에 보여야 하는 5개 정보는 무엇인가
3. 장중 기준 결과를 앞으로 어디까지 신뢰하고 어디까지 참고용으로 둘 것인가
4. shadow/연구 기능을 본선 편입하기 전에 어떤 검증 단계를 반드시 거칠 것인가
5. 자동매매는 어디까지 자동화하고, 어디부터는 의도적으로 사람 승인 단계를 남길 것인가
6. 운영 메모를 자유 텍스트로 둘 것인가, 구조화된 기록으로 바꿀 것인가
7. 지금 시스템이 6개월 뒤 더 복잡해졌을 때도 유지 가능한 구조인가

## 10. 제 제안

제 의견을 한 문장으로 정리하면 이렇습니다.

> 앞으로는 기능을 더 많이 붙이는 시스템보다, "신뢰 가능한 오늘의 운영 판단"을 더 또렷하게 만드는 시스템으로 가는 것이 맞습니다.

그리고 그 방향을 위해서는 아래가 필요합니다.

- 연구/운영/집행 분리
- 기준일 신뢰성 강화
- 운영자 페이지의 의사결정 중심 재구성
- 자동화보다 통제 가능한 집행 설계
- 로그와 기록의 구조화

이 시스템은 이미 "무언가를 할 수 있는 수준"은 넘었습니다.
이제는 "무엇을 중심으로 오래 운영할 것인가"를 정해야 할 시점입니다.
