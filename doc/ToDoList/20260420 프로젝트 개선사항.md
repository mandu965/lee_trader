# 프로젝트 전체 특이점 및 우려 사항 해소 로드맵

## 0. 전체 목표

현재 프로젝트는 기능은 많지만, 아래 3가지가 아직 완전히 정리되지 않았습니다.

* **어떤 점수 공식이 진짜 운영 공식인지**
* **그 점수가 실제로 신뢰할 만한지**
* **그 점수로 실제 주문까지 연결해도 되는지**

따라서 이번 정리의 목적은 아래입니다.

1. **최종 점수 산식을 1개로 통일**
2. **예측값 / 확률값 / 신뢰도값을 검증 가능하게 문서화**
3. **웹 표시용 / 리밸런싱용 / 실거래용 경계를 분리**
4. **실전 주문 리스크를 점수와 별도 관리**

* 리밸런싱 점수
* 주문 판단 점수

가 서로 달라질 수 있습니다.

### 목표

**“최종 점수는 오직 한 곳에서만 계산한다”**로 바꿉니다.

### 코덱스 작업 지시

```text
프로젝트에서 최종 점수(final_score, total_score, recommendation_score, rank score 계열)를 계산하는 모든 위치를 찾아주세요.

특히 아래 파일을 우선 점검해주세요.
- python/scoring.py
- python/ranking_builder.py
- python/rebalance_ranking.py

아래를 표로 정리해주세요.
1. 어떤 함수가 어떤 점수를 계산하는지
2. 입력 컬럼은 무엇인지
3. 출력 컬럼은 무엇인지
4. 실제 운영 파이프라인에서 호출되는지
5. 중복/비활성/구버전 여부

그 다음 최종 운영 점수 계산 함수를 1개 모듈로 통합하는 리팩토링 계획을 제안해주세요.

원칙:
- 최종 점수 계산은 한 파일/한 함수만 담당
- 다른 파일은 그 함수를 import 해서 사용
- 가중치는 config 또는 상수 블록으로 분리
- 웹 표시용/리밸런싱용/실험용 차이가 있다면 mode 인자로 분기

수정 전/후 영향 범위도 함께 적어주세요.
```

## 1-3. 공통 기준일(as-of-date) 강제

### 문제

종목별 최신 row를 그냥 가져오면 날짜가 섞일 수 있습니다.

### 리스크

랭킹이 같은 날짜 기준 비교가 아니게 됩니다.

### 목표

### 코덱스 작업 지시

```text
모델 예측과 랭킹 산출 시 사용되는 feature input이 종목별로 서로 다른 최신일자를 참조하는지 점검해주세요.

특히 아래를 확인해주세요.
- python/model_predict.py
- python/ranking_builder.py
- 최신 feature load 함수들

점검 목표:
1. 종목별 tail(1) 방식으로 최신 row를 가져오는지
2. 전체 공통 기준일을 강제하는 로직이 있는지
3. stale 종목(최신일이 늦은 종목) 처리 로직이 있는지

수정 방향:
- 공통 기준일(as_of_date) 기준으로만 종목 비교
- 해당 날짜 데이터가 없는 종목은 제외 또는 stale flag 부여
- 결과 파일에 as_of_date 컬럼을 반드시 명시

코드 수정안과 함께, stale 종목 수를 로그로 남기도록 제안해주세요.
```

# 제 판단으로 가장 치명도 높은 우려 5개

이 다섯 개는 특히 중요합니다.

1. **최종 점수 공식이 여러 군데 흩어져 있을 가능성**
2. **`scoring.py`가 사실상 no-op일 가능성**
3. **종목별 최신일이 섞인 상태로 랭킹될 가능성**
4. **quality score 표준화에 미래 정보 누수 가능성**
5. **확률값이 calibration 없이 그대로 노출될 가능성**
