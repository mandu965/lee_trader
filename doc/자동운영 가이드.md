# 자동운영 가이드

## 목적
- 이 문서는 `Lee_trader`를 사람이 매일 수동 실행하지 않아도, 시스템 내부에서 정해진 시각에 자동으로 돌리는 운영 방식을 정리합니다.
- 현재 프로젝트 기준 권장 방향은 `윈도우 작업 스케줄러`보다 `시스템 내부 스케줄링`입니다.

## 현재 프로젝트 기준 권장 구조
- 상시 구동 서비스
  - `postgres`
  - `node-api`
- 정시 배치 실행
  - `python/run_pipeline.py`
  - `python/run_operational_refresh.py`

정리하면:

- `node-api`는 계속 켜둡니다.
- 매일 정해진 시각에 Python 파이프라인만 돌려 새 산출물을 만듭니다.
- 코드 변경이 없는 날에는 `node-api`를 매일 재빌드하지 않습니다.

## 왜 시스템 내부 자동운영이 맞는가
- 현재 산출물은 모두 같은 시스템 내부 경로와 DB를 사용합니다.
  - `data`
  - `outputs`
  - `serving`
  - Postgres
- 운영 화면도 이 산출물을 그대로 읽습니다.
- 따라서 자동실행 책임도 같은 시스템 안에 두는 편이 구조적으로 일관됩니다.

## 권장 자동운영 시간
### 결론
- 장중 refresh 시각: `12:00`
- 마감 기준 정식 배치 시각: `16:00`
- 현재 권장 구조: `12:00 장중 + 16:00 마감`

### 이유
- 운영자 관점에서는 오전장과 오후장을 같은 기준으로 보면 해석이 애매해집니다.
- 오전장은 전일 마감 배치 결과로 보고, 오후장은 당일 장중 데이터를 반영한 별도 refresh가 필요합니다.
- 따라서 하루 1회 저녁 배치보다 `12:00 장중 refresh + 16:00 마감 배치`가 실무에 더 맞습니다.
- `16:00` 배치는 당일 종가 기준 정식 산출물입니다.
- `12:00` 배치는 장중 기준 운영 판단 갱신용이며, 마감 기준 결과와 같은 성격으로 보면 안 됩니다.
- 파이프라인은 아래 순서로 하루치 데이터를 만듭니다.
  1. 시장/유니버스 갱신
  2. 가격 다운로드
  3. 가격 정제 및 수정주가 생성
  4. 재무/품질/피처 생성
  5. 모델 예측
  6. 랭킹 생성
  7. 운영 산출물 생성

## 매일 자동실행 대상
### 1. Python 파이프라인
실제 핵심 daily 생성 흐름입니다.

```powershell
docker compose up -d python-pipeline
```

이 컨테이너는 내부에서 [run_pipeline.py](D:/ai/Lee_trader/python/run_pipeline.py)를 실행해 아래를 갱신합니다.

- `data/prices_daily_raw.csv`
- `data/prices_daily_clean.csv`
- `data/prices_daily_adjusted.csv`
- `data/features.csv`
- `data/predictions.csv`
- `data/ranking_final.csv`
- DB `daily_ranking`
- snapshot/history 관련 산출물

### 2. 운영 후처리
파이프라인이 끝난 뒤 운영용 산출물을 만듭니다.

```powershell
python python/run_operational_refresh.py
```

이 단계는 아래를 갱신합니다.

- `outputs/operational_buy_gate.json`
- `outputs/score_kpi_monitor.json` 또는 `data/score_kpi_monitor.json`
- `serving/daily_recommendations.json`
- `data/history/operational_buy_gate_history.csv`
- `data/history/score_kpi_monitor_history.csv`

## 매일 자동실행 대상이 아닌 것
### 1. `python-pipeline` 재빌드
아래 명령은 매일 자동실행용으로는 비권장입니다.

```powershell
docker compose build --no-cache --progress=plain python-pipeline
```

이유:
- 빌드 시간이 길어집니다.
- 매일 같은 이미지를 다시 만드는 비용이 큽니다.
- 코드가 바뀐 날에만 수동 또는 배포 시점에 수행하는 것이 맞습니다.

### 2. `node-api` 재빌드
아래 명령도 매일 자동실행 기본값으로는 비권장입니다.

```powershell
docker compose up -d --build node-api
```

이유:
- `node-api`는 산출물을 읽는 서비스입니다.
- 코드 변경이 없으면 재빌드할 이유가 없습니다.
- 매일은 `상시 구동 유지`가 더 자연스럽습니다.

## 권장 자동운영 루틴
### 최소 권장안
```powershell
docker compose up -d postgres node-api
docker compose up -d python-pipeline
python python/run_operational_refresh.py
```

해석:
- `postgres`, `node-api`는 계속 살아 있어야 합니다.
- 매일 정시에는 `python-pipeline`과 `run_operational_refresh.py`만 돌립니다.

### 코드 변경이 있는 날만 추가로 하는 일
```powershell
docker compose build --no-cache --progress=plain python-pipeline
docker compose up -d --build node-api
```

## 추천 자동운영 구조
### 1안. 전용 scheduler 서비스
가장 권장합니다.

- `postgres`: 상시
- `node-api`: 상시
- `scheduler`: 정시 실행 orchestration

역할:
- `scheduler`는 매일 `16:00`에 마감 기준 배치를 실행
- `scheduler-recovery`는 이름은 그대로지만 현재는 매일 `12:00` 장중 refresh 역할로 사용
- 각 실행은 `python/run_pipeline.py` 뒤에 `python/run_operational_refresh.py`를 이어서 수행
- 로그 기록
- 실패 시 상태 파일 또는 알림 확장 가능

장점:
- 운영 책임이 시스템 내부에 모입니다.
- 윈도우 로그인 세션에 덜 의존합니다.
- 나중에 다른 머신으로 옮기기 쉽습니다.

현재 프로젝트에는 이 구조를 바로 붙일 수 있도록 아래 서비스가 추가되었습니다.

- [docker-compose.yml](D:/ai/Lee_trader/docker-compose.yml) `scheduler`
- [docker-compose.yml](D:/ai/Lee_trader/docker-compose.yml) `scheduler-recovery`
- [run_daily_scheduler.py](D:/ai/Lee_trader/python/run_daily_scheduler.py)

역할:
- 컨테이너 내부에서 계속 살아 있으면서 현재 시각을 확인합니다.
- 매일 지정 시각이 되면 아래를 순서대로 실행합니다.
  1. `python/run_pipeline.py`
  2. `python/run_operational_refresh.py`
- 마지막 실행 결과를 상태 파일로 남깁니다.

상태 파일:
- [auto_ops_scheduler_status.json](D:/ai/Lee_trader/outputs/auto_ops_scheduler_status.json)
- [auto_ops_recovery_scheduler_status.json](D:/ai/Lee_trader/outputs/auto_ops_recovery_scheduler_status.json)

로그 파일:
- [auto_ops_scheduler.log](D:/ai/Lee_trader/logs/auto_ops_scheduler.log)
- [auto_ops_recovery_scheduler.log](D:/ai/Lee_trader/logs/auto_ops_recovery_scheduler.log)

### scheduler 서비스 시작
```powershell
docker compose up -d scheduler scheduler-recovery
```

기본값:
- `16:00`이 지난 뒤 처음 `scheduler`를 올려도 당일 catch-up 실행은 하지 않습니다.
- 기본 설정은 `내일 정시부터` 시작입니다.
- 이 동작은 `SCHEDULER_SKIP_CATCHUP_ON_START=1`로 제어합니다.

### scheduler 서비스 로그 확인
```powershell
docker compose logs -f scheduler
docker compose logs -f scheduler-recovery
```

### 자동수행 시각 변경
`.env` 또는 실행 환경에 아래 값을 넣으면 됩니다.

```env
SCHEDULER_DAILY_TIME=16:00
SCHEDULER_POLL_SECONDS=30
SCHEDULER_SKIP_CATCHUP_ON_START=1
SCHEDULER_RUN_POLICY=always

SCHEDULER_RECOVERY_DAILY_TIME=12:00
SCHEDULER_RECOVERY_POLL_SECONDS=30
SCHEDULER_RECOVERY_SKIP_CATCHUP_ON_START=1
SCHEDULER_RECOVERY_RUN_POLICY=always
SCHEDULER_PRIMARY_MAX_AGE_HOURS=20
```

기본값은 `16:00 마감 배치`, `12:00 장중 refresh`, 30초 주기 확인, 시작 당일 catch-up 건너뛰기입니다.

### 2안. `node-api` 내부 스케줄링
가능은 하지만 차선입니다.

장점:
- 구성 단순

단점:
- 웹 API와 배치 책임이 한 프로세스에 섞입니다.
- 장애 범위가 커집니다.

## 자동운영에서 주의할 점
### 1. PC 또는 서버는 켜져 있어야 합니다
- 시스템 내부 자동운영도 결국 실행 머신이 살아 있어야 합니다.
- PC가 꺼지면 어떤 스케줄 방식도 실행되지 않습니다.

### 2. `run_operational_refresh.py`는 원시 시세 적재 스크립트가 아닙니다
- 이 스크립트는 운영 판단 결과와 serving payload를 갱신하는 후처리 단계입니다.
- 원시 가격/피처/랭킹 생성은 `run_pipeline.py`가 담당합니다.

### 3. 운영 readiness와 자동화는 별개입니다
- 자동운영이 가능하다고 해서 곧바로 전면 실전 운영이 가능하다는 뜻은 아닙니다.
- readiness 판단은 계속 `ops-readiness`, `buy gate`, `matured snapshot` 기준으로 봐야 합니다.

## 현재 시점 권장 방침
- 자동화 자체는 준비해도 됩니다.
- 다만 자동화 목표는 `매일 같은 시각에 산출물을 안정적으로 쌓는 것`입니다.
- 현재 운영 기준은 `12:00 장중 판단 + 16:00 정식 마감 산출물`의 2단 구조입니다.
- 아직은 `공격적 실전 자동매수`가 아니라 `운영 이력 누적 자동화`로 보는 것이 맞습니다.

## 운영자용 요약
- 자동실행 위치: 시스템 내부
- 권장 시각: `12:00 장중 refresh`, `16:00 마감 배치`
- 매일 돌릴 것:
  - `python-pipeline`
  - `run_operational_refresh.py`
- 매일 안 돌려도 되는 것:
  - `python-pipeline` 재빌드
  - `node-api` 재빌드
- 상시 유지:
  - `postgres`
  - `node-api`
