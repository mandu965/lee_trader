## 3. 소스 검토 기준에서 본 핵심 이슈

## A. 가장 큰 이론 이슈: ret/prob가 너무 “상대순위화” 되어 있음

`python/scoring/final_score.py`에서:

* `ret_score`는 `pred_return_60d`, `pred_return_90d`를 같은 날짜 내 백분위 순위로 변환합니다.
* `prob_score`도 `prob_top20_60d`를 절대확률이 아니라 같은 날짜 내 상대 랭크로 변환합니다.

이 구조 자체는 종목 간 순위를 매기는 데는 좋습니다.
하지만 부작용이 있습니다.

### 문제

어떤 날은 시장 전체가 안 좋을 수 있습니다.
그런데도 상대평가만 하면 반드시 상위 10개, 20개가 나옵니다.

예를 들어:

* 모든 종목의 기대수익이 낮아도
* 모든 종목의 Top20 진입확률이 낮아도

그날 안에서 제일 나은 놈은 1등이 됩니다.

즉 지금 점수는
**“오늘 시장이 매수할 만한가?”** 보다는
**“오늘 후보들 중 누가 상대적으로 낫냐?”** 쪽에 더 가깝습니다.

### 왜 중요하냐

실매매에서는 “상위권”보다 **“절대 기대값이 충분한가”**가 더 중요합니다.
특히 사용자가 점수 신뢰도와 추천문서를 중요하게 본다면, 이 부분은 반드시 분리해야 합니다.

### 권장 수정

최종 점수를 아래처럼 2층 구조로 바꾸는 게 좋습니다.

* **상대순위 점수**: 기존처럼 cross-sectional rank 사용
* **절대 매수 적합도 점수**: raw prediction 기반 threshold/gate 사용

예:

* `pred_return_60d_abs_gate`
* `prob_top20_60d_abs_gate`
* `mdd_abs_gate`
* `market_regime_gate`
* `confidence_gate`

그리고

* `ranking_score`
* `buy_eligibility_score`

를 분리하세요.

이건 앞으로 웹서비스에서 아주 중요합니다.
“추천 순위”와 “실제 매수 가능”을 같은 숫자로 처리하면 설명도 애매해지고, 신뢰도도 흔들립니다.

## B. quality score는 구조는 좋지만, 현재 데이터 커버리지가 약합니다

`python/quality_builder.py`는 구조가 깔끔합니다.

* ROE
* 영업이익률
* 순이익률
* 부채비율
* OCF/Assets

를 winsorize → robust z-score → 가중합 → percentile 로 만들고 있습니다.

이 방식은 충분히 합리적입니다.
문제는 **현재 실제 데이터 커버리지**입니다.

제가 현재 출력 데이터를 봤을 때:

* 최신 랭킹에서 `quality_missing_ratio` 평균이 약 **0.46**
* Top20 평균도 **0.48**

즉, 재무 품질 점수가 꽤 많은 종목에서 **절반 가까이 비어 있는 상태**입니다.

### 해석

지금 quality는 “좋은 팩터”지만, 아직 **신뢰도 높은 운영 축**이라고 보긴 어렵습니다.
특히 일부 종목은 quality_score가 높아도, 사실상 2~3개 팩터만으로 나온 결과일 가능성이 있습니다.

### 더 큰 이슈

`quality_builder.py`에서 `quality_score`는 이미 날짜별 percentile score인데,
`final_score.py`에서 다시 `qual_score = percentile_by_date(quality_score)`로 한 번 더 랭킹화합니다.

이건 치명적 버그는 아니지만 **불필요한 이중 순위화**입니다.
단조 증가 변환이라 순서 자체는 거의 유지되지만, 정보량이 늘지는 않습니다.

### 권장 수정

1. `quality_score_raw`와 `quality_score_rank`를 분리
2. 최종 점수에는 둘 중 하나만 쓰기
3. `quality_score_confidence`를 실제로 weight에 반영하기

예:

* confidence 낮으면 quality contribution 축소
* 혹은 quality_score 자체를 `quality_score * confidence_ratio`로 조정

## C. RSI 계산은 초반부 왜곡 가능성이 있습니다

`python/feature_builder.py`의 `compute_rsi()`에서
결과를 `rsi.fillna(0)` 처리하고 있습니다.

이 방식은 초반 구간이나 손실이 없는 구간에서 RSI가 0으로 들어가 버릴 수 있습니다.
특히 일반적인 RSI 해석에서는:

* 초기 warm-up 구간은 NaN 유지
* avg_loss=0 인 경우 RSI는 100에 가깝게 처리

가 더 자연스럽습니다.

### 영향

초기 구간 종목들, 신규 상장 근처, 혹은 최근 상승이 강한 구간에서
기술점수에 미세 왜곡이 생길 수 있습니다.

### 권장 수정

* warm-up 구간은 NaN 유지
* `avg_loss == 0 and avg_gain > 0` → RSI 100
* `avg_gain == 0 and avg_loss > 0` → RSI 0
* 둘 다 0이면 50

이게 더 안정적입니다.

* “60일 이동평균”이라는 해석과

둘 중 하나로 정리하는 게 좋습니다.

* 진짜 60일선이면 `min_periods=60`
* 완화형 선이면 이름을 `ma_60_loose` 같은 식으로 분리

현재 상태는 운영 문서와 explain 단계에서 혼선을 만들 수 있습니다.

## F. confidence score는 잘 만들었지만 아직 “설명용”에 가까움

현재 결과를 보면 `confidence_score`가 꽤 잘 정리되어 있습니다.
문제는 이 값이 **실제 live ranking 결정 로직에 얼마나 강하게 관여하느냐**입니다.

지금은 설명문에는 잘 보이는데,
실제 매수 통제에는 약하게 느껴집니다.

### 권장 방향

confidence는 단순 표시가 아니라 **운영 제어값**으로 바꾸는 게 좋습니다.

* confidence < 55: 매수 금지
* 55~70: 소액
* 70~85: 표준
* 85+: 확대 가능

즉, confidence를 **포지션 사이징과 buy gate에 직접 연결**하세요.

이건 사용자가 “예측 신뢰도”를 매우 중요하게 본다고 했기 때문에 특히 중요합니다.

에 의해 많이 결정되고,
tech/qual/theme의 영향은 상대적으로 약합니다.

이건 현재 이론과 실제 결과가 약간 다르다는 뜻입니다.

### 해석

이론상은 다축 점수 체계인데, 실제 운영에서는
**“수익예측 + 확률 + 리스크 패널티” 중심**으로 사실상 수렴하고 있습니다.

이 자체가 꼭 나쁜 건 아닙니다.
오히려 현실적일 수 있습니다.
다만 문서와 실제 기여도가 일치하도록 맞춰야 합니다.

## 5. 버그/리스크 관점에서 우선 점검할 항목

우선순위 순서로 적겠습니다.

### 1순위

**절대값 기반 buy gate 부재**

* 지금 점수는 상대순위형
* 실매수 승인과 분리 필요

### 2순위

**quality 데이터 커버리지 부족**

* 결측이 너무 많음
* 현재 quality high 종목도 실제론 sparse data일 수 있음

### 3순위

**market regime 입력 원천 검증**

* market_status 수치 이상 여부 확인
* 전부 neutral 상태가 정상인지 검증

### 4순위

**feature_builder RSI / MA window 정합성**

* RSI fillna(0)
* ma_60 min_periods=25

### 5순위

**confidence를 표시용에서 운영용으로 승격**

* 포지션 사이즈, 진입 gate와 연결

### 6순위

**테마 점수의 실질 영향도 재평가**

* 현재 nonzero 종목은 많지만 final 영향은 크지 않음
* 운영용으로 유지할지, shadow/reference 중심으로 둘지 결정 필요

## 6. 앞으로의 방향

제가 보면 다음 단계는 이렇게 가는 게 가장 좋습니다.

## 방향 1. “추천 점수”와 “매수 승인”을 분리

이게 가장 중요합니다.

### 추천 점수

* 기존 final_score 유지
* 종목 간 우선순위 비교 용도

### 매수 승인 점수 / gate

* 절대 기대수익 threshold
* 절대 확률 threshold
* drawdown 제한
* confidence threshold
* market regime gate

이렇게 분리하면 웹에서도 훨씬 설명이 쉬워집니다.

예:

* 추천순위 3위
* 하지만 매수 승인: 보류
* 이유: confidence 부족 / 절대 기대수익 부족

이 구조가 훨씬 신뢰를 줍니다.

---

## 방향 2. confidence를 포지션 사이징 엔진으로 사용

최종 목표가 종목 추천 웹프로그램이라면
점수 하나만 던지는 것보다 다음이 더 강합니다.

* 추천 점수
* 예측 신뢰도
* 권장 액션
* 권장 비중

예:

* A 종목: 점수 82 / 신뢰도 86 / 매수 가능 / 비중 8%
* B 종목: 점수 79 / 신뢰도 58 / 관찰 전용

이렇게 되면 “추천 문서” 품질이 확 올라갑니다.

---

## 방향 3. quality 축을 보강하거나 가중치를 현실화

지금 상태라면 둘 중 하나를 택해야 합니다.

### 선택지 A

quality 데이터 파이프라인을 보강해서
실제 운영 핵심축으로 유지

### 선택지 B

지금처럼 결측이 많다면
quality를 핵심 점수축이 아니라 **보조 gate**로 내리는 것

현재 상태에선 B가 더 현실적일 수 있습니다.

---

## 방향 4. 테마는 “점수”보다 “설명/상황축”으로 더 강할 수 있음

지금 테마는 흥미롭고 프로젝트 차별점도 있습니다.
다만 실제 기여도가 기대보다 약하면, 억지로 점수에 넣는 것보다:

* 추천 이유 설명
* 섹터/테마 노출
* 포트폴리오 집중도 경고
* 테마 분산 체크

쪽으로 더 크게 쓰는 게 나을 수 있습니다.

웹 서비스에서 유저는
“왜 이 종목이 지금 뜨는가”를 좋아하지
테마 점수가 4.2점 올라갔다는 수치 자체를 좋아하진 않습니다.

---

## 방향 5. 운영 검증 기준을 문서화

당장 필요한 건 성능 개선만이 아닙니다.
**“언제 이 시스템을 믿고 쓸 것인가”**를 문서화해야 합니다.

추천 기준 문서에 최소한 아래가 있어야 합니다.

* 데이터 커버리지 기준
* confidence 허용 기준
* walk-forward acceptance 기준
* 시장 레짐별 사용 원칙
* 매수/보류/제외 판정 규칙
* 점수별 행동 가이드

이 문서가 있어야 나중에 웹프로그램에서 사용자에게 일관된 설명이 가능합니다.

## 7. 제 판단: 실제 매수에 써도 되나?

제 답은 이렇습니다.

**“보조 의사결정 도구로는 충분히 쓸 수 있다.
하지만 아직 단독 자동매수 엔진으로 쓰기엔 이론 보강이 더 필요하다.”**

특히 지금은:

* 상대순위형 성격이 강하고
* quality 커버리지가 약하며
* confidence가 아직 gating보다 설명에 가깝고
* market regime 입력 검증이 더 필요합니다.

그래서 현 단계에서는

* Top20을 그대로 전량 신뢰해서 기계적으로 매수
  보다는
* Top20을 1차 후보군으로 보고
* confidence / absolute gate / 뉴스 / 차트 / 실적 일정
  으로 2차 필터링

하는 방식이 맞습니다.

## 8. 현재 기준 우선순위 5개

초기 우선순위 중 일부는 이미 반영되었습니다.  
지금 기준으로 다시 정리하면 아래 순서가 더 맞습니다.

1. **`buy_eligibility_score` 또는 종목 단위 절대 매수 gate 신설**
   * 현재 `buy_gate`는 운영 상태 판단에는 도움이 되지만, 종목별 절대 매수 적합도 점수는 아직 없음

2. **confidence를 포지션 크기와 직접 연결**
   * 설명용 점수에서 끝나지 말고, 비중 규칙으로 연결 필요

3. **quality 커버리지 보강 또는 quality 구조 분리**
   * `quality_score_confidence` 반영은 됐지만, 데이터 커버리지 이슈는 계속 남아 있음

4. **market_status 검증 리포트의 운영 반영 확대**
   * 원천값 검증 리포트는 추가됨
   * 다음 단계는 threshold 조정 실험이나 종목별 gate 설명으로 더 연결하는 것

5. **theme를 점수축으로 둘지, 설명축으로 둘지 역할 재정의**
   * 현재는 차별화 포인트지만, 실제 기여도 대비 역할 정리가 더 필요

### 이미 반영된 항목

* **market_status 원천값 검증 리포트 추가**
* **RSI / MA60 계산 정합성 수정**
* **quality confidence를 반영한 완화형 가중치 조정**
