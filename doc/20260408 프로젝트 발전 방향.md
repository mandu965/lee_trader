# 2026-04-08 프로젝트 발전 방향

기준일: 2026-04-08 KST

이 문서는 현재 `Lee_trader` 프로젝트의 상태를 기준으로, 앞으로 어떤 방향으로 발전시키는 것이 가장 효율적인지 정리한 전략 문서입니다.  
핵심 관점은 `기능 추가`보다 `운영 신뢰도`, `데이터 품질`, `실전 운영 가능성`을 높이는 데 있습니다.

---

## 1. 현재 프로젝트의 위치

이 프로젝트는 단순한 종목 추천 스크립트 단계는 이미 지났습니다.

현재 갖춘 요소:
- 일별 운영 파이프라인
- ranking / prediction / quality / gate 산출물
- shadow quality_risk_guard 검증 루프
- paper trading 추적
- 운영자 페이지와 운영 문서
- scheduler / recovery scheduler 기반 자동 실행 구조

즉, 지금부터의 발전 방향은 `새 기능을 얼마나 더 붙이느냐`보다 아래 질문에 답하는 방향이어야 합니다.

- 이 모델을 실제 운영에 올려도 되는가
- 그 판단 근거가 반복적으로 재현되는가
- 데이터가 안정적이고 설명 가능한가
- 운영 실패나 데이터 이상을 빠르게 감지할 수 있는가

현재 상태를 한 줄로 정리하면 이렇습니다.

> 좋은 분석 파이프라인은 이미 있고, 이제는 그것을 `운영 가능한 시스템`으로 다듬는 단계입니다.

---

## 2. 현재 핵심 병목

### 2.1 가장 큰 병목: 반복성 근거 부족

최근 작업 결과 기준으로 `quality_risk_guard`는 성능 측면에서 긍정 신호가 있었지만, production 승격은 아직 보류 상태입니다.

핵심 이유:
- `ordering_ok = true`
- `quality_coverage_ready = true`
- 하지만 `repeatability_ready = false`
- `usable_snapshot_count = 1`

즉, 지금 시스템의 가장 큰 한계는 `좋아 보이는 결과가 한 번 나온 것`과 `반복적으로 재현되는 결과`를 아직 충분히 구분하지 못한다는 점입니다.

이 문제를 해결하지 않으면:
- 모델 승격 판단이 임시 판단처럼 보일 수 있음
- 운영자가 결과를 신뢰하기 어려움
- 이후 회고 시 “왜 이 시점에 반영했는가”를 설명하기 어려움

### 2.2 두 번째 병목: 데이터 품질의 구조적 안정성 부족

quality coverage는 이미 개선됐지만, 여전히 일부 업종과 최신 재무 데이터 처리에서 불안정성이 남아 있습니다.

남아 있는 문제:
- 금융주/특수 업종의 품질 팩터 해석 불일치
- 최신 연도 결측 대응이 보정 성격에 머무름
- 원천 데이터 정확도와 업종별 예외 규칙이 충분히 구조화되지 않음

즉, 지금부터는 `결측을 메우는 기술`보다 `잘못된 값을 덜 만드는 구조`가 중요합니다.

### 2.3 세 번째 병목: 운영 제품으로서의 완성도 부족

현재 시스템은 내부 운영툴로는 충분히 유용하지만, 아직은 `구조를 잘 아는 사람이 운영해야 하는 시스템`에 가깝습니다.

부족한 부분:
- 장애 원인 가시성
- 기준일 불일치 탐지
- 산출물/정책/점수식 변경 이력 관리
- UI/문서 출력 품질의 일관성

이 단계의 문제는 모델 성능과 별개로 실제 운영 리스크로 이어집니다.

## 3. 발전 방향의 기본 원칙

앞으로의 방향은 아래 4개 원칙으로 정리하는 것이 맞습니다.

### 3.1 예측력보다 운영 신뢰도 우선

새 팩터나 새 모델을 계속 추가하기 전에, 현재 시스템이 내린 판단을 반복적으로 설명하고 방어할 수 있어야 합니다.

핵심 질문:
- 왜 오늘은 BLOCK인가
- 왜 이 후보는 watchlist인가
- 왜 이 shadow 실험은 아직 승격되지 않았는가

이 질문에 자동으로 답할 수 있어야 운영 시스템이 됩니다.

### 3.2 데이터 양보다 데이터 정확도 우선

지금 시점에서는 더 많은 외부 지표를 붙이는 것보다:
- 기존 지표의 정확도
- 업종별 해석 일관성
- 최신성 검증
- 결측/이상치 탐지

이 네 가지를 강화하는 편이 훨씬 효과적입니다.

### 3.3 결과보다 의사결정 로그 우선

운영 프로젝트가 성숙하려면 결과 파일만 쌓이면 안 됩니다.  
그날의 판단과 이유도 함께 축적돼야 합니다.

필요한 것:
- 일자별 운영 verdict 저장
- blocker 저장
- promotion 보류/승격 사유 저장
- 사람이 남긴 운영 메모와 자동 해석의 연결

### 3.4 “실매수 전 단계”를 더 길고 엄격하게 운영

현재 프로젝트는 아직 공격적으로 실매수 자동화를 늘릴 시점이 아닙니다.  
오히려 `paper -> watchlist -> small test -> promotion` 순서를 더 엄격히 분리하는 방향이 적절합니다.

## 4. 권장 발전 로드맵

## 4.1 1단계: 운영 신뢰도 완성

가장 먼저 해야 할 단계입니다.

목표:
- repeatability 판단 자동화 완성
- promotion verdict의 근거 축적
- 운영자 페이지/문서/JSON이 같은 결론을 말하도록 통일

우선 작업:
- snapshot 누적 후 repeatability 리포트 자동 재평가
- promotion verdict 일자별 이력 저장
- `왜 HOLD_FOR_MORE_EVIDENCE인지`를 운영자 화면에서 바로 표시
- shadow 실험별 승격 상태 테이블 추가

완료 기준:
- 운영일이 지나면 승격 판단이 자동 갱신됨
- 운영자가 문서 없이도 페이지에서 blocker를 이해할 수 있음
- 승격/보류 판단의 근거가 일자별로 남음

## 4.2 2단계: 데이터 품질 체계화

이 단계는 모델 성능보다 훨씬 중요합니다.

목표:
- quality/fundamental 데이터의 신뢰도 개선
- 업종별 처리 규칙 명시화
- stale/missing/anomaly 자동 탐지

우선 작업:
- DART 원천 수집 정확도 점검
- 금융주/특수 업종용 별도 quality rule 검토
- feature freshness 검사 추가
- 이상치 탐지 리포트 추가
- 산출물 날짜 불일치 자동 경고 추가

완료 기준:
- 운영자가 어떤 데이터가 약한지 즉시 파악 가능
- coverage 개선이 임시 보정이 아니라 구조적 개선으로 바뀜
- 결측이나 오래된 데이터가 운영 판단에 섞일 때 즉시 표시됨

## 4.3 3단계: 준실전 운영 고도화

이 단계부터는 시스템을 실제 운용 체계에 가깝게 다듬습니다.

목표:
- paper trading을 더 엄격한 준실전 평가로 확장
- 후보 선정이 아니라 포지션 운영까지 평가

우선 작업:
- 슬리피지/분할매수/분할청산 가정 반영
- 포지션 sizing 규칙 추가
- 최대 동시 보유 수와 리스크 예산 도입
- 신호 발생 후 체결 지연 시 성과 저하 추적

완료 기준:
- “추천이 좋다”가 아니라 “실제로 운영 가능한가”를 평가할 수 있음
- 종목 선택뿐 아니라 포트폴리오 운영 능력도 측정 가능

## 4.4 4단계: 서비스 운영화

마지막 단계는 배포와 복구 체계를 안정화하는 것입니다.

목표:
- 운영 환경 안정화
- 이력 관리 강화
- 장애 대응 자동화

우선 작업:
- VPS + Docker Compose 운영 표준화
- Postgres 기준 이력 저장 강화
- 백업/복구 루틴 자동화
- 스케줄 실패 알림 추가
- 운영자 페이지의 인코딩/표시 품질 점검 체계화

완료 기준:
- 하루 단위 자동 운영 실패를 빠르게 감지 가능
- 데이터/문서/페이지 품질 이슈가 운영 판단 오류로 번지지 않음
- 호스팅 후에도 현재 운영 절차를 그대로 유지 가능

## 5. 지금 당장 우선순위가 높은 것

아래 5개는 바로 이어서 진행할 가치가 높습니다.

### 5.1 repeatability 자동 재평가 루프 완성

가장 중요합니다.  
현재 blocker가 거의 이 항목 하나로 모이고 있기 때문입니다.

### 5.2 기준일 불일치 자동 탐지

`ranking_final`, `daily_recommendations`, `operational_buy_gate`, `paper_trading` 사이 날짜가 어긋나는 순간 운영 품질이 크게 떨어집니다.

### 5.3 quality 원천 정확도 개선

carry-forward는 보완책일 뿐입니다.  
이제는 source quality 자체를 끌어올려야 합니다.

### 5.4 운영자 페이지의 해석 품질 강화

운영자 페이지는 숫자를 보여주는 화면이 아니라 `그 숫자를 어떻게 읽어야 하는지`를 알려주는 화면이어야 합니다.

필요한 방향:
- blocker 우선 표시
- 오늘 행동 가이드 고정
- 승격 상태와 보류 이유 분리 표시

### 5.5 운영 판단 로그 저장

운영 메모, 자동 해석, gate verdict, promotion verdict를 같은 날짜 키로 남겨야 합니다.

## 6. 지금 당장 우선순위가 낮은 것

아래 항목은 지금 시점에서는 후순위로 두는 편이 맞습니다.

- 새로운 대형 모델 추가
- 과도한 UI 확장
- 전략 수를 무리하게 늘리는 것
- 복잡한 멀티전략 포트폴리오 실험
- 테마/뉴스 등 설명 신호를 운영 점수에 바로 붙이는 것

이유는 단순합니다.  
현재 병목은 `아이디어 부족`이 아니라 `운영 근거의 재현성 부족`이기 때문입니다.

## 7. 추천 실행 순서

실행 순서는 아래처럼 잡는 것이 현실적입니다.

2. promotion verdict 이력 저장
3. 기준일/산출물 정합성 점검 자동화
4. quality source 정확도 개선
5. 운영자 페이지 해석 품질 고도화
6. 준실전 paper trading 규칙 강화
7. VPS 기준 운영 환경 안정화

## 8. 결론

이 프로젝트의 다음 발전 방향은 `더 똑똑한 추천기`를 만드는 것이 아닙니다.  
핵심은 `왜 이 판단을 했는지 설명 가능하고, 같은 조건에서 반복적으로 신뢰할 수 있는 운영 시스템`으로 가는 것입니다.

현재 기준으로 보면:
- 분석 엔진은 이미 충분히 갖춰져 있음
- 운영 보조 도구도 상당 부분 갖춰져 있음
- 남은 핵심 과제는 `반복성`, `데이터 정확도`, `운영 기록화`

따라서 앞으로의 가장 올바른 방향은 아래 한 줄로 요약할 수 있습니다.

> 기능 확장보다 운영 신뢰도 축적이 우선이다.

이 원칙을 유지하면 이후 실매수 확대, 호스팅 전환, 포트폴리오 운영 자동화도 훨씬 안정적으로 이어갈 수 있습니다.
