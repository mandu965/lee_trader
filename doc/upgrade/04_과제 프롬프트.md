지금부터 Lee Trader 프로젝트의 4차 개선 과제인

"submit\_unknown + broker lookup 복구"를 진행합니다.



이 과제는 1차 Ranking Trust Gate와 독립적으로 진행 가능한 운영 안정성 과제입니다.



핵심 목표:

자동매매에서 가장 위험한 상태인

"주문이 성공했는지 실패했는지 모르는 상태"를 명확히 분리하고,

다음 사이클에서 broker lookup으로 실제 주문 접수 여부를 확인하는 복구 흐름을 만든다.



중요:

\- 이번 과제는 Rule 자동매매 주문 복구 흐름만 다룬다.

\- AI 자동매매 주문 복구는 별도 과제로 분리한다.

\- KIS API를 테스트 목적으로 실제 호출하지 말 것.

\- 실계좌 주문 로직을 직접 실행하지 말 것.

\- 기존 submitted 상태의 fill sync 흐름은 깨지 않도록 한다.

\- 기존 failed 상태의 명확한 실패 처리 흐름은 유지한다.

\## Step 4. 구현 요구사항 A — rule\_order\_submitter.py



현재 문제:

타임아웃, OSError, KIS 5xx 등 "요청이 KIS에 도달했을 수 있는 예외"가 발생해도

order\_status가 failed로만 저장된다.

이 경우 다음 사이클에서 broker lookup 복구가 트리거되지 않는다.



변경 목표:

possibly\_sent 계열 예외는 failed가 아니라 submit\_unknown으로 저장한다.



추가할 상태값:



\- submit\_unknown

&#x20; - 주문 요청이 KIS에 도달했을 수 있으나 응답을 받지 못한 상태

&#x20; - 다음 fill sync 또는 recovery cycle에서 broker lookup 필요



\- reconcile\_required

&#x20; - broker lookup을 시도했으나 매칭 실패 또는 복수 매칭으로 자동 복구 불가

&#x20; - 운영자 수동 확인 필요



예외 분류 기준:



1\. submit\_unknown 대상



아래 예외는 주문이 실제 접수됐을 가능성이 있으므로 submit\_unknown으로 저장한다.



\- TimeoutError

\- OSError 계열 중 요청 전송 후 실패 가능성이 있는 예외

\- KISHTTPError 5xx

\- \_is\_retryable\_order\_error(exc) 결과 retryable=False 이면서, KIS에 도달했을 수 있는 예외

\- 기존 코드에서 order\_submit\_failed\_possibly\_sent 태그가 붙는 예외



2\. failed 대상



아래 예외는 명확한 실패로 보고 기존 failed 흐름을 유지한다.



\- KISAuthError

\- ConnectionRefusedError

\- KISHTTPError 4xx

\- 명확한 validation error

\- 주문 전 단계에서 발생한 오류



구현 방향:



\- 기존 \_is\_retryable\_order\_error()를 최대한 활용한다.

\- 예외 처리 블록에서 possibly\_sent 여부를 별도 변수로 계산한다.

\- possibly\_sent=true이면 다음 값을 기록한다.



order\_status = "submit\_unknown"

reconciliation\_status = "submit\_unknown\_pending\_lookup"

order\_block\_reason에는 기존 사유와 함께 "order\_submit\_unknown\_possibly\_sent"를 추가한다.

error\_type, error\_message가 저장되는 구조가 있다면 유지한다.



\- possibly\_sent=false이면 기존처럼 failed 처리한다.



order\_status = "failed"

reconciliation\_status = "submit\_failed"



\- 기존 submitted 처리 흐름은 변경하지 않는다.

\- 기존 debug\_skipped, blocked, planned 처리 흐름은 변경하지 않는다.



submit\_unknown 발생 시 구조화 로그를 WARNING으로 남긴다.



로그 예시:



RULE\_SUBMIT\_UNKNOWN | date=2026-05-07 | code=005930 | name=삼성전자 | side=BUY | qty=10 | error\_type=TimeoutError | reconciliation\_status=submit\_unknown\_pending\_lookup

\## Step 5. 구현 요구사항 B — submit\_unknown 알림



submit\_unknown 발생 시 아래 환경변수가 true이면 notify\_warning을 호출한다.



환경변수:



RULE\_NOTIFY\_ON\_SUBMIT\_UNKNOWN=true



알림 형식:



title:

\[RULE] 주문 상태 불명확 - 확인 필요



message:

{as\_of\_date} | code={code} | side={side} | qty={qty}



details:

{

&#x20; "code": code,

&#x20; "name": name,

&#x20; "side": side,

&#x20; "order\_qty": qty,

&#x20; "error\_type": type(exc).\_\_name\_\_,

&#x20; "error\_message": str(exc),

&#x20; "as\_of\_date": as\_of\_date,

&#x20; "reconciliation\_status": "submit\_unknown\_pending\_lookup",

&#x20; "action\_required": "다음 사이클 broker lookup 자동 시도. 미해소 시 수동 확인 필요."

}



주의:

\- notifier.py는 수정하지 말 것.

\- notify\_warning 함수가 없거나 호출 방식이 다르면 기존 notifier.py 구조에 맞춰 최소 변경하라.

\- 알림 실패가 주문 결과 저장을 방해하지 않도록 try/except로 보호하라.

\- 알림 실패 시 warning 로그만 남기고 주문 결과 기록은 계속 진행한다.

\## Step 6. 구현 요구사항 C — rule\_order\_fill\_sync.py



현재 문제:

rule\_order\_fill\_sync.py는 일반적으로 order\_status == submitted 이고 broker\_order\_id가 있는 항목을 기준으로 체결 조회를 한다.

submit\_unknown 상태는 broker\_order\_id가 없을 수 있으므로 기존 fill sync 대상에 잡히지 않는다.



변경 목표:

submit\_unknown 상태 항목을 broker lookup 대상으로 포함한다.



환경변수:



RULE\_UNKNOWN\_ORDER\_LOOKUP\_ENABLED=true

RULE\_UNKNOWN\_ORDER\_MAX\_LOOKUP\_DAYS=1

RULE\_NOTIFY\_ON\_RECONCILE\_REQUIRED=true



구현 방향:



1\. submit\_unknown 대상 선별



다음 조건을 만족하는 항목을 unknown lookup 대상으로 분리한다.



\- order\_status == "submit\_unknown"

\- reconciliation\_status in \["submit\_unknown\_pending\_lookup", "lookup\_api\_failed"] 또는 비슷한 pending 상태

\- as\_of\_date 또는 주문일이 RULE\_UNKNOWN\_ORDER\_MAX\_LOOKUP\_DAYS 범위 이내

\- RULE\_UNKNOWN\_ORDER\_LOOKUP\_ENABLED=true



2\. broker lookup 함수 추가



rule\_order\_fill\_sync.py 내부에 다음 성격의 함수를 추가한다.



def \_lookup\_unknown\_orders(items, client, account, as\_of\_date):

&#x20;   """

&#x20;   submit\_unknown 상태 항목에 대해 KIS 당일 주문내역을 조회하여 접수 여부를 확인한다.

&#x20;   실제 KIS API를 테스트에서 직접 호출하지 않도록 테스트 가능하게 client 호출부를 분리한다.



&#x20;   매칭 기준:

&#x20;   - code

&#x20;   - side

&#x20;   - order\_qty

&#x20;   - as\_of\_date 또는 주문일

&#x20;   """



3\. 매칭 기준



broker\_order\_id가 없는 submit\_unknown 주문은 아래 기준으로 보수적으로 매칭한다.



필수 기준:

\- 종목코드 code 일치

\- 매수/매도 side 일치

\- 주문수량 order\_qty 일치

\- 주문일 as\_of\_date 일치



가능하면 추가 기준:

\- 주문가격 또는 limit\_price 근접

\- 주문시각이 submit 시간 이후

\- 계좌번호 또는 account profile 일치



주의:

\- 매칭 기준이 불명확하면 자동 복구하지 말고 reconcile\_required로 둔다.

\- 복수 매칭이면 reconcile\_required로 둔다.

\- 매칭 없음이면 reconcile\_required로 둔다.



4\. lookup 결과별 상태 전환



\- 매칭 1건 성공:

&#x20; order\_status = "submitted"

&#x20; reconciliation\_status = "lookup\_matched\_submitted"

&#x20; broker\_order\_id 저장

&#x20; broker\_order\_time 또는 주문번호 등 조회 결과에서 얻은 메타데이터가 있으면 저장

&#x20; 이후 기존 submitted fill sync 흐름이 처리할 수 있게 한다.



\- 매칭 없음:

&#x20; order\_status = "reconcile\_required"

&#x20; reconciliation\_status = "lookup\_no\_match"

&#x20; 신규 주문이 무리하게 진행되지 않도록 기존 reconciliation guard가 이 상태를 감지할 수 있는지 확인한다.

&#x20; 감지하지 못한다면 최소한 rule\_order\_fill\_sync 결과에 명확히 남긴다.



\- 매칭 복수:

&#x20; order\_status = "reconcile\_required"

&#x20; reconciliation\_status = "lookup\_ambiguous\_match"



\- 조회 API 실패:

&#x20; order\_status = "submit\_unknown" 유지

&#x20; reconciliation\_status = "lookup\_api\_failed"

&#x20; error\_message 기록



5\. reconcile\_required 지속 알림



reconcile\_required 상태가 다음 사이클까지 지속되면 RULE\_NOTIFY\_ON\_RECONCILE\_REQUIRED=true일 때 notify\_critical을 호출한다.



title:

\[RULE] 주문 미확인 지속 - 즉시 수동 확인 필요



message:

{as\_of\_date} | code={code} | side={side} | broker lookup 실패



details:

{

&#x20; "code": code,

&#x20; "name": name,

&#x20; "side": side,

&#x20; "order\_qty": qty,

&#x20; "order\_status": "reconcile\_required",

&#x20; "reconciliation\_status": current\_status,

&#x20; "action\_required": "KIS 주문내역과 계좌 체결내역을 수동 확인하세요."

}



주의:

\- notify\_critical 호출 실패가 fill sync 저장을 방해하지 않도록 try/except로 보호한다.

\- 알림 실패 시 warning 로그만 남긴다.

11\. 이번 과제는 Rule 자동매매 주문 복구만 다룬다는 설명

\## Step 10. 주의사항



반드시 지켜라.



1\. KIS API 호출을 테스트 목적으로 실행하지 말 것

2\. 실계좌 주문 로직을 직접 실행하지 말 것

3\. python/kis\_client.py, python/kis\_live\_account.py, python/notifier.py는 수정하지 말 것

4\. 기존 submitted 상태 항목의 fill sync 흐름은 변경하지 말 것

5\. failed 상태의 기존 동작은 변경하지 말 것

6\. broker\_order\_id 없는 항목의 lookup은 종목코드·날짜·수량·side 매칭으로 처리한다

7\. 복수 매칭 시 자동 복구하지 말고 reconcile\_required로 보수적 처리한다

8\. 매칭 없음도 reconcile\_required로 처리한다

9\. lookup API 실패 시 submit\_unknown 상태를 유지한다

10\. 알림 실패가 주문 결과 저장이나 fill sync 저장을 방해하지 않게 한다

11\. 기존 운영 파일을 삭제하지 말 것

12\. 변경 전후 영향 범위를 반드시 보고할 것
