# 블로그 콘텐츠 자동 생성 — 운영 가이드

LeeTrader 종가 데이터를 바탕으로 네이버 블로그 / 티스토리 게시용 글 초안을 자동 생성하는 모듈의 운영 가이드.

설계 문서: [콘텐츠자동화PRD.md](콘텐츠자동화PRD.md)

---

## 1. 한눈에 보는 운영 흐름

```
18:10  종가 배치 실행 (run_daily_scheduler.py, command_set=close)
   ├─ 추천·랭킹·시장 데이터 생성 (핵심 스텝)
   └─ generate_blog_posts.py --type all  ← 자동 실행 (비치명적 후처리)
          ↓
   outputs/blog_drafts/ 에 글 파일 6개 생성
          ↓
   운영자: 파일 열기 → 내용 확인 → 복사
          ↓
   네이버 블로그 / 티스토리에 붙여넣고 게시
```

운영자가 할 일은 **생성된 파일을 복사해서 블로그에 올리는 것뿐**이다. 글 작성·데이터 입력은 시스템이 처리한다.

---

## 2. 매일 운영 루틴 (운영자)

1. 18:10 종가 배치가 끝나면 `outputs/blog_drafts/`에 당일 파일이 생성된다.
2. 올릴 플랫폼에 맞는 파일을 연다.
   - 네이버 → `..._naver.txt` (그대로 복사·붙여넣기)
   - 티스토리 → `..._tistory.md` (마크다운 모드로 붙여넣기)
3. 내용을 한 번 훑어본다 (§6 체크리스트).
4. `[이미지 삽입 위치]` 표시 자리에 차트/캡처 이미지를 넣는다 (네이버 권장).
5. 게시한다.
6. 어떤 글을 어디에 올렸는지 별도 기록(스프레드시트 등)에 남긴다 (§7).

## 3. 생성되는 파일

위치: `outputs/blog_drafts/`

파일명: `{기준일}_type{유형}_{플랫폼}.{확장자}`

| 파일 예시 | 유형 | 플랫폼 |
|---|---|---|
| `2026-05-28_typeA_naver.txt` | 오늘의 AI 관찰 종목 | 네이버 |
| `2026-05-28_typeA_tistory.md` | 〃 | 티스토리 |
| `2026-05-28_typeB_naver.txt` | 랭킹 급상승 종목 | 네이버 |
| `2026-05-28_typeB_tistory.md` | 〃 | 티스토리 |
| `2026-05-28_typeC_naver.txt` | 시장 분석 | 네이버 |
| `2026-05-28_typeC_tistory.md` | 〃 | 티스토리 |

- 네이버용은 plain text(.txt), 티스토리용은 markdown(.md)이다.
- 같은 날 같은 파일이 있으면 기본은 건너뛴다. 종가 배치는 `--force`로 매번 새로 덮어쓴다.

## 4. 수동 실행 (필요할 때)

평소엔 종가 배치가 자동으로 돌리므로 수동 실행은 불필요하다. 다시 만들거나 특정 유형만 만들 때 사용한다.

```bash
# 전체(A·B·C) 다시 생성
python python/generate_blog_posts.py --type all --force

# 전체 생성 후 Gemini로 A타입 티스토리 대표 글만 문장 다듬기
python python/generate_blog_posts.py --type all --force --polish-gemini

# 전체 생성 후 Gemini로 A타입 티스토리 대표 글만 SEO/기업별 사업/산업 맥락 보강
python python/generate_blog_posts.py --type all --force --enrich-gemini

# 특정 유형만
python python/generate_blog_posts.py --type A

# 특정 플랫폼만
python python/generate_blog_posts.py --type A --platform naver

# 특정 날짜 데이터로 (데이터가 그 날짜로 존재해야 함)
python python/generate_blog_posts.py --type all --date 2026-05-28 --force
```

옵션 요약

| 옵션 | 의미 |
|---|---|
| `--type` | `A` / `B` / `C` / `all` (기본 `A`) |
| `--platform` | `naver` / `tistory` (미지정 시 둘 다) |
| `--date` | 데이터 기준일 (미지정 시 데이터의 asof_date) |
| `--force` | 기존 파일 덮어쓰기 |
| `--strict` | 요청 날짜와 데이터 날짜가 다르면 중단 |
| `--enrich-gemini` | Google AI Studio/Gemini로 SEO 구조, 기업별 주요 사업, 산업 맥락을 보강한 최종본 생성 |
| `--polish-gemini` | Google AI Studio/Gemini로 본문 문단을 다듬은 최종본 생성 |
| `--polish-ollama` | 로컬 Ollama로 본문 문단을 다듬은 최종본 생성 |
| `--keep-latest-only` | 로컬 파일과 DB payload를 최신 기준일 1개만 유지 |

Gemini 후처리 환경변수:

| 환경변수 | 의미 |
|---|---|
| `G_STUDIO_API_KEY` | Google AI Studio API 키. `GEMINI_API_KEY`, `GOOGLE_API_KEY`도 대체 인식 |
| `BLOG_ENRICH_GEMINI_ENABLED=1` | 종가 배치 후 블로그 생성 시 Gemini SEO/사업/산업 설명 보강 자동 실행 |
| `BLOG_ENRICH_GEMINI_MODEL` | 기본값 `gemini-3.1-flash-lite` |
| `BLOG_POLISH_GEMINI_ENABLED=1` | 종가 배치 후 블로그 생성 시 Gemini 문장 다듬기 자동 실행 |
| `BLOG_POLISH_GEMINI_MODEL` | 기본값 `gemini-3.1-flash-lite` |
| `BLOG_GEMINI_TARGET_TYPES=A` | Gemini를 적용할 글 유형. 무료 티어 기본 운영은 A타입만 |
| `BLOG_GEMINI_TARGET_PLATFORMS=tistory` | Gemini를 적용할 플랫폼. 무료 티어 기본 운영은 티스토리 대표 글 1개만 |
| `BLOG_POLISH_PROVIDER=gemini` | DB 저장 시 Gemini 최종본을 우선 사용 |
| `BLOG_POLISH_TEMPERATURE` | 문장 변형 강도. 기본 `0.45` |
| `BLOG_OUTPUT_KEEP_LATEST_ONLY=1` | 로컬 `outputs/blog_drafts`, `outputs/blog_polished`와 로컬/웹 DB 블로그 payload를 최신 기준일만 유지 |

Gemini 최종본은 `outputs/blog_polished/{날짜}_type{유형}_{플랫폼}_gemini_polished.*`로 저장된다.
DB 저장 시 원본 초안 payload 안에 `polished`로 포함되며, 운영 대시보드의 블로그 초안 화면은 `polished` 최종본이 있으면 이를 우선 표시한다.

무료 Gemini API는 일일 요청 수 제한이 작으므로 기본 운영에서는 원본 초안은 A/B/C와 네이버/티스토리를 모두 생성하더라도, Gemini 보강은 `typeA_tistory` 1개에만 적용한다. `--type all --enrich-gemini`를 실행해도 `BLOG_GEMINI_TARGET_TYPES`, `BLOG_GEMINI_TARGET_PLATFORMS` 기본값 때문에 API 호출은 대표 글 1건으로 제한된다.

## 5. 데이터 소스 (유형별)

| 유형 | 데이터 소스 우선순위 |
|---|---|
| A 관찰 종목 | `serving/daily_recommendations.json` (파일) |
| B 랭킹 급상승 | ① DB `daily_ranking` → ② `fixtures/blog/daily_ranking_sample.json` (mock) |
| C 시장 분석 | ① DB `market_status` → ② `outputs/market_status_validation_report.json` (실데이터 파일) → ③ mock |

- **운영 PC**(DATABASE_URL 설정)에서는 A·B·C 모두 실데이터로 생성된다.
- **DB가 없는 PC**에서는 A·C는 실데이터 파일로 동작하고, **B만 mock(샘플)**로 생성된다. 로그에 `fixture 사용(개인 PC 모드)`로 표시된다.
- 로그에서 `시장상태: ... 사용`, `랭킹 ... 사용` 메시지로 어떤 소스를 썼는지 확인할 수 있다.

## 6. 게시 전 체크리스트

- [ ] 날짜·종목·숫자가 오늘 데이터와 맞는가
- [ ] 영문 코드가 그대로 노출된 곳은 없는가 (정상이면 모두 한글)
- [ ] "추천/매수/보장" 같은 단정 표현이 없는가 (관찰·참고 표현이어야 함)
- [ ] Gemini/Ollama 최종본을 쓴 경우, 숫자·종목명·상태값이 원문과 달라지지 않았는가
- [ ] Gemini SEO 최종본을 쓴 경우, 제목·도입·FAQ가 과장 없이 검색 의도에 맞게 정리됐는가
- [ ] 면책 고지 문장이 글 끝에 있는가
- [ ] 네이버 글은 `[이미지 삽입 위치]`에 이미지를 넣었는가
- [ ] 글자 수가 충분한가 (A는 보통 2,000자 이상, B·C는 1,000~1,500자대)

## 7. 저품질(유사문서) 회피 — 운영 수칙

시스템은 제목·도입·문구·구조를 날짜별로 자동 변형하고, 네이버/티스토리를 서로 다르게 생성한다(`templates/blog/variations.json`). 하지만 **코드로 못 막는 부분은 운영에서 보완**한다.

- 매일 같은 시각에 기계적으로 올리지 않는다 (게시 시각 분산).
- 매번 같은 이미지/캡처를 재사용하지 않는다.
- 네이버·티스토리에 **동일 글을 그대로 동시 게시하지 않는다**. (변형이 다르게 나오지만, 가능하면 한쪽은 한두 문장 직접 가필)
- 주 1~2회는 도입/마무리에 운영자 코멘트를 직접 덧붙인다.
- 게시 이력(날짜·유형·플랫폼·URL)을 스프레드시트 등에 기록해 중복 게시를 막는다.

## 8. 트러블슈팅

| 증상 | 원인 / 조치 |
|---|---|
| 파일이 안 생김 | 종가 배치 로그 확인. `generate_blog_posts`는 비치명적 스텝이라 실패해도 경고만 남고 배치는 통과한다. 로그에서 해당 스텝 경고 확인 후 수동 재실행. |
| 글 날짜가 어제로 나옴 | 종가 데이터(`daily_recommendations.json`)의 `asof_date`가 갱신 안 됨 → 종가 배치가 정상 완료됐는지 확인. |
| B가 샘플 데이터처럼 보임 | 그 PC에 DB 연결이 없어 mock 사용 중. 운영 PC(DATABASE_URL 설정)에서 생성해야 실데이터. |
| 같은 글이 안 바뀜 | 변형은 **날짜 시드** 기반이라 같은 날·같은 유형은 동일하게 재현된다(정상). 날짜가 바뀌면 자동으로 달라진다. |
| 문구를 바꾸고 싶음 | `templates/blog/variations.json`의 문구 풀을 편집하거나, `templates/blog/type_*.j2` 템플릿을 수정. |
