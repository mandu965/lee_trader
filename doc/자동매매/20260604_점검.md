# 2026-06-04 AI 자동매매 중간 점검

## 1. 결론

2026-06-04 기준 KR AI 자동매매는 실계좌 주문, 보유 동기화, 체결 동기화, 보유기간 보호 로직이 모두 작동 중이다. 특히 `ai_position_state.json`에 각 보유 종목의 `entry_date`, `entry_price`, `peak_price`가 누적되고 있고, `trade_intents`에서 보유 10영업일 미만 종목의 교체가 보류된 사례가 확인된다.

다만 현재 상태는 `BUY_ALLOWED`가 아니라 `PILOT`이며, KPI는 `ALERT`다. 따라서 신규 확대보다 중간 점검과 운영 정합성 보강이 우선이다.

핵심 판단:

- 자동매매 실행: 정상 작동. 2026-06-04 09:30 사이클 성공, 4건 제출.
- 실계좌 동기화: 정상 작동. 2026-06-04 16:00 및 18:28 기준 잔고 확인.
- 보유기간 보호: 작동 중. 10영업일 미만 교체 보류 기록 확인.
- 운영 모드: `PILOT`. 제한 진입만 허용하는 상태.
- 성과/품질: 아직 확대 불가. `score_kpi_monitor`는 `ALERT`, walk-forward soft diagnostics rejected.
- 보완 필요: 장후 live sync가 `ai_position_state`를 갱신하지 않아 장후 고점/현재가가 상태파일에 늦게 반영된다.

## 6. Gate/KPI/성과 점검

### 6.1 Gate

`serving/buy_gate_status.json` 기준 전체 상태는 `PILOT`이다.

PILOT 사유:

- matured benchmark dates 0 < required 3
- operational confidence calibration not reliable enough
- walk-forward acceptance rejected on soft diagnostics
- market regime은 bull이나 breadth 0.314로 확산 신호 약함

따라서 현재 자동매매는 “제한 실운용”이다. 신규 진입은 가능하지만, 공격적 확대나 완전 자동 확대는 아직 이르다.

## 7. 중간 점검 포인트

### 7.1 즉시 점검

- `live_sync`에 `update_ai_position_state` 추가 검토.
- 09:30 자동매매 실행 시 `asof_date`가 최신 거래일인지 명시 로그 추가.
- `trim_ratio_zero`가 반복되는 종목은 “실행할 수 없는 TRIM”으로 남지 않도록 최소 주문수량/비중 계산 로직 점검.
- `model_portfolio`는 5종목 목표인데 실제 계좌는 10종목 보유다. 의도한 운영 모드가 “Top5 집중”인지 “Top10 분산”인지 문서/정책을 맞춘다.
- 운영 서버 Python 환경에 `jinja2` 설치 또는 블로그 초안 후처리 분리. 자동매매에는 직접 영향이 작지만 운영 warning을 만든다.

### 7.2 이번 주 관찰

- 한온시스템: 현재 -4.55%, stop-loss -7% 전이지만 고점 대비 -5% 부근이다. 다음 동기화 후 trailing stop 조건을 확인한다.
- 한국타이어앤테크놀로지: 비중 12.26%로 가장 크며 수익권이다. 보유기간 보호로 교체 보류된 상태라 10영업일 경과 전후 재평가가 중요하다.
- 한국금융지주: TRIM executable 후보이나 preview에서는 `trim_ratio_zero`가 날 수 있다. 실제 주문 가능 수량 산정 확인 필요.
- 신규 3종목(GS, 비에이치아이, 우리기술): 2026-06-04 진입 직후라 최소 10영업일 보호 구간에 들어간다. 성급한 교체보다 리스크 조건 중심으로 본다.

### 7.3 승격 조건

PILOT에서 더 적극적 운용으로 가려면 최소한 아래 조건을 확인해야 한다.

- `score_kpi_monitor.overall_status`가 ALERT에서 WATCH/GOOD로 개선.
- benchmark matured dates가 최소 요건을 충족.
- confidence calibration 신뢰도 개선.
- BUY intent 성과가 음수 편향에서 벗어남.
- `ai_position_state`가 장후 동기화까지 반영되어 trailing/보유기간 판단이 안정화.

## 8. 운영 판단

현재 자동매매는 “멈출 상태”는 아니다. 주문/체결/잔고/보유기간 추적은 살아 있고, 특히 조기 교체 보호가 실제로 동작한다.

하지만 “늘릴 상태”도 아니다. Gate가 PILOT이고 KPI가 ALERT이며 BUY 성과가 약하다. 지금은 다음 방향이 적절하다.

1. 자동매매는 계속 `PILOT`으로 유지한다.
2. 신규 매수는 제한 진입만 허용한다.
3. 보유기간 10영업일 보호는 유지한다.
4. 장후 `ai_position_state` 갱신을 보강한다.
5. 다음 중간 점검은 2026-06-07 이후, 신규 3종목의 D+1~D+3 흐름과 한온시스템 리스크 조건을 중심으로 본다.

### 9.3 중복 실행 / 재실행 흔적

2026-06-04 18:10 배치만 보면 동일 `close` 스케줄러가 중복으로 다시 시작한 흔적은 없다. `auto_ops_scheduler.log`에는 다음 두 건만 있다.

### 9.4 과거 중복 방지락 발동 이력

중복 실행 우려는 완전히 근거 없는 것은 아니다. 2026-06-02 로그에는 다음 에러가 반복됐다.

`Another run_pipeline instance is already running. Check for duplicate scheduler or task triggers.`

이 메시지는 `run_pipeline.py`의 PostgreSQL advisory lock이 이미 잡힌 상태에서 다른 `run_pipeline`이 다시 시작되려 할 때 발생한다. 즉, 실제로 중복 실행 시도가 있었고, 다행히 락이 막았다.

다만 문제는 실패 후 짧은 간격으로 재시도가 반복됐다는 점이다. 2026-06-02에는 18:28:42, 18:29:18, 18:29:53 전후로 재시도 흔적이 있다. `SCHEDULER_SKIP_AFTER_FAILURE_UNTIL_NEXT_DAY=1` 설정이 있어야 같은 날 재시도를 멈추는데, 당시에는 상태 반영 전 재평가 또는 컨테이너 재기동/상태 파일 갱신 타이밍 문제로 여러 번 시도된 것으로 보인다.

### 9.5 판단

2026-06-04의 긴 실행은 중복 실행보다는 정상 단일 실행의 후처리 지연이다. 하지만 2026-06-02에 중복 실행 방지락이 발동한 이력이 있으므로 스케줄러 안정성 보강은 필요하다.

우선순위:

1. `sync_web_display_data.py`를 18:10 핵심 배치에서 분리하거나, `flow_daily`/US macro 동기화를 별도 저빈도 배치로 분리한다.
2. `submit_live_orders.py`의 preview 모드에서 웹 동기화가 필요한지 재검토한다. 주문 preview가 웹 전체 동기화까지 수행하면서 6분을 소비한다.
3. `scheduler_health_report.md` 생성이 누적 로그 전체를 훑는 구조인지 확인하고, 최근 N일 또는 오늘 command_set만 집계하도록 제한한다.
4. `run_daily_scheduler.py`에 파일 기반 scheduler-level lock을 추가해 같은 command_set이 이미 실행 중이면 즉시 skip 처리한다. 현재는 `run_pipeline.py` 내부락은 있지만, 스케줄러 전체락은 약하다.
5. 실패 직후 `last_attempt_schedule_slot` 또는 `last_failure_skip_date`가 반드시 먼저 저장되도록 보강해 30초 polling 재시도를 막는다.
6. `generate_blog_posts`용 `jinja2`를 운영 이미지에 설치하거나, 블로그 초안 생성은 별도 배치로 분리한다.

운영 결론:

- 자동매매 주문 중복 위험은 2026-06-04 로그에서는 확인되지 않았다.
- 파이프라인 중복 실행 시도는 2026-06-02에 실제로 있었다.
- 현재 가장 큰 지연 원인은 `run_pipeline` 자체보다 웹 동기화/헬스 리포트/optional 블로그 후처리다.
- 18:10 배치는 핵심 산출물 생성과 웹/블로그/헬스 후처리를 분리하는 방향이 안전하다.
