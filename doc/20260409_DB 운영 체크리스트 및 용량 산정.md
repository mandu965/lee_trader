# DB 운영 체크리스트 및 용량 산정

작성일: 2026-04-09

## 1. 현재 상태 요약

- 핵심 운영 조회 경로는 DB-first로 전환됨
- CSV/JSON은 여전히 생성 산출물, 백업, parity 검증, 일부 보조 리포트 역할로 유지됨
- 운영 화면 기준:
  - `manual-trading`, `trading-policy`, `ops-readiness`, `score-kpi`, `top20-meaningfulness`는 DB payload 우선 조회
  - `daily_recommendations`, `operational_buy_gate`, `score_kpi_monitor`, `walkforward_acceptance`, `intraday_recommendations` 등은 `research.app_payload_store`에 적재
- 파이프라인 기준:
  - 핵심 public 테이블은 CSV와 DB parity가 맞춰진 상태
  - 운영 보조 아티팩트도 payload store를 통해 DB로 동기화됨

## 2. flow_daily가 점수 산정에 미치는 현재 영향

### 2.1 현재 직접 영향

현재 기준으로 `flow_daily`는 **최종 점수(final_score) 산정에 직접 사용되지 않음**.

근거:

- `python/run_pipeline.py`
  - `download_flows_kis.py`와 `check_flow_ingestion.py`는 optional step
  - 수집/검증까지만 수행
- `python/scoring/final_score.py`
  - final score 축은 `ret_score`, `prob_score`, `tech_score`, `qual_score`, `risk_penalty`
  - `flow_daily`를 직접 읽는 로직 없음
- `python/ranking_builder.py`
  - 입력은 `predictions.csv`, `features.csv`, `market_status.csv`, `universe.csv`, `scores_final.csv` 중심
  - `flow_daily` 직접 join 없음

정리:

- `flow_daily` 수집 여부가 지금 당장 개별 종목 `final_score`를 바꾸지는 않음
- 현재는 "저장만 되고, 점수식에는 연결되지 않은 상태"에 가까움

### 2.2 현재 간접 영향

현재 간접 영향도 사실상 제한적임.

- 시장 국면 관련 컬럼으로 쓰이는 것은 `market_status.foreign_net_5d`
- 이 값은 현재 `fetch_market_data.py`에서 만든 market status 계열을 통해 들어감
- 즉 `flow_daily`를 직접 읽어 market regime을 바꾸는 구조는 아직 아님

### 2.3 향후 붙일 경우 영향 포인트

`flow_daily`를 실전적으로 붙이려면 아래 3축 중 하나로 들어가는 게 맞음.

1. 시장 국면 보강
- 외국인/기관 순매수 누적을 `market_status`의 보조 신호로 사용
- 예: `foreign_net_5d > 0` 외에 `universe flow breadth`, `top20 flow support ratio` 추가

2. 종목 단위 수급 축 추가
- 개별 종목별 `flow_score`를 만들어 `tech_score` 보조축 또는 별도 진입 필터로 사용
- 예: 외국인/기관 5일 순매수 양수, 거래대금 대비 순매수 비율 상위, 수급 지속성 점수

3. 진입 veto 또는 승급 조건
- `buyability_status` 또는 `promotion_readiness_score`에 반영
- 예: `TRUSTED`여도 최근 5일 수급이 급격히 나쁘면 `WATCH` 유지

### 2.4 권장 결론

현 시점에서는 `flow_daily`를 곧바로 `final_score` 본식에 넣기보다 아래 순서가 더 안전함.

1. `buyability/promotion_readiness` 보조축으로 먼저 사용
2. 운영자 페이지에 `flow support` 진단 카드 추가
3. 검증 후에만 `final_score` 또는 `market regime` 본식 반영 검토

이유:

- 수급 데이터는 단기 노이즈가 강함
- 본식에 바로 넣으면 rank churn이 커질 수 있음
- 먼저 운영 판단 보조축으로 붙여야 회귀/과최적화 위험이 낮음

## 3. DB-only 운영 체크리스트

### 3.1 일일 운영 체크

- `ops-readiness`에서 `recent artifact refresh`가 오늘 날짜인지 확인
- `ops-readiness`에서 `auto close success`, `auto intraday success` 확인
- `daily_recommendations`, `operational_buy_gate`, `score_kpi_monitor`, `top20_meaningfulness_report`의 `asof_date`가 최신 랭킹일과 맞는지 확인
- `csv_db_parity_report.md`에서 mismatch가 0인지 확인
- `research.app_payload_store`에 핵심 payload 10개 이상이 존재하는지 확인
- `manual-trading`과 `ops-readiness` 화면이 정상 응답하는지 확인
- `pipeline_history`에서 실패 step이 있어도 전체 success로 끝난 항목이 없는지 확인

### 3.2 배포 전 체크

- DB 연결 문자열이 API, scheduler, scheduler-recovery에서 동일한지 확인
- `schema.sql` 최신 버전이 반영됐는지 확인
- `research.app_payload_store` 존재 여부 확인
- `daily_ranking`, `prediction_history`, `ranking_history` 최신일 확인
- `auto_ops_scheduler_status`, `auto_ops_recovery_scheduler_status` payload가 DB에 적재되는지 확인
- 운영자 메모 저장 시 DB에도 반영되는지 확인

### 3.3 장애 대응 체크

- DB 장애 시 file fallback으로 최소 조회는 되는지 확인
- `run_operational_refresh.py` 단독 실행으로 핵심 payload 복구 가능한지 확인
- `sync_auxiliary_payloads.py` 단독 실행으로 보조 payload 복구 가능한지 확인
- `csv_db_parity_sync` 재실행으로 public 핵심 테이블 parity 복구 가능한지 확인

## 4. 현재 기준 DB 용량 증가 추정

주의:

- 아래는 현재 사용 중인 append 성격 테이블 중심 추정치
- replace 성격 테이블은 "순수 누적 증가"가 거의 없다고 보고 제외
- 실제 디스크 사용량은 인덱스, VACUUM, page slack, WAL에 따라 더 커질 수 있음

### 4.1 현재 운영 기준 추정

실무 계획용 권장치:

- 평시: `0.3 ~ 0.6 MB/day`
- 월간(30일 환산): `9 ~ 18 MB/month`
- 연간(365일 환산): `0.11 ~ 0.22 GB/year`

보수적이지 않은 순수 row payload 관점 추정치는 약 `0.21 MB/day` 수준이지만, 운영 계획은 위 보수치로 잡는 것이 안전함.

### 4.2 현재 주요 증가 테이블

| 테이블 | 일일 증가 성격 | 비고 |
| --- | ---: | --- |
| `research.prediction_history` | 약 44 KB/day | 203종목 기준 |
| `research.ranking_history` | 약 38 KB/day | 203종목 기준 |
| `research.paper_trading_position` | 약 16 KB/day | 최근 run 기준 |
| `research.paper_trading_nav` | 약 8 KB/day | 최근 run 기준 |
| `public.pipeline_history` | 약 3 KB/day | step 로그 |
| `research.app_payload_store` | overwrite 성격 | payload key upsert라 순누적 작음 |

## 6. flow_daily 포함 시나리오 용량 추정

### 6.1 전제

- `download_flows_kis.py`는 종목 1개, 날짜 1개당 보통 2 row 생성
  - `foreign`
  - `institution`
- 즉 순증 row 수는 대략:
  - `일일 신규 row = 종목 수 x 2`
- `7일 window fetch`를 돌려도 DB는 upsert라서 중복 누적되지 않음
- row 본문 + 인덱스 포함 실무 추정치는 대략 `0.9 ~ 1.3 KB/row`로 보는 것이 적절
- raw JSON 파일(`output/kis_flow_raw`) 용량은 아래 표에 **포함하지 않음**

### 6.2 시나리오 표

| 대상 종목 수 | 일일 신규 row | 일일 증가량 | 월간(21영업일) | 연간(252영업일) |
| --- | ---: | ---: | ---: | ---: |
| 203종목 | 406 | 0.36 ~ 0.52 MB | 7.6 ~ 10.9 MB | 91 ~ 131 MB |
| 500종목 | 1,000 | 0.88 ~ 1.27 MB | 18.5 ~ 26.7 MB | 222 ~ 320 MB |
| 1,000종목 | 2,000 | 1.76 ~ 2.54 MB | 37.0 ~ 53.3 MB | 444 ~ 640 MB |

### 6.3 현재 시스템 총량에 미치는 영향

현재 운영 증가량(`0.3 ~ 0.6 MB/day`)에 `flow_daily`를 더하면:

- 203종목 기준:
  - 총합 약 `0.66 ~ 1.12 MB/day`
- 500종목 기준:
  - 총합 약 `1.18 ~ 1.87 MB/day`
- 1,000종목 기준:
  - 총합 약 `2.06 ~ 3.14 MB/day`

즉 `flow_daily`를 붙여도 203종목 수준에서는 연간 수백 MB 이내로 충분히 관리 가능함.

## 7. 운영 판단 요약

- 현재 `flow_daily`는 점수식 직접 영향이 거의 없음
- 즉 지금 DB 용량 관점에서 `flow_daily`를 붙여도 부담은 크지 않음
- 다만 raw JSON 저장까지 계속 유지하면 DB보다 파일 용량 증가가 더 빨라질 수 있음
- 따라서 실무 권장안은:

1. `flow_daily`는 DB 적재 유지
2. raw JSON 파일은 보존기간 정책 적용
3. 점수식 직접 반영 전, `buyability/promotion_readiness` 보조축으로 먼저 검증

## 8. 권장 다음 단계

1. `flow_daily` 기반 `flow_support_score` 설계
2. 운영자 페이지에 `수급 지지율` 카드 추가
3. `buyability_status` 승급 조건에만 1차 반영
4. 최소 1~2개월 shadow 검증 후 `final_score` 반영 여부 재검토
