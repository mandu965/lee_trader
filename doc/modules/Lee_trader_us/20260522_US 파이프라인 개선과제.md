# 20260522_US 파이프라인 개선과제

> 상태 메모: 2026-05-22 기준 현재 운영 원칙상 US 자동매매는 `paper-only` 유지가 기본이다.  
> 따라서 이 문서는 `live 전환` 문서가 아니라, **US paper 운영 품질을 높이기 위한 파이프라인 개선과제 정리 문서**로 본다.

## 1. 목적

이번 점검의 목적은 개별 기능 추가가 아니라, 아래 전체 흐름을 기준으로 `US 파이프라인의 버그 / 구조적 누락 / 운영상 위험`을 찾는 것이었다.

- 종목 선정
- 가격 수집
- 재무 수집
- 피처 생성
- 학습
- 예측
- 점수 산정
- paper 후보 선별 및 주문 생성

결론부터 적으면, **치명적 결함은 "모듈이 아예 없다"보다 "모듈은 있는데 연결과 시점 정합성이 깨져 있는 부분"에 더 많이 존재한다.**

---

## 2. 핵심 결론

현재 US 파이프라인의 우선 개선축은 아래 5가지다.

1. `정식 파이프라인 1개로 단일화`
2. `stale ranking 사용 차단`
3. `재무 as-of 조인 정합성 확보`
4. `학습 피처 스펙과 실제 생성 피처 정렬`
5. `수급 레이어는 현재 없음으로 명시`

즉 지금 필요한 것은 모델 교체보다 먼저 **운영 파이프라인의 일관성 확보**다.

---

## 3. 주요 Findings

### 3-1. 파이프라인 연결 구조가 이원화되어 있음

현재 US 일간 실행 경로는 하나로 보이지만 실제로는 두 갈래다.

- `python/us/run_us_daily_pipeline.py`
- `scripts/run_us_daily_pipeline.ps1`

문제는 이 둘이 같은 흐름을 보장하지 않는다는 점이다.

#### 확인 내용

- `run_us_daily_pipeline.py`
  - universe load
  - price collect
  - quality validation
  - base feature build
  - macro feature build
  - sector feature build
  - optional ML ranking
  - trade scheduler / buy scheduler

- `run_us_daily_pipeline.ps1`
  - `run_us_daily_pipeline.py`
  - `build_us_relative_strength_features.py`
  - `calculate_us_stock_rule_scores.py`

즉, 본체 파이프라인과 스크립트 래퍼가 서로 다른 완성 형태를 가정한다.

#### 추가 문제

스크립트는 아래처럼 본체에 `--mode incremental`을 넘긴다.

```powershell
& $python python/us/run_us_daily_pipeline.py --mode incremental
```

그런데 `run_us_daily_pipeline.py`는 `--mode` 인자를 받지 않고 `--incremental`, `--backfill`만 받는다.

이 상태는 다음 의미를 가진다.

- 운영자가 어떤 실행 경로가 정식인지 혼동할 수 있음
- 직접 실행 결과와 스케줄러 실행 결과가 달라질 수 있음
- 스케줄러 래퍼 기준으로는 첫 단계부터 실패 가능성 존재

#### 개선 방향

- `run_us_daily_pipeline.py`를 유일한 정식 orchestrator로 고정
- `.ps1`는 thin wrapper만 유지
- `rule score`, `RS`, 필요 시 `label`, `financial feature`까지 본체에서 명시적으로 호출

---

### 3-2. 재무 데이터 조인에 look-ahead leakage 위험 존재

현재 가장 중요한 구조적 리스크다.

#### 확인 내용

- 재무 raw 수집 시 `reported_date`가 채워지지 않고 `None`으로 들어감
- 이후 학습/예측에서는 `fiscal_date <= trade_date` 기준으로 LOCF 조인

이 방식은 실제 공시일 이전 시점에도 미래 재무가 붙을 수 있다.

예를 들어:

- 2026-05-10 거래일 feature
- 2026-05-15에 공개된 분기 재무
- 그런데 fiscal_date가 2026-03-31이면
- 현재 구조에서는 2026-05-10에도 이미 그 재무가 붙을 수 있음

이건 다음 영역을 모두 오염시킨다.

- rule score 해석
- ML 학습
- ML 예측
- backtest / paper 결과 해석

#### 개선 방향

- `reported_date` 수집 가능 여부 재확인
- 재무 feature 조인은 `reported_date <= trade_date` 기준으로 변경
- `reported_date`가 없으면 conservative fallback 필요
  - 예: 해당 row 사용 금지
  - 또는 일정 공시 지연 buffer 적용

#### 우선순위

`최우선`

---

### 3-3. paper 주문이 stale ranking을 사용할 수 있음

현재 paper 후보 로더는 요청 날짜와 정확히 일치하는 랭킹이 없어도, 그 이전 최신 날짜 랭킹을 가져올 수 있다.

이 fallback은 편해 보이지만 운영상 매우 위험하다.

#### 위험 시나리오

- 오늘 rule ranking 생성 실패
- candidate loader가 어제 ranking 사용
- paper 주문은 정상처럼 계속 생성
- 운영자는 당일 파이프라인 실패를 즉시 알기 어려움

paper 운영은 live보다 리스크가 낮아야 하는데, 이 구조는 오히려 **조용한 오류 은닉**을 만든다.

#### 개선 방향

- buy/sell/trade orchestration에서는 `requested_trade_date == ranking.trade_date` 강제
- 불일치 시:
  - 주문 생성 금지
  - `SOURCE_DATA_STALE`
  - 리포트 / 알림 / 로그 명시

#### 우선순위

`최우선`

---

### 3-4. ML 예측 단독 실행 경로는 현재 표준 rank upsert와 불일치

ML ranking은 파이프라인 내부 우회 경로에서는 비교적 안전하지만, standalone prediction 경로는 현재 표준과 맞지 않는다.

#### 확인 내용

- 현재 rank 테이블 표준 키: `(trade_date, symbol, source)`
- 그런데 `us_model_predict.py`는 `ticker` 기준 row payload와 `ON CONFLICT (ticker, trade_date, source)`를 사용

즉 다음 문제가 있다.

- standalone predict 결과가 정상 upsert되지 않을 수 있음
- ML 경로 문서와 실제 코드가 다를 수 있음
- 운영자가 `us_model_predict.py`를 직접 쓰면 오작동 가능

#### 개선 방향

- `us_model_predict.py`를 `upsert_us_rank_rows` 표준에 맞춰 정리
- `ticker` / `symbol` 사용 규칙 통일
- standalone script와 pipeline-internal path를 같은 writer로 통일

#### 우선순위

`상`

---

### 3-5. 학습 피처 스펙과 실제 생성 피처가 drift 상태

trainer가 기대하는 피처와 실제 daily feature writer가 저장하는 피처 사이에 불일치가 있다.

#### 예시

trainer 기대:

- `close_over_ma20`
- `dollar_volume_20`
- `sector_rel_ret_20d`
- `sector_rel_ret_60d`
- `sector_rank_pct`

실제 base feature writer 저장:

- `ret_*`
- `ma_*`
- `volume_avg_20d`
- `volume_ratio_20d`
- `rsi_14`
- `atr_14_norm`
- `bb_position`
- `high_52w_ratio`

즉 일부 피처는:

- 아예 생성되지 않거나
- 별도 스크립트에 의해 나중에 보강되거나
- trainer 코드만 남고 실사용 경로에서는 비어 있을 수 있다

이 상태는 모델 품질 이전에 **데이터 계약 자체가 불분명한 상태**다.

#### 개선 방향

- `ML_FEATURE_CONTRACT` 문서 또는 코드 상수 1곳에서 feature set 고정
- 실제 writer가 채우는 컬럼과 trainer가 읽는 컬럼을 일치시킴
- 미사용 피처는 trainer 목록에서 제거
- 필요한 피처는 base/derived builder에서 명시적으로 생성

#### 우선순위

`상`

### 3-6. 수급 레이어는 현재 사실상 미구현

이번 점검 질문에 `수급`이 포함되어 있었지만, 현재 US 파이프라인에 별도 수급 collector / feature builder / scorer는 없다.

존재하는 것은 주로 아래다.

- 가격
- 재무
- 기술 피처
- SPY/QQQ 상대강도
- 섹터 상대강도
- VIX / macro regime
- analyst consensus

즉 현재 문맥에서 `수급`은 아래 중 어느 것으로도 독립 구현되어 있지 않다.

- insider flow
- institutional flow
- short interest
- ETF flow
- options flow

#### 개선 방향

- 문서에 `현재 수급 레이어 없음`을 명시
- 향후 추가 후보를 별도 backlog로 분리
  - insider 거래
  - short interest
  - ETF net flow

#### 우선순위

`중`

## 4. 단계별 점검 메모

### 4-1. 종목 선정

현재는 사실상 `NASDAQ100 CSV 기반 universe`다.

체크 포인트:

- universe가 static CSV 기준으로 고정되어 있음
- 변경 감지와 deactivate 정책은 있지만 동적 선정 로직은 아님
- 종목 선정 자체보다 `universe 최신성` 관리가 중요

보완점:

- universe 업데이트 주기 명확화
- ETF / leveraged / inverse exclusion rule 문서화

### 4-2. 가격 수집 / 종가 기준

장점:

- adjusted close fallback 구조 존재
- quality validation 단계 존재

주의점:

- stale price를 엄격히 막는 구조는 quality 단계에 의존
- downstream order path에서 stale ranking과 결합되면 품질 저하 가능

### 4-3. 재무

핵심 리스크:

- reported_date 부재
- fiscal_date 기준 LOCF

이 부분은 반드시 수정 필요.

### 4-4. 피처

장점:

- 기술 피처 기본 세트는 무난함
- macro / sector / RS 확장도 존재

보완점:

- builder 간 역할 분리가 되어 있어도 본체 pipeline 연결이 약함
- feature contract drift 존재

### 4-5. 학습

보완점:

- feature contract 정리 필요
- leakage 제거 전 성과 해석 금지
- 현재 모델 성과 수치가 좋더라도 신뢰도 제한적일 수 있음

### 4-6. 예측

보완점:

- standalone path 정리 필요
- pipeline 내부 ML ranking과 외부 CLI path를 하나로 합칠 필요

### 4-7. 점수 산정

rule score 자체는 구조가 비교적 명확하다.

다만 전제조건이 있다.

- 조인 데이터가 정확해야 함
- 당일 trade_date 데이터가 정확히 있어야 함
- stale fallback이 없어야 함

즉 점수 함수보다 **점수 입력 데이터의 시점 정합성**이 더 중요하다.

## 6. 운영 기준 제안

현재 US paper 운영 기준에서는 아래를 기본 원칙으로 두는 것이 맞다.

1. `당일 ranking 없으면 주문 없음`
2. `재무 시점 정합성 확보 전 ML 성과 해석 보수적`
3. `정식 파이프라인은 1개만 허용`
4. `feature contract가 고정되기 전 모델 성능 수치 과신 금지`
5. `수급은 현재 없음으로 가정하고 전략 설명에 포함하지 않음`
